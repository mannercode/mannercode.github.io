# AI 코딩 글 작업 안내

현재 1편은 [ai_coding_part1.md](./ai_coding_part1.md)에서 작성한다. 1편은 참여자들의 경험과 판단, 관계의 변화를 중심으로 전개하며 전체 검토의 결과는 짧게 남긴다. 결제·단말 연동, DB 전환, 리팩터링, 동시번역, 새 시스템의 상세 검토는 [2편 메모](./ai_coding_part2_notes.md)에서 해결 방안을 설명하는 사례로 다룬다. 이후 개발자의 역할과 성장에 관한 추가 설명으로 이어간다.

블로그 발행본은 [_posts/2026-09-20-ai-coding-part1.md](../_posts/2026-09-20-ai-coding-part1.md)에 있다. 원고를 수정하면 발행본에도 반영한다. [유튜브 구성안](./presentation/ai_coding_part1_storyboard.md)은 페이지마다 **화면 내용**과 **대사**만 정리한다. 예상 시간이나 화면 전환·낭독 지시는 넣지 않는다. 대사는 저자의 말투에 맞춰 ‘했습니다·입니다’를 기본으로 쓰고, 실제로 말하기 편하게 문장을 풀어 쓴다. 구어체로 다듬기 위해 말끝을 ‘해요·했죠’로 바꾸지 않는다.

본문에 실제로 사용한 이미지·동영상은 [1편 본문 자료](../assets/ai-coding-part1/README.md)에 모아 둔다. 저자가 편집한 GitHub Projects 캡처도 이 폴더의 `github-projects.png`를 사용한다. 본문용 파일을 원본·후보 자료 폴더에 다시 복사하지 않는다.

기존의 세 초안은 중복되는 내용을 주제별 참고자료로 정리하고, 전체 원문은 `archive/`에 보관했다. 집필할 때는 아래 자료에서 필요한 사건과 논점을 찾고, 원래 문장이 필요하면 보관본을 확인하면 된다.

이 폴더의 원고·참고자료·보관본은 공개를 전제로 식별 정보를 일반화한다. 실제 서비스명과 저장소명은 역할 중심의 표현으로, 연락처와 도메인은 예시 값으로 바꾸고, 커밋 해시와 불필요한 지역명은 싣지 않는다. 기술명과 사례의 동작·검증 결과는 유지하며, 원래 이름과 대체 표기의 대응표는 이 폴더에 남기지 않는다.

1편에서는 사건의 상황·행동·결과를 따라간다. 제목은 본문에서 다루는 사건과 변화를 정확히 표현한다. 구체적인 연월 대신 사건의 순서와 의미 있는 기간을 본문에서 설명한다. 참고자료의 날짜는 근거로 보존하고, 원고에서 기간으로 바꿀 때는 확인된 범위로만 쓴다. 2편에서는 구체적인 사례를 살펴보며 어떤 판단과 작업 방식이 필요했는지 설명한다. 실제로 실행해 효과를 본 방법과 돌아보며 제안하는 대안을 구분한다. 개발 방법의 변화, 개발자의 역할과 성장, 학생의 학습 지원은 추가 설명으로 이어간다. 참고자료의 분류가 완성 원고의 목차를 정하는 것은 아니다.

문체는 담백하게 쓴다. 제목에 감상적인 부제나 결론을 붙이지 않고, 본문에서도 문단마다 교훈을 반복하지 않는다. 수식어가 길게 겹치거나 행동을 추상적인 표현으로 늘여 쓴 문장은 줄인다. 저자의 원래 감정 표현과 편집 과정에서 덧붙인 감정은 구분한다. 회고 기간은 ‘8개월’로 표기한다.

코딩 방식은 다음 용어로 구분한다.

- **직접 코딩**: 개발자가 코드를 직접 작성·수정하면서 구현하는 방식
- **AI 코딩**: 개발자가 요구사항을 설명하고 AI에게 코드 작성·수정을 맡긴 뒤 결과를 검토하는 방식

‘개발’은 요구사항 정리·설계·구현·검증 등을 포함하는 넓은 뜻으로 쓴다. 혼자 개발하거나 개발을 주도했다는 사실과 코딩 방식은 구분한다. 검토·실행·접근 등을 ‘직접’ 했다는 표현은 문맥에 맞게 유지한다. AI에게 일을 지시하고 결과를 확인하는 구체적인 서술까지 모두 ‘AI 코딩’으로 바꾸지는 않는다. 검토를 생략한 사례는 그 사실을 그대로 서술한다.

서비스·시스템·프로젝트는 완성 여부가 아니라 문장에서 가리키는 대상에 따라 구분한다.

- **서비스**: 고객에게 제공하는 기능과 이용 경험. 서비스의 방향·요구사항·출시·이용을 이야기할 때 쓴다. 아직 기획하거나 개발하는 단계에서도 서비스라고 부를 수 있다.
- **시스템**: 서비스를 구현하는 앱·서버·DB와 그 연결 구조. 실행·구조 분석·기술 구성·교체·복구·코드 검토의 대상을 가리킬 때 쓴다. 특정 구성 요소를 뜻하면 백엔드·앱·저장소처럼 더 구체적인 이름을 쓴다.
- **프로젝트**: 목표를 정하고 개발과 출시를 진행하는 일. 합류·일정·범위·인력·협업·진행 상황을 이야기할 때 쓴다. ‘시드 프로젝트’처럼 개발 도구에서 관용적으로 쓰는 표현은 유지한다.

같은 대상을 말해도 관점에 따라 용어가 달라질 수 있다. 서비스를 만들기 위한 프로젝트에서 시스템을 개발하는 관계다. 저장소명이나 프로젝트명을 서비스명으로 일괄 치환하지 않으며, 반복을 피하려고 세 용어를 번갈아 쓰지도 않는다.

저자가 구분용으로 사용하도록 지정한 프로젝트명은 실제 이름을 유지하고 역할 설명 뒤 괄호에 넣는다. 예를 들어 기존 시스템(`legacy`), 대표가 만든 시스템(`superman`), 새 백엔드(`marksman`), 사용자 앱(`pointman`)처럼 쓴다. 처음 등장하거나 절이 바뀌는 지점, 여러 대상을 비교하는 문장에서 병기하고, 바로 이어지는 설명에서는 반복을 줄인다. 기존 시스템을 비교할 때는 백엔드 프로젝트명인 `legacy`를 구분용으로 함께 쓰되, 구성 요소 목록에서는 백엔드라는 역할을 유지한다. 이 기준은 앞의 식별 정보 일반화 원칙보다 우선한다.

보관본은 원래 서술과 구조를 유지하되, 공개를 위해 식별 정보를 일반화했다. 폴더 이동에 맞춰 두 경험담의 이미지 상대 경로도 고쳤다. [원문 구간별 대응표](./materials/03_pending.md#sources)에서 새 자료의 위치를 찾을 수 있다.

새 사례와 논점은 해당 집필 자료에 추가하고, 현재 원고에 반영할 내용을 고른다. 이미 정리한 사건의 설명은 여러 자료에 다시 복사하기보다 링크로 연결한다.

대화와 행동은 저자가 제공한 기록을 바탕으로 쓴다. 원고의 연결을 매끄럽게 하려고 발언·사건·후속 행동을 만들어 넣지 않는다. 실제 발언인지 확인되지 않은 문장을 직접 인용하지 않으며, 빠진 사실은 확인 항목에 남긴다.

저자가 대화에서 직접 설명하거나 정정한 내용도 집필 근거이며, 최신 설명과 지시를 우선한다. 보관 문서에서 찾지 못했다는 이유만으로 AI가 추가한 내용이라고 단정하거나 기존 내용을 삭제하지 않는다. 출처를 확인하지 못한 기존 내용은 보존하고 확인 항목에 남긴다. 사실관계를 바꿀 때는 근거와 변경 내용을 함께 기록하고, 검토 결과에는 실제 대조한 자료와 확인하지 못한 범위를 명시한다.

저자의 말을 충실히 옮기는 것과 주장의 타당성을 검토하는 것은 별개다. 원인 설명과 일반화는 근거·반례·다른 가능한 설명을 검토한다. “내 생각에는”이라고 붙이는 것만으로 부족한 근거가 보완되지는 않는다. 경험이 뒷받침하는 범위로 원고를 다듬고, 남은 가설과 검토 근거는 확인 메모에 기록한다.

발행 전에는 사건의 시점·인원·업무 범위·수치의 조합, 이미지와 첨부파일, 과거 Git 이력에서도 대상을 특정할 수 있는지 별도로 확인한다. 현재 파일의 명칭을 바꿨다는 사실만으로 완전한 익명성이 보장되지는 않는다.
