# AI 코딩, 어떻게 개발해야 하는가

> 구현이 빨라진 뒤 개발자가 해야 할 일

C를 처음 공부한 것은 1995년 무렵이었다. 당시에는 “프로그래밍을 제대로 알려면 어셈블리어를 알아야 한다”는 말을 종종 들었다. 실제로 C 코드 사이에 어셈블리어가 섞여 있는 소스를 보기도 했다.

어셈블리어를 알면 분명 도움이 됐다. 하드웨어가 어떻게 동작하는지 깊이 이해할 수 있었고, 필요한 경우에는 기계를 세밀하게 제어해 더 높은 성능을 끌어낼 수도 있었다.

하지만 범용 애플리케이션을 개발하기에는 생산성이 너무 낮았다. 이식성과 유지보수에도 불리했고 컴파일러까지 발전하면서, 어셈블리어로 애플리케이션을 개발하는 방식은 점차 주류에서 밀려났다. 어셈블리어가 없어진 것은 아니다. 운영체제, 컴파일러, 디바이스 드라이버와 극단적인 성능 최적화처럼 꼭 필요한 곳에서 여전히 사용된다. 다만 대부분의 개발자가 매일 직접 다루는 언어에서는 한 단계 아래로 내려갔다.

C가 애플리케이션 개발의 주류가 된 뒤에도 컴파일러를 신뢰하지 못하거나 제대로 된 프로그램은 어셈블리어로 직접 작성해야 한다고 생각하는 개발자들이 있었다. 성능과 하드웨어 제어가 중요한 영역에서는 그럴 만한 이유도 있었지만, 그 방식을 모든 애플리케이션 개발에 적용하기에는 생산성 차이가 너무 컸다.

30여 년이 지나 AI 코딩이 빠르게 확산된 지금도 비슷한 기시감을 느낀다. AI가 작성한 코드는 믿을 수 없고, 코드를 직접 작성해야만 제대로 이해할 수 있다는 이유로 AI 코딩을 외면하는 개발자들이 있다. 이러한 우려에는 분명한 근거가 있다. AI는 틀릴 수 있고, 그럴듯하지만 잘못된 코드도 만든다.

물론 C와 AI는 같지 않다. 컴파일러는 명시적인 소스를 정해진 규칙으로 번역하지만, AI는 사람의 요구를 해석해 확률적으로 결과를 만든다. C와 어셈블리어의 관계는 생산성과 추상화 수준의 변화를 설명하는 비유일 뿐 신뢰 방식까지 같다는 뜻은 아니다. 오히려 이 차이 때문에 AI 코딩에는 더 체계적인 검증이 필요하다.

AI의 문제를 경계하는 것과 AI 코딩 자체를 거부하는 것은 다른 문제다. 일반적인 프로덕션 개발에서 모든 코드를 처음부터 끝까지 사람이 직접 작성하는 방식을 기본값으로 고집하는 것은 점점 비현실적인 선택이 되어가고 있다. 직접 구현은 여전히 이해와 디버깅, 판단력을 기르는 중요한 훈련이지만 생산의 중심은 달라지고 있다.

AI가 크게 낮춘 것은 구현 비용이다. 판단을 돕기도 하지만 최종 판단과 책임의 비용까지 없애지는 않는다. 이 문서는 다음 세 가지 질문을 차례로 다룬다.

1. AI로 어떻게 개발하며 기존 방식과 무엇이 다른가?
2. 그렇게 개발하면 어떤 문제가 발생하는가?
3. 그 문제를 어떻게 통제하고 해결할 것인가?

## 챕터 1. AI로 어떻게 개발하는가

### 1.1 생산성이 높아지면 개발 방법도 달라진다

프로그래밍의 생산성이 높아질 때마다 개발자가 다뤄야 하는 추상화 수준과 소프트웨어를 통제하는 방법도 달라졌다.

어셈블리어로 개발하던 시절에도 프로그램의 구조는 중요했다. 하지만 생산성이 낮았기 때문에 오늘날처럼 거대한 애플리케이션을 빠르게 만들고 변경하기는 어려웠다. 고급 언어와 개발 도구가 발전하면서 개발자가 작성할 수 있는 코드의 양과 프로그램의 규모는 크게 늘어났다. 반면 사람이 한 번에 이해할 수 있는 복잡성은 그만큼 늘어나지 않았다.

커진 프로그램을 통제하기 위해 구조적 프로그래밍, 모듈화, 객체 지향 프로그래밍, 디자인 패턴과 소프트웨어 아키텍처가 발전했다. 이 방법들은 단순히 코드를 잘 작성하기 위한 기술이 아니다. 높아진 생산성으로 만들어진 더 큰 소프트웨어를 인간이 계속 이해하고 관리하기 위한 방법이다.

AI 코딩은 코드 생산성을 다시 한 단계 높였다. 작업에 따라 한 명의 개발자가 과거에는 여러 사람이 상당한 시간을 들여야 했던 양의 코드를 짧은 시간에 만들고 변경할 수 있다. 그러나 코드를 읽고 전체 구조를 이해하며 변경의 영향을 판단하는 인간의 능력까지 같은 속도로 증가한 것은 아니다.

기존의 소프트웨어 공학이 사람이 작성한 대규모 코드를 관리하기 위한 방법이었다면, AI 시대의 소프트웨어 공학은 사람이 모두 읽을 수 없을 만큼 빠르게 생성되는 변경을 통제하는 방법이어야 한다. 기존 방법론이 폐기되는 것이 아니라 더 높은 생산성을 감당할 수 있도록 우선순위와 적용 방식이 달라지는 것이다.

대규모 엔터프라이즈 프로젝트는 이미 비슷한 문제를 겪었다. 코드와 참여자가 늘어나면 모든 규칙을 사람이 코드 리뷰로 매번 확인할 수 없다. 그래서 코드 리뷰 같은 직접 검토를 `lint`, 타입 검사, 정적 분석, 자동화된 테스트와 CI 품질 게이트로 보완해왔다. 기계적으로 판정할 수 있는 반복적인 기준은 도구에 맡기고, 사람은 요구사항과 설계, 시스템 경계와 예외처럼 맥락이 필요한 판단에 집중하는 방식이다.

AI 코딩은 다른 경로로 같은 한계에 도달한다. 엔터프라이즈 프로젝트는 오랜 시간 여러 사람이 만든 코드의 총량이 너무 많아서 한 사람이 모두 읽을 수 없다. AI 코딩에서는 한 사람이나 작은 팀도 사람이 처리하기 어려운 속도로 변경을 생성한다. 이 때문에 지속적으로 운영할 소프트웨어라면 작은 프로젝트에서도 과거 대규모 프로젝트에 적용하던 통제 체계가 훨씬 이른 시점부터 필요해진다.

문제는 이런 체계를 설계하고 운영하려면 엔터프라이즈 프로젝트에서 축적해온 경험이 필요하다는 점이다. 도구를 설치하는 것은 어렵지 않지만 어떤 규칙을 자동화하고, 무엇을 사람이 판단하며, 어느 검사를 배포 조건으로 삼을지는 도구가 대신 결정해주지 않는다. AI 코딩은 코드 생성의 진입 장벽을 낮추는 동시에 대규모 소프트웨어 공학의 문제를 더 많은 개발자 앞으로 끌어왔다.

> 엔터프라이즈 개발은 코드의 총량 때문에, AI 코딩은 코드의 생성 속도 때문에 한 사람이 모든 코드를 읽을 수 없게 된다.

### 1.2 개발 프로세스는 사라지지 않는다

AI로 인해 소프트웨어 개발이 완전히 다른 일이 된 것처럼 보이지만, 단순하게 생각하면 AI는 사람이 하던 작업의 일부를 대신하는 도구다. 개발 프로세스의 테두리는 여전히 다음과 같다.

```text
문제와 요구사항 분석
→ 기존 시스템 조사
→ 설계와 계획
→ 구현
→ 검증
→ 배포와 운영
```

AI는 이 모든 단계에서 일부 작업을 수행할 수 있다.

| 개발 단계 | AI가 수행할 수 있는 작업 | 사람이 책임질 일 |
|---|---|---|
| 문제와 요구사항 | 자료·사용자 의견·로그 조사, 요구사항과 완료 조건 초안 | 해결할 문제와 우선순위 결정 |
| 설계 | 기존 구조 조사, 대안과 변경 영향 분석, 설계안 작성 | 프로젝트에 맞는 선택과 감수할 위험 결정 |
| 계획 | 작업 분해, 의존성 분석, 구현 순서와 병렬 작업 구성 | 작업 범위와 변경 전략 승인 |
| 구현 | 코드·테스트·설정·마이그레이션·문서 작성 | 중요한 맥락과 제약 전달 |
| 검증 | 테스트 실행, 정적 분석, 동작 확인과 검토 | 검증 기준과 증거의 충분성 판단 |
| 배포와 운영 | 빌드·배포 준비, 상태 관찰, 장애 조사와 수정안 작성 | 출시 승인, 사용자 영향과 운영 위험 판단 |

AI가 모든 단계에 참여할 수 있다는 것과 전체 과정을 스스로 결정하고 책임질 수 있다는 것은 다른 이야기다. AI는 각 단계의 작업을 대신할 수 있지만 개발 프로세스와 결정권, 책임을 없애지는 않는다.

요구사항 분석, 도메인 모델링, 객체 지향 설계, 패턴, 아키텍처, 테스트와 지속적 통합도 여전히 유효하다. 오히려 AI가 더 많은 코드를 더 빠르게 만들기 때문에 결과를 구조화하고 통제하는 소프트웨어 공학의 중요성은 더 커진다.

> AI가 바꾼 것은 개발 프로세스가 아니라, 그 안에서 사람이 직접 수행하는 작업의 비중이다.

### 1.3 사람은 AI의 작업을 지휘하고 책임진다

달라진 것은 역할 배분이다. AI는 모든 단계의 일부를 도울 수 있지만 특히 많은 시간이 들던 구현을 크게 대신한다. 그동안 구현을 중심으로 일해 온 개발자는 요구사항 분석, 설계, 작업 분해, 검증과 통합에 더 많은 시간을 사용하게 된다.

AI와 함께 일하는 과정은 팀장이 팀원에게 일을 맡기는 과정과 닮았다. 팀장은 요구사항을 해석해 작업을 나누고, 필요한 맥락과 제약을 설명하며, 완료 조건을 정한다. 진행 중에는 방향이 맞는지 확인하고, 결과가 나오면 검증과 피드백을 거쳐 다른 작업과 통합한다.

AI에게 일을 맡길 때도 마찬가지다. 사람은 AI가 작업을 시작하기 전에 목표와 제약, 완료 조건을 승인해야 한다. 작업 중에는 중요한 방향과 위임 범위를 관리하고, 작업이 끝난 뒤에는 테스트와 실행 결과가 충분한지 판단하며 통합과 배포 여부를 결정해야 한다.

사람이 모든 산출물을 직접 작성할 필요는 없다. 요구사항, 설계안, 인터페이스와 테스트도 AI에게 초안을 맡길 수 있다. 다만 무엇을 채택할지 결정하고 최종 결과에 책임지는 판단까지 넘길 수는 없다.

AI는 작업과 검증을 수행할 수 있다. 사람은 목표와 위임 경계를 정하고, 증거의 충분성을 판단하며, 결과에 책임진다.

### 1.4 AI 코딩의 실제 작업 흐름

AI 코딩에서도 새로운 개발 프로세스가 생기는 것은 아니다. 기존 단계 안에서 사람과 AI가 다음과 같이 작업을 주고받는다.

```text
사람이 목표·제약·완료 조건을 정의한다
→ AI에게 프로젝트 맥락과 개발 지침을 제공한다
→ AI가 기존 코드와 문서를 조사한다
→ AI가 작업 계획을 만들고 사람이 방향을 확인한다
→ AI가 요구사항과 기존 동작을 검증 기준과 테스트로 구체화한다
→ 사람이 검증 기준을 확인한 뒤 AI가 실제 변경을 수행한다
→ 자동화된 테스트와 실행 증거로 결과와 회귀 여부를 확인한다
→ 사람이 통합과 배포 여부를 결정한다
→ 실제 동작을 관찰하고 다음 작업에 반영한다
```

기존에는 사람이 프로젝트의 맥락을 머릿속에 유지하면서 요구사항을 코드로 직접 번역했다. AI 코딩에서는 사람이 목표와 기준을 관리하고 AI가 조사와 구현, 검증에 포함된 작업을 수행한다. 구현은 줄어들지만 분석과 설계, 검증과 의사결정은 더 선명하게 드러난다.

### 1.5 추상적인 생각을 빠르게 구체화한다

추상적인 생각을 글과 그림, 설계와 코드로 구체화하는 일은 원래 어렵다. 머릿속 생각을 다른 사람이 이해할 수 있도록 설명하는 것부터 쉽지 않다.

AI는 대략적인 설명만으로도 화면, 문서, 설계안, API, DTO, 데이터 스키마와 테스트의 초안을 만들 수 있다. 큰 생각에서 세부 구현으로 내려가는 탑다운 개발이 훨씬 쉬워진 것이다. 다만 AI가 잘하는 것은 첫 번째 구체화다. 초안이 실제 의도를 반영하고 시스템 전체와 어울리는지 판단하는 일은 여전히 사람의 몫이다.

UI 개발 과정에서 이 변화가 특히 잘 드러난다. 기존에는 기획자가 기능 명세를 작성하거나 화면을 러프하게 스케치하면 디자이너가 Figma 같은 도구로 구체적인 화면을 만들었다. 프론트엔드 개발자는 그 디자인을 보고 실제로 동작하는 화면을 구현했다.

```text
기존: 기획 명세·러프 스케치 → UI 디자인 → 프론트엔드 구현 → 실제 동작 확인
AI:   기획 의도·제약 입력      → UI 후보와 동작하는 목업 생성 → 실제 동작 확인
```

기존 방식에서는 기획 의도가 디자인으로, 디자인이 코드로 번역될 때마다 시간과 의사소통 비용이 들었다. 실제로 동작하는 화면을 확인한 뒤에야 빠진 요구사항이나 잘못된 사용자 흐름을 발견하기도 했다.

이제 기획자는 프롬프트를 통해 원하는 화면을 여러 번 조정하고, 실제로 동작하는 목업 애플리케이션까지 만들 수 있다. 디자인도 기획 의도를 시각적으로 구현하는 일이라고 본다면, AI가 디자인 단계의 구현과 개발 단계의 첫 구현을 함께 흡수한 것이다. 기획의 산출물이 기능 명세와 스케치에서 실행 가능한 프로토타입으로 확장되면서 기획과 피드백의 속도도 크게 높아진다.

개발에서 설계를 시작할 때도 같은 일이 일어난다. 만들려는 서비스를 간단히 설명하면 AI는 폭넓은 지식과 기존 사례를 바탕으로 다음과 같은 첫 설계 자료를 만들어준다.

- 사용자와 외부 시스템, 주요 유스케이스
- 시스템의 범위와 구성 요소 사이의 경계
- 주요 기능의 시퀀스와 데이터 흐름
- 상태 전이와 예외 상황
- 도메인 개념과 데이터 모델의 초안

머릿속 생각만으로는 놓치기 쉬운 행위자와 흐름, 상태와 경계를 여러 다이어그램으로 펼쳐주기 때문에 전체 구조를 알아보고 다른 사람과 논의하기 쉬워진다. 아무것도 없는 상태에서 설계를 시작하는 대신 구체적인 초안을 비판하고 수정하면서 생각을 발전시킬 수 있다.

물론 AI가 만든 다이어그램이 대부분 유용한 출발점이 된다는 뜻이지 항상 올바르다는 뜻은 아니다. 설명하지 않은 부분을 일반적인 사례로 채우면서 존재하지 않는 요구사항을 만들거나 엉뚱한 경계와 흐름을 제안할 가능성은 언제나 있다. 따라서 AI가 만든 설계 자료는 완성된 설계가 아니라 빠진 질문과 가정을 찾아내기 위한 베이스로 사용해야 한다.

AI가 추상적인 생각을 구체화할 때 주는 가장 큰 도움은 정답을 대신 내려주는 것이 아니다. 사람이 검토하고 고칠 수 있는 첫 형태를 빠르게 만들어주는 것이다.

이것이 기획자, 디자이너와 개발자가 필요 없어졌다는 뜻은 아니다. 기획자는 해결할 문제와 요구사항을 판단하고, 디자이너는 사용자 경험과 시각 체계, 접근성을 책임지며, 개발자는 설계 초안과 목업을 운영 가능한 구조와 데이터, 성능과 품질을 갖춘 제품으로 만들어야 한다. 각 직군의 역할도 첫 산출물을 직접 만드는 일에서 AI가 만든 결과를 판단하고 제품 수준으로 끌어올리는 일로 이동한다.

### 1.6 사람이 쉬어도 작업이 진행되도록 구조화한다

비동기 실행을 지원하는 에이전트 환경에서는 작업을 미리 나누고 맡겨두면 사람이 다른 일을 하거나 쉬는 동안에도 조사, 구현, 테스트와 리팩터링을 진행할 수 있다. 중요한 것은 쉬지 않는 사람이 되는 것이 아니라 사람이 자리를 비워도 안전하게 진행되도록 작업 범위와 입력, 완료 조건과 산출물을 구조화하는 것이다.

한 명의 개발자는 자신이 모든 작업을 직접 수행하는 사람에서 여러 작업이 독립적으로 진행되는 생산 시스템을 설계하는 사람으로 이동한다.

### 1.7 AI는 개발자의 기존 역량을 증폭한다

많은 개발자가 AI 코딩을 어려워하는 이유도 여기에서 찾을 수 있다. AI에게 코드를 작성해 달라고 요청하는 것 자체는 어렵지 않다. 어려운 것은 요구사항을 분석하고, 작업 가능한 단위로 나누고, 시스템의 경계와 인터페이스를 설계하며, 무엇을 통과해야 완료인지 정의하는 일이다.

현실에서는 TDD는 고사하고 구현 전에 체계적으로 분석하고 설계하는 데 익숙한 개발자가 많지 않다. 기존에는 모호한 요구사항을 붙잡고 직접 코딩하면서 조금씩 의도를 구체화할 수도 있었다. AI는 모호한 상태에서도 생각하지 않은 부분을 그럴듯한 구현으로 빠르게 채운다. 분석과 설계가 부족하면 잘못된 방향으로 더 빨리 멀어질 수 있다.

반대로 분석과 설계에 능숙한 개발자에게 AI는 강력한 생산성 도구다. 요구사항을 구조화하고 책임과 경계를 나누며 인터페이스와 검증 기준을 정할 수 있다면, 그동안 병목이었던 구현을 AI에게 맡길 수 있다. 머릿속 설계를 실제 코드로 옮기고 반복해서 수정하는 시간이 줄면서 전체 개발 속도가 몇 배로 체감될 만큼 높아지기도 한다.

큰 소프트웨어를 개발하려면 개별 기능을 만드는 능력보다 전체 구조와 경계를 정하고, 여러 기능의 일관성을 유지하며, 변경의 영향과 운영 위험을 관리하는 능력이 필요하다. AI는 코드의 양을 늘려줄 수 있지만 그 코드를 하나의 안정된 시스템으로 만드는 역량까지 자동으로 높여주지는 않는다.

AI는 일정 수준까지 구현 역량의 하한을 높인다. 동시에 큰 소프트웨어에서는 개발자가 이미 가진 설계와 판단 능력의 차이까지 증폭한다.

### 1.8 AI는 아키텍처 선택의 기준도 바꾼다

AI는 개발 과정뿐 아니라 개발 방법과 아키텍처를 선택하는 기준에도 영향을 준다. 기존 방법 중에는 사람이 한 번에 이해하고 안전하게 변경할 수 있는 코드의 크기가 제한적이라는 전제에서 발전한 것들이 많다.

마이크로서비스 아키텍처(MSA)도 코드와 책임을 작은 서비스로 나누고 의존 관계를 명확히 함으로써 각 팀이 이해해야 할 범위를 줄여준다. 거대한 모놀리스를 여러 팀이 함께 변경할 때 생기는 인지 부담과 배포 조율 비용을 줄일 수 있다. 대신 네트워크 통신, 분산 트랜잭션과 데이터 정합성, 장애 전파, 배포와 관찰 같은 새로운 복잡성을 감수해야 한다.

AI는 큰 코드베이스를 검색하고 호출 관계와 변경 영향을 추적하며 전체 구조의 초안을 파악하는 시간을 크게 줄여준다. 코드가 다소 많고 복잡하더라도 사람이 혼자 처음부터 읽을 때보다 훨씬 빠르게 필요한 맥락을 찾아낼 수 있다. 항상 정확하게 이해한다는 뜻은 아니지만, 코드의 크기와 탐색 비용 때문에 시스템을 잘게 나눠야 했던 압력은 낮아질 수 있다.

따라서 내부 경계가 잘 정리된 모듈러 모놀리스라면 과거보다 더 큰 규모까지 유지하고, 모놀리스에서 MSA로 전환하는 시기를 상당히 늦출 수 있다. 코드베이스가 커졌다는 이유만으로 분산 시스템의 운영 복잡성을 일찍 도입할 필요는 줄어드는 것이다.

그렇다고 AI가 MSA를 불필요하게 만드는 것은 아니다. 서비스별 독립 배포와 확장, 장애 격리, 보안 경계, 서로 다른 팀의 독립적인 소유권처럼 실행 환경과 조직에서 생기는 요구는 AI가 코드를 빨리 읽는다고 사라지지 않는다. 전환 시점은 코드 줄 수보다 현재 병목이 코드 이해에 있는지, 배포와 확장, 장애와 조직 경계에 있는지를 보고 결정해야 한다.

AI가 기존 코드를 빠르게 이해한다고 분산 시스템의 복잡성까지 없어지는 것은 아니다. 다만 인간의 인지 한계가 주요 전제였던 개발 방법은 그대로 답습하지 말고 다시 검토할 필요가 있다.

> 기존 방법론을 버리자는 것이 아니다. 그 방법이 해결하려던 제약이 AI 시대에도 같은 형태로 남아 있는지 다시 묻자는 것이다.

## 챕터 2. AI 개발에서는 어떤 문제가 발생하는가

### 2.1 코드 생성 속도와 소프트웨어 완성 속도는 다르다

AI가 분명 크게 유용해 보이는데도 프로젝트 전체의 생산성은 기대만큼 높아지지 않을 수 있다. AI가 구현 시간을 크게 줄여도 분석과 설계가 늦어지거나 생성된 결과를 검증하고 통합하는 데 같은 시간이 든다면 전체 개발 기간은 그만큼 줄어들지 않는다.

큰 규모의 소프트웨어를 완성하는 일은 생각보다 어렵다. 주요 화면과 API가 만들어지고 정상 흐름이 대략 동작하는 지점까지는 비교적 쉽게 도달한다. 여기서 말하는 중반은 전체 작업량의 정확한 절반이 아니라, 겉으로 보이는 주요 기능이 갖춰져서 거의 다 만든 것처럼 느껴지는 시점이다. 이 경험만 반복하면 시간만 더 주어지면 프로젝트를 얼마든지 완성할 수 있다고 생각하기 쉽다.

그러나 실제로 프로젝트를 끝까지 밀어붙여 출시하고 운영해보면 주요 기능의 구현은 완성의 일부에 불과하다는 것을 알게 된다. 예외와 실패 처리, 권한과 보안, 데이터 정합성과 마이그레이션, 기존 기능과의 통합과 회귀 검증, 성능, 배포와 복구, 관찰과 장애 대응까지 갖춰야 비로소 운영 가능한 소프트웨어가 된다. 눈에 잘 띄지 않는 이 작업들은 많은 노력뿐 아니라 여러 프로젝트를 끝까지 경험하며 얻은 판단력을 요구한다.

AI 코딩은 프로젝트의 앞부분을 더욱 빠르게 만든다. 화면과 API, 데이터 구조와 정상 흐름을 순식간에 만들어 겉보기에는 완성에 가까운 상태까지 데려간다. 하지만 무엇이 아직 빠져 있는지 찾아내고, 어느 수준을 통과해야 출시할 수 있는지 정하며, 그 결과를 검증하는 지식과 경험까지 자동으로 만들어주지는 않는다. AI도 남은 작업을 도울 수 있지만 사람이 완성의 조건을 모르거나 판정할 수 없다면 생산성 향상은 그 지점에서 멈춘다.

모호한 요구사항으로 잘못된 코드를 빠르게 만들면 수정과 재작업도 늘어난다. 구현은 개발 프로세스의 한 단계일 뿐이다. 한 단계의 속도만 높이고 나머지 단계의 작업 방식과 역량을 그대로 두면 병목은 다른 곳으로 이동한다.

AI의 생성 속도는 사람이 결과물을 이해하고 검증하고 통합하는 속도를 넘어설 수 있다. 여러 작업을 동시에 시작하더라도 검증과 통합 능력을 초과하면 대기 중인 변경, 충돌과 재작업만 쌓인다.

안드로이드 키오스크를 AI와 함께 개발할 때 이 병목을 직접 겪었다. AI가 작업하는 환경에는 에뮬레이터만 있었고 실제 단말기는 없었다. 에뮬레이터에서 구현과 기본 확인은 진행할 수 있었지만, 실제 키오스크에서 제대로 동작하는지는 AI가 검증할 수 없었다.

변경이 나올 때마다 내가 중간에 빌드하고 결과물을 실제 단말기로 옮겨 설치한 뒤 실행해 확인해야 했다. 문제가 발견되면 그 결과를 다시 AI에게 전달해야 다음 수정이 진행됐다. AI가 코드를 만드는 속도와 관계없이 이 검증 단계는 사람과 실제 단말기를 거쳐야 했고, 결국 이틀 동안 작업하고도 끝내지 못했다. 구현 속도가 빨라도 검증 환경과 사람의 검증 속도가 전체 작업의 상한이 된다는 것을 보여준 사례였다.

이 경험을 돌아보면 AI는 문제의 본질을 한 번에 꿰뚫는 통찰이나 추론만으로 정답을 찾아내기보다, 학습한 수많은 사례에서 가능성이 높은 답을 제시하고 실행 결과를 바탕으로 여러 번 수정하면서 정답에 가까워지는 경우가 많다. 이 방식이 빠르게 작동하려면 AI가 스스로 시도하고 결과를 관찰할 수 있어야 한다.

따라서 AI가 사용할 수 있는 테스트 환경은 가능한 한 완전해야 한다. 실제 하드웨어, 외부 시스템, 권한과 운영 환경 같은 조건이 사람에게만 열려 있으면 AI의 반복은 매번 사람 앞에서 멈춘다. AI에게 구현을 맡기고 검증 환경을 제공하지 않으면 코드 생성 속도가 아무리 빨라도 전체 작업 속도는 빨라지지 않는다.

```text
전체 개발 속도는 생성·검증·통합 가운데 가장 느린 단계에 묶인다.
```

> AI는 프로젝트의 중반까지 가는 시간을 크게 줄여주지만, 중반을 완성으로 바꾸는 지식과 경험까지 대신하지는 않는다.

### 2.2 변경량이 늘면 회귀 위험도 커진다

AI는 요청한 기능을 정상적으로 만들면서도 공통 코드, 데이터 구조, 설정이나 외부 계약을 함께 변경할 수 있다. 그 결과 이전에 잘 동작하던 기능이 오동작하기도 한다.

회귀는 AI만의 문제가 아니다. 사람도 코드를 변경하면서 회귀를 만든다. 그러나 AI 코딩에서는 한 번에 만들어지는 변경의 양과 속도가 크게 증가한다. 개별 변경의 오류 가능성이 낮아 보여도 변경량이 많아지면 프로젝트 전체의 회귀 위험은 커진다.

AI는 명시된 요구사항에는 대응하지만 코드 곳곳에 암묵적으로 존재하는 기존 동작까지 항상 파악하지는 못한다. 따라서 다음 두 질문을 함께 확인해야 한다.

1. 새롭게 요청한 기능이 올바르게 동작하는가?
2. 기존에 잘 동작하던 기능도 여전히 올바르게 동작하는가?

검증 체계 자체도 틀릴 수 있다. 같은 요구사항을 잘못 이해한 AI가 잘못된 테스트와 그 테스트를 통과하는 잘못된 구현을 함께 만들 수 있다. 테스트가 통과했다는 사실만으로 요구사항을 올바르게 이해했다는 것까지 보장되지는 않는다.

새로운 요구사항이 무엇을 바꿀 것인지 말한다면 회귀 테스트는 무엇을 바꾸면 안 되는지 말한다. 회귀 테스트는 보존해야 할 기존 동작을 기록한 실행 가능한 프로젝트의 기억이다.

### 2.3 높은 성공률이 검증을 포기하게 만든다

AI가 코딩을 대신하면서 오히려 개발자가 검증을 소홀히 하는 경향도 강해진다. AI의 결과가 대부분 그럴듯하고 실제로도 자주 맞기 때문이다. 정확한 통계는 아니지만 열 번 중 아홉 번 문제가 없다고 느끼기 시작하면, 나머지 한 번을 찾기 위해 매번 검증하는 일이 불필요하고 귀찮게 느껴진다.

그러나 드문 오류는 평범한 사용 흐름이 아니라 경계값, 권한, 데이터 정합성, 장애 상황이나 운영 환경에서 드러날 수 있다. 변경의 수가 늘어날수록 낮아 보이는 오류 가능성도 프로젝트 전체에서는 무시하기 어려운 위험이 된다. AI의 높은 평균 성공률은 검증을 생략할 근거가 아니라 검증을 생략하고 싶게 만드는 유혹에 가깝다.

검증을 계속 생략하면 개발자의 역할은 다음과 같이 축소된다.

```text
누군가에게 들은 요구사항을 AI에게 전달한다
→ AI가 만든 답이나 코드를 확인하지 않고 다시 사람에게 전달한다
```

이 과정에서 개발자는 요구사항의 모호함을 찾아내지 않고, AI가 내린 선택의 이유도 이해하지 않으며, 결과가 실제 문제를 해결하는지도 확인하지 않는다. 대화 사이에 사람이 존재하지만 판단과 책임은 존재하지 않는다.

> 판단과 검증이 없다면 개발자는 사람과 AI 사이의 단순 중계자일 뿐이다.

### 2.4 AI의 설계는 정답이 아니라 후보안이다

이 문제는 구현에만 해당하지 않는다. AI에게 설계를 맡기면 익숙한 패턴과 전문 용어를 사용해 그럴듯한 근거를 설명하고 API까지 빠르게 설계한다. 문서의 형식도 완성되어 있고 각 선택의 설명도 자연스럽기 때문에 그대로 구현해도 될 것처럼 보인다.

그러나 AI가 제시하는 설계는 대체로 이미 알려진 모범 사례를 조합한 후보안이다. 프로젝트의 맥락과 우선순위, 트레이드오프를 충분히 따지지 않은 채 여러 모범 사례 중 하나를 제시하기도 한다. 선택한 뒤에는 논리적인 설명까지 붙여주지만, 그 설명은 설계와 함께 생성된 주장이지 설계가 옳다는 독립적인 증거가 아니다.

내 경험으로는 AI가 만든 설계를 수정 없이 그대로 받아들인 경우가 매우 드물었다. 실제 설계에는 문서에 드러나지 않은 도메인 규칙, 기존 시스템의 역사와 제약, 충돌하는 요구사항의 우선순위, 운영 비용과 앞으로의 변경 방향에 대한 판단이 필요하기 때문이다.

조금 거칠게 말하면 AI는 지식이 많은 것이지, 그 자체로 설계 책임자가 될 만큼 똑똑한 것은 아니다. AI는 질문과 대안, 판단 근거의 후보를 제시할 수 있다. 하지만 폭넓은 지식과 유창한 설명을 현재 프로젝트에 맞는 설계 판단력으로 착각해서는 안 된다. 많이 아는 것과 무엇을 선택하고 포기할지 결정하며 그 결과에 책임지는 것은 다른 능력이다.

AI의 설계는 참고 자료이자 검토할 후보안으로 다뤄야 한다. 프로젝트 맥락을 아는 설계 책임자가 전제와 도메인 모델, 시스템 경계, 대안, 실패 조건과 변경 비용을 면밀히 검토한 뒤에야 실제 설계로 채택할 수 있다.

> AI가 설계안을 만들었다는 것은 설계가 끝났다는 뜻이 아니라, 검토할 후보가 하나 생겼다는 뜻이다.

### 2.5 사례: 좋은 원칙이 나쁜 아키텍처가 된 과정

설계를 반드시 검토해야 하는 단적인 사례가 [DB_SCHEMA_COMPLEXITY.md](./DB_SCHEMA_COMPLEXITY.md)에 정리되어 있다. 내가 이 프로젝트에서 Claude 4.7 Opus에게 설계를 맡겼을 때, AI는 온라인 중심의 기존 데이터베이스를 여러 단말과 상품군으로 확장하기 위해 다음 네 가지 원칙을 제시했다.

1. **추가형만** — 컬럼과 테이블 추가가 기본이며 기존 컬럼 삭제는 마지막 단계에서 수행한다.
2. **이중 기록과 백필** — 기존 모델과 신규 모델에 함께 기록하고 과거 데이터를 옮긴 뒤 전환한다.
3. **한 번에 한 축만** — 권종, 채널, 디바이스, 체크인, 재고와 결제를 순서대로 변경한다.
4. **쓰기는 단일 RPC로** — 발권과 체크인 쓰기 로직을 PostgreSQL 함수 한 곳에 모은다.

운영 중인 데이터베이스를 안전하게 변경한다는 관점에서는 모두 합리적인 원칙이었다. 특히 추가형 변경은 파괴적인 마이그레이션을 피하고 단계적으로 전환할 수 있다는 장점이 있다.

문제는 첫 번째 원칙인 ‘추가형만’이 임시 마이그레이션 전략을 넘어 사실상 영구적인 설계 제약으로 작동했다는 것이다. 기존 테이블을 변경하거나 공통 모델을 다시 설계하기보다 새로운 기능에 필요한 컬럼과 테이블을 옆에 계속 추가했다. 판매, 결제와 검표처럼 같은 업무 개념을 표현하는 유사한 모델이 여러 실행 경로에 생겼다.

추가형 원칙 하나만으로 모든 복잡성이 생긴 것은 아니다. POS 백엔드 방향이 바뀐 뒤 이전 모델이 남았고, 여러 기능이 공유 DB에 각자의 도메인 모델을 만들었으며, 변경 소유권과 마이그레이션 이력이 분산됐다. 공통 거래 모델을 먼저 확정하지 않은 채 여러 원장을 조회 시점에 통합하면서 구조의 분리도 가려졌다. 마지막에 기존 구조를 정리한다는 계획은 담당자, 실행 시점과 검증 조건이 없어 실제 작업으로 이어지지 않았다.

2026년 7월 12일 기준 `public` 스키마에는 기본 테이블 145개와 컬럼 1,786개가 있었고 통계상 0행으로 추정되는 테이블은 75개였다. 테이블 수와 0행 추정치만으로 나쁜 설계라고 판단할 수는 없다. 문제는 데이터 규모가 아직 크지 않은 서비스에서 같은 업무 개념을 여러 모델이 동시에 표현하고, 어느 모델이 정본이며 무엇을 폐기해야 하는지가 불명확해졌다는 점이다.

데이터 마이그레이션은 진행됐지만 아키텍처 마이그레이션은 끝나지 않았다. AI가 일반적으로 안전한 원칙을 제안할 수는 있지만, 이 사례에서는 사람이 프로젝트에 맞는 적용 범위와 종료 조건을 검토하고 끝까지 관리하지 못했다.

> 좋은 원칙도 적용 범위와 종료 조건 없이 반복하면 나쁜 아키텍처가 될 수 있다.

### 2.6 AI는 문제를 해결하지 않고 숨기기도 한다

AI는 요청받은 문제의 근본 원인을 해결하기보다 현재 발생한 오류를 빠르게 사라지게 만드는 방법을 선택하기도 한다. 당장의 컴파일과 테스트 통과에는 유리하지만 실패를 숨기거나 기존 계약을 약화시키는 편법이 될 수 있다.

- 예외를 잡은 뒤 `null`, 빈 배열이나 빈 문자열 반환
- 반드시 있어야 하는 값에 `??`로 임의의 기본값 사용
- 타입 오류를 `any`나 강제 캐스팅으로 우회
- 실패하는 테스트를 새 구현에 맞게 수정하거나 삭제
- 기존 인터페이스와 검증 조건을 느슨하게 변경
- 공통 원인을 해결하지 않고 호출부마다 예외 처리 추가
- 원인을 확인하지 않은 채 재시도나 fallback 추가

이러한 코드는 정상적으로 빌드되고 테스트를 통과할 수도 있다. 하지만 오류 신호를 없애고 잘못된 상태를 정상 상태처럼 보이게 하며 운영 환경에서 문제를 발견하기 어렵게 만든다. 해결되지 않은 문제는 다른 형태로 더 깊은 곳에 남는다.

문제는 특정 문법 자체가 아니다. `value ?? defaultValue`는 값이 없는 것이 정상적인 도메인 상황이라면 올바른 코드다. 반드시 존재해야 하는 값이 사라졌는데 임의의 기본값으로 대체하는 것이 문제다. fallback도 마찬가지다. 실패를 감추기 위한 편의인지, 명시적으로 설계된 도메인·운영 정책인지 구분해야 한다.

### 2.7 아무도 읽지 않는 문서가 쌓인다

AI는 코드뿐 아니라 설명서, 작업 보고서와 설계 문서도 순식간에 만들어낸다. 문서 작성 비용이 낮아진 것은 장점이지만 필요성을 판단하지 않고 생성하기 시작하면 프로젝트는 아무도 읽지 않는 문서 파일로 넘쳐난다.

비슷한 내용이 여러 파일에 반복되고 구현이 바뀐 뒤에도 오래된 설명이 남는다. 결국 어떤 문서가 현재 기준인지 알 수 없고 필요한 정보를 찾는 비용만 커진다. 코드에서 확인할 수 있는 구현을 사람이 다시 문서로 옮겨 적으면 그 문서는 코드와 함께 자동으로 바뀌지 않는 낡은 복사본이 되기 쉽다.

특히 AI도 프로젝트 문서를 작업의 맥락으로 사용한다. 불필요하거나 충돌하는 문서는 사람만 혼란스럽게 하는 것이 아니라 AI에도 잘못된 지침을 제공한다. 생성 비용이 낮아질수록 문서의 양보다 신뢰도와 밀도가 중요해진다.

### 2.8 주니어는 팀원이 되기 전에 AI의 팀장이 되어야 한다

AI에게 일을 맡기려면 요구사항을 해석하고 작업을 나누며, 맥락과 제약을 설명하고 결과를 검증할 수 있어야 한다. 이런 능력은 보통 여러 구현과 실패, 운영과 협업을 경험한 뒤에 생긴다. AI 도구의 사용법은 쉽게 배울 수 있어도 AI를 제대로 지휘하는 방법은 쉽게 배우기 어렵다.

과거에는 프로젝트의 규모와 책임이 커지는 동안 코드 리뷰, 테스트 자동화, 품질 게이트와 운영을 차례로 경험할 수 있었다. 이제는 작은 프로젝트도 AI의 생성 속도를 감당하기 위해 이런 통제 체계를 일찍 갖춰야 한다. 주니어에게는 팀원으로 경험을 쌓기도 전에 엔터프라이즈 프로젝트에서나 접하던 판단과 책임이 한꺼번에 요구되는 셈이다.

잘 정의된 구현 작업에서는 AI가 경험이 적은 개발자보다 빠르고 폭넓은 결과를 만들기도 한다. 그런데 주니어에게는 자신보다 구현을 잘하는 AI를 지시하고 검증하며 결과에 책임지라는 요구가 주어진다.

기존에는 주니어가 작은 기능을 직접 구현하고 실패하고 코드 리뷰를 받으면서 성장했다. 그 일을 AI가 먼저 수행하면 시행착오를 겪고 판단력을 기를 기회가 줄어든다. AI를 검증하려면 경험이 필요한데 그 경험을 쌓기 위해 하던 일을 AI가 가져가는 역설이 생긴다.

> 주니어는 팀원으로 경험을 충분히 쌓기도 전에 AI의 팀장이 되라는 요구를 받는다.

## 챕터 3. AI의 결과를 어떻게 통제할 것인가

검증은 모든 결함이 없음을 증명하는 일이 아니다. 요구사항과 알려진 위험을 반복 가능한 조건으로 만들고, 결과가 그 조건을 만족한다는 증거가 충분한지 판단하는 일이다. AI 코딩의 높은 생산성을 실제 소프트웨어의 생산성으로 바꾸려면 위임과 검증의 체계를 먼저 만들어야 한다.

### 3.1 매니지드 코딩: 위임의 범위를 관리한다

AI에게 절대로 맡기면 안 되는 특정 산출물이 정해져 있는 것은 아니다. 코드뿐 아니라 테스트, 인터페이스와 설계안도 AI에게 초안을 맡길 수 있다. 중요한 것은 무엇을 직접 작성할지가 아니라 어디까지 위임하고 어디서 사람이 개입할지를 정하는 일이다.

위임 범위를 정할 때는 다음을 판단해야 한다.

- 목표와 완료 조건이 충분히 명확한가?
- 결과를 테스트나 실행 증거로 검증할 수 있는가?
- 실패했을 때 안전하게 되돌릴 수 있는가?
- 변경의 영향 범위와 실패 비용은 어느 정도인가?
- AI가 판단하는 데 필요한 프로젝트 맥락이 충분한가?
- 어느 시점에 사람의 확인과 승인이 필요한가?

기능 정의만 전달하고 성공 기준과 개입 시점을 정하지 않은 채 결과를 믿는 방식은 무검증 AI 코딩에 가깝다. 반면 위임 범위와 검증 기준, 실패 조건과 사람의 개입 지점을 정한 뒤 AI에게 작업을 맡기는 방식은 매니지드 코딩이라고 부를 수 있다.

AI에게 끝까지 위임할 수 없는 것은 특정 코드나 인터페이스, 테스트 자체가 아니다. 위임의 경계를 정하고 증거의 충분성을 판단하며 결과에 책임지는 일이다.

> 매니지드 코딩은 위임하지 않는 방식이 아니라, 위임의 범위를 관리하는 방식이다.

### 3.2 경계와 계약을 먼저 정의한다

AI가 중간 과정을 빠르게 채워주더라도 애매한 부분을 그대로 두면 아래 단계로 내려갈수록 더 크게 꼬인다. 특히 여러 구성 요소가 만나는 경계를 명확하게 정의해야 한다.

- API 요청과 응답
- DTO와 데이터 스키마
- 함수의 입력과 출력
- 데이터 흐름과 상태 전이
- 실패 조건과 에러 형식
- 인증과 권한
- 시스템 간 계약

이러한 계약도 AI에게 초안을 맡길 수 있다. 하지만 도메인 개념을 제대로 반영하는지, 내부 모델을 불필요하게 외부에 노출하지 않는지, 실패와 권한, 데이터 정합성을 충분히 표현하는지는 사람이 검토하고 승인해야 한다.

경계가 명확하면 AI가 각 내부 구현을 독립적으로 만들 수 있고, 서로 다른 작업의 결과도 같은 계약을 기준으로 통합할 수 있다. 경계가 모호하면 AI는 빈칸을 일반적인 추측으로 채우고 그 추측이 아래 단계 전체로 퍼진다.

AI 시대에는 코드를 많이 작성하는 능력보다 경계와 계약을 정확히 정의하는 능력이 중요해진다.

### 3.3 테스트를 실행 가능한 명세로 만든다

지속적으로 변경하고 운영하는 소프트웨어에서 테스트 자동화는 사실상 필수다. AI가 생성한 모든 코드를 사람이 직접 읽어 검증할 수 없다면 요구사항을 만족하고 기존 기능을 훼손하지 않았다는 사실을 반복해서 확인할 수 있어야 한다.

기존에는 일정이 부족하다는 이유로 테스트가 뒤로 밀리는 프로젝트가 많았다. 구현 비용이 크게 낮아진 AI 코딩에서는 테스트를 여유가 있을 때 추가하는 작업으로 볼 수 없다. 테스트는 AI의 결과를 받아들일 수 있는지 판단하는 기본 조건이다.

- 유닛 테스트는 작은 단위의 규칙과 불변조건을 확인한다.
- 통합 테스트는 컴포넌트와 시스템 사이의 계약을 확인한다.
- E2E 테스트는 사용자의 전체 흐름을 확인한다.
- 회귀 테스트는 바꾸면 안 되는 기존 동작을 보호한다.

테스트 자동화와 TDD가 같은 말은 아니다. TDD는 구현 전에 실패하는 테스트를 만들고 최소한의 구현과 리팩터링을 반복하는 개발 방식이다. AI 코딩에서 더 중요한 것은 모든 작업에 전통적인 TDD 절차를 강제하는 것이 아니라 구현 전에 요구사항, 완료 조건, 예외 상황과 보존해야 할 동작을 실행 가능한 검증 기준으로 만드는 것이다.

어려운 것은 테스트 코드를 작성하는 일이 아니다. 무엇이 올바른 동작인지 정의하고 시스템을 어떤 단위로 나누며 각 경계가 어떤 계약을 가져야 하는지 결정하는 일이다. 결국 테스트를 설계하는 일은 소프트웨어를 설계하는 일이다.

AI가 테스트 코드를 작성할 수는 있지만 테스트 케이스의 타당성까지 자동으로 보장되지는 않는다. 사람은 정상 흐름뿐 아니라 경계값, 실패, 권한, 데이터 정합성, 불변조건과 회귀 시나리오가 충분한지를 검토해야 한다.

> AI 코딩에서 테스트는 부가 작업이 아니라, 무엇이 올바른 결과인지 알려주는 실행 가능한 명세다.

### 3.4 리뷰의 중심을 인터페이스와 테스트 케이스로 옮긴다

AI가 생성한 모든 구현 코드를 사람이 같은 깊이로 정독하는 방식은 확장하기 어렵다. 사람이 면밀히 검토해야 할 기본 대상은 요구사항과 완료 조건, 인터페이스, 테스트 시나리오다. 앞에서 정의한 계약과 실행 가능한 명세가 서로 일치하는지 확인하는 데 제한된 검토 시간을 집중해야 한다.

테스트 코드의 문법을 모두 읽기보다 어떤 상황에서 무엇을 기대하는지와 빠진 시나리오가 없는지를 검토한다. 정의한 요구사항과 위험을 테스트가 충분히 다루고 실행 증거가 수용 기준을 충족했다면 일반적인 구현 검토의 상당 부분을 자동화된 검사로 대체할 수 있다.

```text
요구사항과 완료 조건
→ 인터페이스와 시스템 경계
→ 테스트 시나리오와 불변조건
→ 테스트·정적 분석·실행 증거
→ 남은 우려를 검증할 추가 조건과 증거
```

염려되는 부분이 있다면 구현을 더 오래 읽는 것으로 끝내서는 안 된다. 가능한 경우 테스트 케이스나 정적 규칙으로 만들고, 그 밖에는 보안 검사, 마이그레이션 예행연습과 데이터 대조, 동시성·부하 테스트, 관찰 지표, 단계적 배포와 롤백 조건처럼 반복 가능한 검증 수단으로 바꿔야 한다.

구현 코드는 실패 원인을 조사하거나 어떤 검증이 더 필요한지 찾기 위해 선택적으로 읽을 수 있다. 그러나 사람이 모든 분기와 실행 환경을 머릿속으로 추적해 문제를 찾아낸다는 보장은 없다. “코드를 읽어보니 괜찮아 보인다”는 판단은 최종 승인 근거가 될 수 없다.

> 우려를 코드 리뷰의 질문으로 남겨두지 말고, 반복해서 실행할 수 있는 검증 조건으로 바꾼다.

### 3.5 실패를 숨기는 편법을 정책으로 통제한다

반복해서 판단하는 기준은 개발 지침과 자동화된 규칙으로 만들어야 한다. 특정 문법을 무조건 금지하기보다 어떤 실패를 숨기는지와 기존 계약을 약화하는지를 판정해야 한다.

다음 질문을 정책과 테스트에 반영할 수 있다.

1. 근본 원인을 해결했는가, 증상만 감췄는가?
2. 실패 상태를 정상 상태처럼 만들지는 않았는가?
3. 기존 인터페이스나 테스트 기준을 느슨하게 만들지는 않았는가?
4. fallback이 명시적인 도메인·운영 정책에 따른 것인가?
5. 문제가 발생했을 때 로그와 지표로 발견하고 복구할 수 있는가?

fallback은 구현상의 편의가 아니라 어떤 실패에서 동작하고, 대체 결과가 왜 유효하며, 어떻게 감지하고 복구할지를 정한 명시적인 정책이어야 한다. `null`, `any`, 기본값, 재시도도 마찬가지다. 정상적인 도메인 표현인지 실패 신호를 없애는 우회인지 구분해야 한다.

정적 분석으로 잡을 수 있는 패턴은 자동으로 차단하고 의미적인 문제는 실패·경계 테스트와 운영 지표로 검증해야 한다. 사람이 같은 기준을 매번 코드에서 다시 찾게 해서는 AI의 생성 속도를 따라갈 수 없다.

편법을 금지한다는 것은 짧은 코드를 금지하는 것이 아니다. 실패를 숨겨 성공처럼 보이게 만드는 수정을 금지하는 것이다.

### 3.6 검증할 수 있는 만큼만 생성하고 병렬화한다

비동기 에이전트가 사람이 없어도 안전하게 진행할 수 있도록 각 작업의 범위, 입력, 산출물과 완료 조건을 독립적으로 정의해야 한다. 변경 단위가 작고 계약이 명확할수록 조사, 구현, 테스트와 리팩터링을 병렬로 맡기기 쉽다.

많은 작업을 동시에 시작하는 것 자체가 생산성은 아니다. 생성된 결과를 검증하고 통합할 수 있는 양보다 더 많은 작업을 실행하면 변경 대기열과 충돌만 늘어난다. 병렬 작업 수는 검증과 통합 처리량에 맞춰 제한해야 한다.

AI 작업의 수나 생성된 코드량이 아니라 검증을 마치고 시스템에 안전하게 통합된 결과를 생산성으로 봐야 한다.

### 3.7 임시 구조에는 종료 조건을 둔다

기존 경로를 대체하거나 임시 호환 구조를 추가하는 작업에는 기존 경로를 언제 정리할지도 포함해야 한다. 이중 기록, fallback과 추가형 모델에는 정본, 적용 범위, 담당자, 종료 시점, 대조 방법과 제거 후 회귀 검증이 필요하다. 구현 완료와 아키텍처 전환 완료를 구분하지 않으면 과도기 구조가 영구화된다.

DB 사례와 같은 마이그레이션을 승인하기 전에는 다음을 확인해야 한다.

- 기존 모델을 유지해야 하는 범위는 어디까지인가?
- 새 모델이 기존 모델과 표현하는 개념은 어떻게 다른가?
- 신규 모델의 정본은 무엇이며 언제 전환되는가?
- 기존 모델을 제거할 담당자, 시점과 완료 조건은 무엇인가?
- 이중 기록과 fallback의 종료를 어떻게 검증할 것인가?

임시 구조를 만드는 것 자체가 문제는 아니다. 끝낼 방법이 없는 임시 구조가 문제다.

### 3.8 문서는 적게 만들고 신뢰도를 관리한다

코드, 스키마나 테스트에서 안정적으로 확인할 수 있는 사실을 사람이 별도 문서에 반복해서 적을 필요는 없다. 중복 문서는 구현과 함께 갱신되지 않아 서로 다른 정본을 만든다. 필요한 경우 코드에서 자동으로 생성되는 참조 문서를 사용할 수 있다.

문서에는 코드만으로 알 수 없지만 사람과 AI가 반드시 공유해야 하는 정보를 남긴다.

- 프로젝트가 지켜야 하는 핵심 개발 지침
- 설계 의도와 선택의 이유
- 시스템 경계와 외부 계약
- 보안과 데이터 정합성처럼 위반해서는 안 되는 원칙
- 빌드, 배포와 장애 대응에 필요한 절차

새 문서를 만들기 전에는 기존 기준 문서에 통합할 수 없는지, 코드나 자동화된 규칙으로 표현할 수 없는지부터 확인한다. 문서를 추가했다면 갱신 책임자와 폐기 기준도 정해야 한다. 유지할 책임이 없는 문서는 생성하는 순간부터 부채가 된다.

코드와 테스트는 시스템이 어떻게 동작하는지를, 설계 결정 기록은 왜 그렇게 만들었는지를, 운영 절차는 장애와 배포 때 무엇을 해야 하는지를 설명하는 정본이 되어야 한다.

다국어 문서를 운영하는 방식도 달라진다. 지금까지 오픈소스 프로젝트에서는 언어별 번역 문서를 별도로 제공하는 것이 접근성을 높이는 데 실질적인 도움이 됐다. 그러나 번역본마다 별도의 구조를 만들고 각각 갱신하면 원문과 번역본의 시점이 어긋나고, 어느 문서가 최신인지 알기 어려워진다.

이제는 필요한 시점에 AI로 원하는 언어의 번역본을 만들 수 있다. 따라서 모든 언어의 문서를 각각 관리하기보다 하나의 정확하고 명료한 원문을 정본으로 유지하고, 번역에 필요한 용어집과 맥락을 함께 관리하는 편이 낫다. 문서 관리에 드는 힘은 번역본의 수를 늘리는 데보다 핵심 내용의 정확성과 구조, 최신성을 높이는 데 써야 한다.

다국어 지원을 없애자는 뜻은 아니다. 처음 접하는 사용자의 접근성이나 검색 가능성을 위해 공식 번역본이 여전히 필요할 수 있다. 특히 법적 고지, 보안과 안전 지침, 도메인 전문 용어처럼 오역의 비용이 큰 내용은 AI 번역을 그대로 배포해서는 안 된다. 중요한 번역은 사람이 검토해야 한다. 핵심은 여러 언어의 문서를 각각 정본처럼 관리하지 않는 것이다.

> 코드나 스키마에서 안정적으로 확인·생성할 수 있는 사실은 수동으로 중복하지 않고, 문서에는 설계 이유와 핵심 지침, 운영 판단을 남긴다.

### 3.9 AI가 번 시간을 소프트웨어 공학에 다시 투자한다

기존에도 테스트 자동화, 지속적인 리팩터링, 구조 개선, 운영 검증과 필요한 문서의 유지가 중요하다는 사실은 잘 알려져 있었다. 하지만 실제 프로젝트에서는 일정이 부족하다는 이유로 뒤로 밀리는 경우가 많았다. 당장 필요한 기능 구현과 장애 해결이 우선이었기 때문이다.

AI는 기능 구현뿐 아니라 테스트 작성, 코드 분석과 반복적인 리팩터링에 드는 비용도 낮춘다. 그동안 중요성을 알면서도 비용 때문에 충분히 적용하지 못했던 체계적인 개발 방법을 일상적인 개발 과정에 포함할 수 있게 된 것이다.

동시에 이러한 방법은 선택 사항이 아니라 AI의 높은 생산성을 감당하기 위한 기본 조건이 된다. AI가 절약한 시간을 더 많은 기능과 코드 생성에만 사용하면 검증 병목과 기술 부채는 오히려 커진다. 높아진 생산성의 일부를 테스트와 CI, 구조 개선, 운영 관찰, 정리 작업과 신뢰할 수 있는 핵심 문서 유지에 다시 투자해야 한다.

> AI 코딩의 진정한 생산성은 더 많은 코드를 만드는 데 있지 않다. 과거에는 비용 때문에 생략했던 소프트웨어 공학을 일상적으로 실행하는 데 있다.

### 3.10 개발자의 학습 중심을 한 단계 높인다

AI가 세부 구현을 맡아주는 만큼 사람은 요구사항, 설계, 테스트, 아키텍처와 운영을 연결하는 방법을 더 많이 배워야 한다. 특정 기술의 세부 명세를 암기하는 능력보다 도메인 모델링, 책임과 경계, 기술적 트레이드오프, 데이터 일관성, 테스트 전략, 보안, 마이그레이션과 장애 대응을 함께 다루는 능력이 중요해진다.

프레임워크와 라이브러리의 세부 지식이 필요 없어지는 것도 아니다. 그 역할이 암기와 반복 구현에서 선택과 검증의 기반으로 이동한다. 개발자는 AI가 사용한 기술이 현재 시스템에 적절한지 판단할 수 있을 만큼의 기반 지식을 갖춰야 한다.

이것은 프로그래밍 언어, 데이터베이스와 운영체제의 기초를 배우지 않아도 된다는 뜻이 아니다. 기초 원리는 AI의 결과를 이해하고 검증하기 위해 여전히 필요하다. 저수준의 원리를 생략하는 것이 아니라 반복 구현에 사용하는 시간을 줄이고 그 위의 설계와 판단을 더 깊게 배워야 한다.

97학번인 내가 전산과에서 데이터베이스를 배울 때는 한 학기 동안 관계형 데이터베이스의 구조와 특성, SQL 문법과 쿼리 작성법을 자세히 공부했다. 이러한 기초는 지금도 배워야 한다. 다만 AI가 SQL과 스키마를 작성할 수 있다면 학습이 직접 쿼리를 작성하는 능력에서 끝나서는 안 된다. 왜 이런 모델을 선택했는지, 어떤 제약조건이 필요한지, 트랜잭션 경계를 어디에 둘지, 인덱스가 어떤 비용을 만들고 운영 스키마를 어떻게 변경할지를 판단할 수 있어야 한다.

객체 지향 프로그래밍은 책임과 상태를 어디에 둘지 생각하게 하고, 디자인 패턴은 반복되는 설계 문제를 설명하는 언어를 제공하며, 소프트웨어 아키텍처는 시스템 전체의 경계와 선택을 다루게 한다. OOP, 패턴과 아키텍처는 학습의 추상화 수준을 높이는 출발점이 될 수 있다.

직접 구현하는 훈련도 사라져서는 안 된다. 프로덕션에서 모든 코드를 직접 작성하는 방식은 비효율적일 수 있지만, 학습 과정에서는 먼저 설계하고 실행 결과를 예상하며 핵심 로직을 직접 구현해 봐야 AI의 결과를 판단할 내부 모델을 만들 수 있다. 직접 코딩은 기본 생산 방식에서 이해와 판단 능력을 기르는 의도적인 훈련으로 이동한다.

AI 시대에는 배워야 할 것이 줄어드는 것이 아니라 학습의 중심이 한 단계 높은 곳으로 이동한다.

### 3.11 주니어에게 작은 책임의 경계를 제공한다

주니어는 AI와 코드 작성 속도로 경쟁하기보다 작은 시스템 경계를 처음부터 끝까지 책임지는 경험을 쌓아야 한다.

- 요구사항을 구체적인 사례와 완료 조건으로 바꾸기
- 버그를 직접 재현하고 실패하는 테스트 만들기
- AI의 변경이 왜 동작하는지 설명하기
- 공식 문서와 실행 결과로 AI의 설명을 확인하거나 반증하기
- 여러 설계안을 비교하고 선택한 이유 기록하기
- 기능을 배포한 뒤 로그와 사용자 반응 관찰하기
- 장애 원인을 추적하고 회고하기

조직도 주니어에게 단순히 AI를 잘 검토하라고 요구해서는 안 된다. 주니어가 책임질 수 있는 작은 경계, 시니어가 정의한 개발 지침과 아키텍처 원칙, 검증 가능한 테스트 환경과 지속적인 피드백을 제공해야 한다. 주니어가 하던 일을 모두 AI로 대체하면 당장의 생산성을 얻는 대신 미래의 시니어 개발자를 잃을 수 있다.

> AI 시대의 개발자는 코드를 한 줄씩 생산하는 사람이 아니라, AI에게 위임할 일을 설계하고 결과의 올바름을 반복 가능한 증거로 검증하며 최종 결과에 책임지는 사람이다.
