# AI 코딩을 대하는 개발자의 자세

## 들어가며

C를 본격적으로 공부하기 시작한 것은 1995년 무렵이었다. 당시에는 “프로그래밍을 제대로 알려면 어셈블리어를 알아야 한다”는 말을 종종 들었다. 실제로 C 코드 사이에 어셈블리어가 섞여 있는 소스도 심심찮게 볼 수 있었다.

그래서 어셈블리어를 잔뜩 설명해 놓은 책에도 도전했다. 당시 고등학생이었던 나는 GW-BASIC 정도밖에 몰랐다. 어셈블리어가 어려워서 이해하지 못했다기보다, 더하기 같은 단순한 연산 하나에도 값을 레지스터로 옮기고 결과를 다시 저장하는 여러 동작을 일일이 지시해야 한다는 방식이 불합리하게 느껴졌다.

결국 책을 끝까지 읽지 못했다. 그때 도전했던 책은 30년이 지난 지금도 구석 어딘가에 잠들어 있다.

![당시 도전했던 『마이크로소프트 매크로 어셈블러 바이블』](../scm544242603556.jpg)

어셈블리어를 알았다면 하드웨어의 동작과 C 코드가 기계에서 실행되는 방식을 더 깊이 이해할 수 있었을 것이다. 성능이 중요하거나 하드웨어를 세밀하게 제어해야 하는 상황에서도 도움이 됐을 것이다.

하지만 어셈블리어로 범용 애플리케이션을 개발하기에는 생산성이 너무 낮았고 이식성과 유지보수에도 불리했다. C와 컴파일러가 발전하면서 개발자는 모든 명령을 직접 작성하지 않고도 더 많은 일을 빠르게 구현할 수 있게 됐다. 어셈블리어는 사라지지 않았지만, 대부분의 개발자가 매일 직접 다루는 작업에서는 한 단계 아래로 내려갔다.

그 뒤에도 컴파일러가 만든 코드를 믿지 못하거나, 제대로 된 프로그램은 어셈블리어로 직접 작성해야 한다고 생각하는 개발자들이 있었다. 특정 영역에서는 타당한 태도였지만, 모든 애플리케이션을 그렇게 개발하기에는 생산성 차이가 너무 컸다.

30여 년이 지난 지금, AI 코딩을 둘러싼 반응에서 비슷한 기시감을 느낀다. AI가 작성한 코드는 믿기 어렵고, 직접 작성해야만 제대로 이해할 수 있다는 이유로 AI 도입을 주저하거나 제한적으로 사용하는 개발자들이 있다. 이런 우려에는 근거가 있다. AI는 그럴듯하지만 잘못된 코드를 만들 수 있다.

물론 컴파일러와 AI는 전혀 다르게 동작한다. 컴파일러는 형식 언어로 작성된 소스를 정해진 규칙에 따라 변환하지만, AI는 자연어 요구와 프로젝트 맥락을 바탕으로 결과를 생성한다. 그 결과가 개발자의 의도를 보존한다는 보장은 없으므로 별도의 검증이 필요하다. 테스트가 통과했다는 이유만으로 요구사항을 충족했다고 단정해서도 안 된다.

둘이 닮은 점은 작동 방식이나 신뢰성이 아니다. 개발자가 모든 구현 세부를 직접 작성하지 않고도 더 넓은 문제를 다룰 수 있게 한다는 점이다.

여기서 말하는 AI 에이전트는 채팅창에서 코드 조각만 답해 주는 도구가 아니다. 프로젝트 저장소를 탐색하고 파일을 수정하며, 명령을 실행해 빌드와 테스트 결과까지 확인한다. 새로운 기술을 조사하고 요구사항을 정리하며, 설계안과 코드, 테스트, 문서도 작성한다.

나 역시 2025년 말까지는 코딩을 직접 주도하고 AI에는 검토와 보완을 주로 맡겼다. AI가 작성한 코드를 내가 직접 작성한 코드만큼 신뢰하기 어려웠기 때문이다.

그러나 2026년 초부터 AI 에이전트를 실제 프로젝트에 본격적으로 적용하면서 생각이 달라졌다. AI에게 구현의 상당 부분을 맡기고 내가 요구사항과 방향을 정한 뒤 결과를 검증하는 방식으로도 개발을 진행할 수 있었다. 무엇보다 직접 모든 코드를 작성할 때보다 내가 동시에 다룰 수 있는 문제의 범위가 크게 넓어졌다.

AI에는 여전히 분명한 한계가 있다. 잘못된 전제를 바탕으로 멀쩡해 보이는 코드를 만들거나 프로젝트 전체의 맥락을 놓칠 수 있고, 결과를 검증하는 데도 비용이 든다. 그럼에도 실제 프로젝트에서 체감한 생산성 향상은 이런 한계와 검증 비용을 감수할 가치가 있을 만큼 컸다.

AI와 어떻게 일할 것인가. 무엇을 맡기고 무엇을 직접 판단할 것인가. AI가 만든 결과를 어떻게 검증하고, 그 결과에 대해 누가 책임질 것인가.

이 글은 7개월 동안 AI 에이전트와 함께 프로젝트를 진행하며 이 질문들에 대한 답을 찾아간 경험담이다.

## 출시 6주 전, 프로젝트에 합류하다

2026년 1월, 나는 팀장 한 명과 팀원 두 명으로 구성된 개발팀에 합류했다. 팀은 전시·행사 현장에서 사용할 티켓 서비스를 개발하고 있었고, 정식 운영까지 남은 기간은 불과 6주였다.

합류 직후 가장 먼저 프로젝트의 진행 상황과 시스템 구성을 파악했다. 당시 개발팀이 담당하던 제품과 구현 방식은 다음과 같았다.

| 구성 요소 | 당시 구현 형태 |
| ------- | ------------------------------------------------ |
| 서비스 백엔드 | Java |
| 입장 키오스크 | iOS 네이티브 앱 |
| 발권 키오스크 | Android 앱에서 서버가 JSP로 렌더링한 웹 화면을 표시 |
| POS | Android 네이티브 앱 |
| 사용자용 앱 | iOS와 Android 네이티브 앱으로 각각 개발 |
| 백오피스 | JSP로 화면과 서버 로직을 함께 구현한 별도 애플리케이션. 서비스 백엔드와 DB 공유 |

인력 구성도 불안정했다. 팀장이 퇴사를 앞두고 있어 서비스 백엔드는 주니어 개발자 한 명이 사실상 전담하고 있었다. 다른 팀원 한 명은 사용자용 iOS 앱뿐 아니라 Android 기반 발권 키오스크까지 담당하고 있었다. 사용자용 Android 앱은 팀장이 직접 개발하고 있었지만, Android 개발 경험은 이번 프로젝트가 처음이었다.

시스템 구성을 살펴보면서 가장 먼저 확인한 문제는 제품별 기술과 개발 방식이 지나치게 분산돼 있다는 점이었다.

사용자용 앱은 iOS와 Android 네이티브로 각각 개발되고 있어 동일한 기능을 두 번 구현하고 검증해야 했다. 입장 키오스크는 iOS, 발권 키오스크와 POS는 Android로 구성돼 전용 단말조차 하나의 개발·배포 체계로 관리하기 어려웠다.

발권 키오스크는 Android 앱 내부에서 JSP 화면을 표시하는 구조였다. 하나의 기능을 수정하려면 Android 앱과 서버 화면을 함께 확인해야 했고, 문제가 발생했을 때도 앱과 서버 양쪽을 오가며 원인을 추적해야 했다. 백오피스는 JSP로 화면과 서버 로직을 함께 구현한 별도 애플리케이션이었지만, 서비스 백엔드와 동일한 DB를 직접 사용하고 있었다. 이 때문에 한 시스템의 변경이 다른 시스템에 미치는 영향을 통제하기도 어려웠다.

세 명뿐인 개발팀이 서로 다른 기술로 구현된 여러 제품을 동시에 개발하고 운영해야 하는 상황이었다. 제품별 기술 선택은 분산돼 있었고, 팀 전체가 공유하는 개발 기준이나 출시 이후의 운영 계획도 명확하지 않았다.

남은 6주 안에 모든 기능을 완성하는 것만으로는 부족했다. 실제 현장에서 안정적으로 운영할 수 있는 구조를 만들어야 했다. 일정 지연과 운영 장애 가능성이 모두 높은 상태였기 때문에, 상황을 파악한 첫날부터 우선순위를 다시 정하고 즉시 작업에 착수했다.

### AI 에이전트로 프로젝트를 분석하다

그날 밤부터 AI 에이전트를 활용해 프로젝트를 구체적으로 파악하기 시작했다.

AI에게 구현된 REST API를 목록으로 만들고 기능별로 분류하게 했다. 그런 다음 각 API가 어떤 역할을 하는지 분석하게 하고, 이해하기 어려운 요청 인자가 나오면 관련 코드를 추적해 용도를 확인하게 했다. 서비스에 어떤 기능이 구현돼 있고 서로 어떻게 연결되는지에 대한 전체적인 윤곽을 파악하는 데 하루가 걸렸다.

물론 그날 얻은 분석이 모두 정확했던 것은 아니다. 이후 실제 개발을 진행하며 다시 확인해 보니, AI가 구현된 것으로 파악한 API 중에는 개발하다 중단된 것도 있었고, API의 이름을 바탕으로 추정한 용도가 실제 동작과 전혀 다른 경우도 있었다. 그럼에도 짧은 시간 안에 전반적인 기능을 파악하는 데는 충분히 큰 도움이 됐다. 같은 수준의 분석을 기존 방식으로 진행했다면 아마 일주일은 필요했을 것이다.

조사 결과 백엔드에는 많은 기능이 구현돼 있었다. 그러나 DB 스키마와 REST API의 구조와 이름만으로는 각 요소의 역할과 연결 관계를 파악하기 어려웠다. 일부 API에는 별도의 암호화·복호화 로직이 들어가 있었지만 적용 기준이 일관되지 않았고, 같은 종류의 데이터도 API에 따라 처리 방식이 달랐다. 다른 시스템과 연동하거나 문제의 원인을 추적하기 어려운 구조였다.

사용자용 앱은 Android와 iOS 네이티브 코드베이스로 나뉘어 있었다. 같은 기능과 화면을 플랫폼별로 따로 구현하고 테스트해야 했기 때문에 작은 팀이 감당해야 할 작업도 그만큼 늘어났다. 키오스크와 POS 역시 실제 운영을 위한 완성품이라기보다 각 기능의 동작 가능성을 확인하기 위한 시제품에 가까웠다.

그렇다고 아무것도 동작하지 않는 것은 아니었다. 개별 화면과 API는 동작했기 때문에, 기능 단위의 시연만으로는 프로젝트가 마무리 단계처럼 보였다.

하지만 데모가 가능한 것과 실제 서비스를 운영할 수 있는 것은 달랐다. 사용자가 처음부터 끝까지 서비스를 이용할 수 있도록 기능들이 연결돼 있지 않았다. 출시를 앞둔 하나의 제품이라기보다 여러 시제품이 한 프로젝트 안에 모여 있는 상태에 가까웠다.

개발팀장은 2월 출시에 필요한 작업을 자신이 마무리하겠다고 했다. 그러나 나는 기존 시스템만으로 6주 뒤 서비스를 안정적으로 운영하기는 어렵다고 판단했다. 개발팀장의 의지와는 별개로, 일정 안에 실행할 수 있는 대응책이 필요했다.

### AI 에이전트로 백오피스를 다시 만들다

기존 시스템에 대한 1차 분석을 마친 뒤, 나는 프로젝트 전체 일정과 출시 범위를 관리하는 한편, JSP로 개발된 백오피스를 Next.js로 다시 만들기로 했다. 이유는 크게 세 가지였다. 우선 백오피스는 전체 구성 요소 가운데 완성도가 가장 낮았다. 또한 화면과 서버 로직이 뒤섞인 기존 JSP 구조는 기능을 빠르게 추가하기 어려웠고, 이후 유지보수에도 불리했다. 더 많은 기능이 쌓이기 전에 교체하는 편이 낫다고 판단했다. 서비스 백엔드와 백오피스가 동일한 DB에 각각 직접 접근하는 구조도 정리할 필요가 있었다.

내가 마지막으로 백오피스를 직접 개발한 것은 2년 전이었다. 당시에도 Next.js를 사용했으며, 개발 속도를 높이기 위해 React UI 컴포넌트 라이브러리인 MUI 기반의 유료 템플릿을 구매해 사용했다.

그러나 AI 에이전트로 백오피스를 개발해 보니, 과거에는 효율적이라고 생각했던 템플릿 수정 방식조차 상대적으로 비효율적으로 느껴졌다. 필요한 메뉴와 각 화면에 보여 줄 데이터를 간략히 설명하면, AI 에이전트는 그 요구를 바탕으로 백오피스의 기본 구조와 주요 화면을 빠르게 구현했다. 데이터를 간략히 설명했다고 했는데 정확하게는 rest api의 req/res 정리한 문서를 던졌을 뿐이다.

급박한 일정에서 백오피스의 시각적 완성도는 고려 대상이 아니었다. 그럼에도 결과물은 별도의 유료 템플릿이 필요 없을 만큼 완성도가 높았다.

### AI에게 맡기고 검토하지 않다

백오피스 개발은 순조로웠다. 백엔드 API 연동을 시작하기 전까지는.

백엔드를 담당한 개발자는 경력 3년 차였다. 경험은 많지 않았지만 그동안 요구사항을 곧잘 구현했기 때문에, API 개발도 무리 없이 맡길 수 있다고 생각했다.

나는 백오피스에 필요한 API를 요청하고 연동을 시작했다. 그러나 과정은 매끄럽지 않았다. 구현됐다는 API를 호출하면 동작하지 않았고, 수정했다는 말을 듣고 다시 확인하면 또 다른 오류나 누락이 드러났다. 하나의 API를 연동하는 과정에서 세 차례나 문제가 반복되자, 이 방식으로 연동 작업을 계속하는 것은 무리라고 판단했다.

나는 백엔드 개발자에게 AI가 만든 코드를 직접 검토했는지 물었다. 돌아온 답은 충격적이었다. 구현 결과를 검토하지 않았을 뿐 아니라, AI가 설계한 API조차 확인하지 않았다. 백엔드 개발자가 한 일은 내가 전달한 요구사항을 그대로 AI 에이전트에 입력하고, 에이전트가 작업을 완료했다고 답하면 그 말을 나에게 전달하는 것이 전부였다.

그 답을 듣고 나자, 나는 그에게 개발 업무를 계속 맡겨도 되는지 의문을 품기 시작했다.

왜 이런 일이 발생했을까?

내가 내린 결론은 책임감과 검증 능력이 모두 부족했다는 것이었다. 경험이 부족한 개발자에게 AI가 만든 API를 검토하는 일은 쉽지 않다. 요구사항부터 API 설계, 정상 동작과 예외 상황까지 하나씩 따져봐야 하기 때문이다. 경험으로 빠르게 판단할 수 없다면 그만큼 더 많은 시간과 집중력을 들여야 한다. 긴장되고 피곤한 작업이지만, 바로 그것이 개발자가 해야 할 일이다.

그 과정을 생략한 채 AI의 완료 보고만 전달한다면, 구현만 AI에게 맡긴 것이 아니라 개발자가 수행해야 할 판단과 검증의 의무까지 AI에게 떠넘긴 셈이다.

이것은 엄청난 비효율이었다. 나는 개발자에게 요구사항의 배경과 의도, 구현 방향과 주의사항을 설명하는 데 많은 시간을 썼다. 그러나 정작 개발자는 그 내용을 바탕으로 판단하거나 결과를 검증하지 않았다. 내 요구사항을 AI 에이전트에 전달하고, AI의 완료 보고를 다시 나에게 전달했을 뿐이다.

그 과정에서 요구사항의 의도는 구현에 제대로 반영되지 않았고, 나는 아무런 판단도 더하지 않는 중계자를 이해시키는 데 시간을 쓰고 있었다. 그렇다면 차라리 내가 직접 AI 에이전트에게 일을 맡기는 편이 더 효율적이지 않을까?

더 경악스러웠던 것은 하나의 애플리케이션에 AI 에이전트를 서너 개씩 동시에 투입하고 있었다는 사실이었다. 기존 기능이 반복해서 깨지고 매출 통계가 계속 맞지 않아, 작업 방식을 확인하던 중 알게 됐다.

여러 에이전트를 동시에 사용하는 것 자체가 문제는 아니다. 작업 범위와 변경 사항을 분리하고 각 결과를 검토한 뒤 통합한다면 병렬 개발의 효과를 얻을 수 있다. 그러나 그는 작업 간 충돌과 회귀 오류를 통제할 방법도 없이 여러 에이전트가 같은 애플리케이션을 동시에 수정하게 하고 있었다.

이런 방식은 토큰을 불필요하게 소모했을 뿐 아니라, 충돌과 오류를 확인하고 다시 수정하는 데 다른 개발자들의 시간까지 계속 낭비하게 했다.

이후에도 그가 다른 개발자와 키오스크 연동을 진행하면서 같은 API를 여러 차례 다시 만드는 모습을 보았다. 프로젝트가 급박한 상황이라 그때마다 깊이 개입할 여유는 없었다. 그러다 그가 한 말이 결정적이었다.

“큰 회사에서도 기획자들이 몇 명이 붙어서 검증해도 완벽하기 어려운데, 이 작은 회사에서 어떻게 팀장님 기준에 맞출 수 있겠어요?”

내가 요구한 것은 완벽함이 아니었다. 구현을 완료했다고 보고하기 전에 요구사항을 확인하고, API가 실제로 동작하는지 테스트하라는 것이었다. 오류가 발생할 수 있다는 사실과 검증을 생략해도 된다는 것은 전혀 다른 문제였다.

그 말을 듣고 나는 그가 단순히 경험이 부족한 것이 아니라, 자신이 완료했다고 보고한 결과물을 검증하는 일을 개발자의 의무로 받아들이지 않는다고 판단했다. 그는 팀에 기여하지 못했을 뿐 아니라 다른 개발자의 발목까지 잡고 있었다. 프로젝트가 급박했지만, 남겨 둘 이유는 없었다. 미련 없이 다음 날 해고를 통보했다. 이 때가 4월 초의 일이었다.

### AI로 커뮤니케이션 비용을 줄이다

위에서 얘기했지만 백오피스를 개발하는 과정에서 백엔드 API와 연동하는 비용이 컸다. 백오피스의 기능은 대부분 API에서 가져온 데이터를 보여주는 것이다. 그런데 연동하는 단계에서 수 차례 실패가 반복되자 프론트와 백엔드가 일을 나눠서 하는 것이 비효율적으로 느껴졌다. 그래서 백오피스 개발도 백엔드 개발자가 담당하도록 했다. 백엔드 개발자는 처음에 프론트를 하고 싶지 않다고 했지만 그게 더 효율적인 방법이라는 데는 동의하고 있었다. 백엔드 개발자가 거부하는 이유는 백엔드 전문 개발자가 되고 싶다는 것이었다. 나도 어설프게 이것저것 아는 것 보다 하나라도 제대로 아는 개발자를 더 좋게 생각한다. 지금까지는 그랬다는 말이다.

앞서 백엔드 개발자가 프론트엔드인 백오피스까지 개발하는 게 더 효율적이라는데 동의했다고 했다. 그러나 불과 1년 전이라면 결코 주니어에게 두 개의 애플리케이션을 같이 하라고 하지는 않았을 것이다. 그 때는 백엔드와 프론트엔드 각각의 기술에 대해서 자세히 알아야 했고 백엔드 만으로도 손 델 곳이 많았다. 이런 경우 두 개를 같이 하는 건 비효율적이다.

지금까지는 주니어 개발자가 풀스택을 지향하면 부정적으로 생각했다. 그러나 이제는 풀스택을 지향해야만 하는 개발환경이 된 것이다.

이런 변화는 백엔드만 개발자에게만 해당하는 것은 아니다. 그리고 백엔드가 프론트까지 해야 한다고 했지만 그것은 백오피스라는 API가 밀접한 관련이 있고 고급 프론트엔드 기술이 필요하지 않았기 때문이다.

백엔드가 프론트엔드까지 개발한다면 프론트엔드 개발자의 영역은 축소되는 것일까? 아니면 프론트엔드도 백엔드를 개발하는 모두가 풀스택이 되어야 할까?

아니다. 백엔드가 보다 윗 단계인 프론트엔드까지 영역을 넓히는 만큼 프론트엔드도 윗 단계인 UX 디자인까지 영역을 넓혀야 한다.

백오피스를 백엔드 개발자에게 넘기면서 시간적 여유가 생겼다. 백엔드를 포함해서 프로젝트 전체를 다시 만들 필요가 있었기 때문에 팀이 서비스를 런칭하고 유지하는 동안 나는 백엔드와 사용자앱을 만들어서 가능한 빨리 기존 시스템을 대체시킬 계획을 세웠다.

사용자 앱을 다시 만들려고 했을 때 두 개의 선택지가 있었다. 플러터와 RN 중에 무엇을 선택해야 할까 잠깐 고민했지만 경험이 있었던 RN이 아니라 한 번도 해보지 않은 플러터가 선택했다. 시간적 여유가 없었음에도 불구하고 낯선 기술을 선택하는 게 크게 부담되지 않았는데 AI 에이전트가 알아서 해주리란 기대가 있었기 때문이다.

사용자 앱을 다시 만들려고 했을 떄 가장 고민했던 지점은 AI 에이전트에게 어떻게 프론트 개발을 시켜야 할지 몰랐던 것이다. 처음에는 기존에 디자이너들이 만들어 놓은 피그마 파일을 AI에게 주고 개발을 시켰다. 그러나 결과물은 디자인과 일치하지도 않았고 제대로 동작하지도 않았다. 피그마 파일 대신 pdf나 svg로 줘도 마찬가지였다.

또 난감했던 점은 난 피그마를 다룰 줄 모르는데 AI에게 파일을 그대로 전달하기에는 고쳐야 할 부분이 꽤 있었다는 것이었다. 시간도 없는데 지금 피그마를 익혀야 하는 게 맞을까를 고민스러웠다.

그렇게 몇 시간을 이것 저것 해보다가 문득 깨달았다. AI 에이전트에게 똑같이 개발하라고 할게 아니라 개발해야 하는 기능을 알려주면 되는게 아닌가? 굳이 피그마로 디자인을 해야 하나? 과거에는 코드로 구현하는 시간이 길었기 때문에 디자인을 신중하게 하고 코딩에서 시행착오를 줄이는 것이 효율적이었다. 그래서 피그마로 디자인 하고 그것을 보고 그대로 구현하는 게 일반적인 방법이었다. 그러나 이제는 필요한 기능을 전달하면 에이전트가 알아서 그럴듯한 앱을 만들 수 있다. 그렇게 초안을 생성하고 더 구체적인 지시를 해가며 원하는 앱을 만드는 게 효율적이지 싶었다.

그리고 실제로 해보니 기대 이상의 결과물이었다. 몇 개의 문장으로 완성된 초안은 실제로 동작하기까지 했다. 어떤 기능이 필요한지 요구사항을 정의하는 대표에게 결과물을 보여주고 뭘 고치면 좋을지 논의하고 그자리에서 고친 화면을 검토할 수 있었다.

이 과정에서 디자이너들이 열심히 만든 피그마 파일은 필요가 없었다. 디자이너의 디자인 보다 AI가 생성한 디자인이 더 훌륭했다.

대표가 자신의 생각을 디자이너에게 이해시키고 프론트엔드가 디자인 파일을 보면서 구현하다가 버튼이 없거나 역할이 모호한 이상한 부분을 발견하면 다시 대표와 얘기하고 기획과 디자인을 수정하는 지난한 과정이 한 단계로 줄어든 것이다.

이렇게 단계가 많았던 것은 각 단계마다 전문가가 필요했기 때문인데 그 모든 일을 AI 하나로 할 수 있다면 단계를 생략해도 되는 것이었다.

결론은 기술 접근이 쉬워지면서 전문화에서 일반화로 스택을 넓히는 것이 더 효율적인 개발환경이 됐다는 것이다. 각자의 생각을 긴밀하게 파악해서 개발하는 것이 아니라 결과물을 갖고 검토하는 쪽이 생산적인 것이다.

한 사람이 더 넓은 영역을 담당하면 역할 사이의 전달과 조율이 줄어든다. 과거에는 한 사람이 여러 영역을 직접 구현하는 비용이 커서 전문 분야별로 일을 나누는 편이 효율적이었다. 그러나 AI가 각 영역의 구현 비용을 크게 낮추면서 상황이 달라졌다. 적어도 일정 규모까지는 역할을 세분화하기보다 한 사람이 더 넓은 범위를 맡아 커뮤니케이션 비용을 줄이는 편이 효율적일 수 있다.

### AI 에이전트는 제어가 어렵다

처음 AI 코딩을 해보면 개떡같이 말해도 찰떡같이 알아듣는 AI 에이전트가 그렇게 신기하고 기특할 수 없다.

별 기대가 없었을 때는 설마 이걸 하겠어? 하는 심정으로 조심스럽게 프롬프팅을 하게 된다. 그런데 곧잘 해내면 이게 되네? 하면서 점점 더 추상적이고 큰 목표를 던져주게 된다. 이렇게 하는게 더 빠르게 만들 수 있기 때문이다. 다시 얘기하지만 이제 개발의 병목은 커뮤니케이션에서 발생한다. 그게 사람 사이든 사람과 에이전트 사이든 말이다.

그 비용을 줄이려고 일을 큼지막하게 던져주면 AI 에이전트는 그럴듯한 똥덩어리를 만들기 시작한다.
처음 사용자 앱과 새 백엔드를 만들기 시작했을 떄 정확히 이 시행착오를 겪었다. 개발 시간이 부족한 만큼 점점 욕심을 내기 시작한다. 큰 일거리를 연속으로 2~3개 던져주는 동안 검증을 소홀히 했다. 일단 동작은 하고 지금까지 잘해왔기 때문에 검증하느라 코딩을 멈추는 것은 비효율적으로 느껴졌다.
더군다나 이 때는 잠을 자면서 2~3시간 마다 깨서 다시 프롬프팅을 하던 때여서 이런 문제는 더 심화됐다.

그렇게 밤새 열심히 일을 시키고 멀쩡한 정신으로 찬찬히 훑어보면, 내가 요구하지 않은 기능을 구현해 놓거나 정작 있어야 할 기능을 빠뜨린 부분이 보였다. 특히 보안에는 병적으로 집착하는 경향을 보였다. 필요 이상의 방어 로직과 제약을 추가해 아주 작은 변화에도 기능 전체가 중단되곤 했다.

한 번은 카드번호를 검색에 사용할 방법은 남겨 두지 않은 채 모두 마스킹해서 저장하고, 카드번호로 결제 기록을 검색하는 UI는 번듯하게 만들어 놓았다. 화면만 보면 완성된 기능처럼 보였지만 저장된 값으로는 애초에 검색할 수 없는 구조였다. 그런데도 AI에게 전체 기능을 테스트하라고 하면 몇 번이고 정상이라고 보고했다.

주어진 작업을 어떻게든 완료하려는 적극성이 지나친 것도 문제였다. 정상적인 방법으로 해결되지 않으면 꼼수를 쓰거나 문제를 과도하게 우회한 뒤 해결했다고 보고하는 경우도 흔했다.

AI에게 판단을 맡길 수는 있다. 그러나 그 판단을 검토하고 결과에 책임지는 일까지 넘겨서는 안 된다. 그렇지 않으면 AI는 잘못된 방향으로도 놀라울 만큼 열정적으로 삽질한다.

### AI를 쓰면서도 과거의 기준으로 판단하다

3월 초, 서비스는 가까스로 출시됐다. 같은 시기 iOS 개발자의 계약이 끝나면서, 그가 맡던 iOS 키오스크와 사용자 앱을 새로 채용한 Android 개발자에게 맡기기로 했다.

처음 이야기를 꺼냈을 때 그는 강하게 거부했다. 이미 Android 키오스크와 사용자 앱을 담당하고 있는데, iOS 키오스크와 사용자 앱까지 어떻게 맡느냐는 것이었다. 예상했던 반응이었다. 기존 방식으로 생각하면 한 사람이 네 개의 애플리케이션을 관리하는 것은 결코 가벼운 일이 아니었다.

그러나 AI 에이전트를 전제로 하면 업무량을 계산하는 방식이 달라진다. 개발자가 모든 코드를 직접 작성하는 대신, 요구사항을 정리해 에이전트에게 전달하고 결과를 검증하는 일이 중심이 된다. 플랫폼별 문법과 프레임워크의 세부를 모두 숙달해 직접 구현해야 하는 부담도 크게 줄었다.

iOS와 Android라는 플랫폼의 차이는 있었지만 구현해야 할 기능은 대부분 같았다. 구현 자체는 AI 에이전트가 매우 빠르게 처리했기 때문에, 실제 병목은 사람이 요구사항을 파악하고 결과를 검증하는 단계로 옮겨갔다. 물론 플랫폼별 빌드와 배포, 권한 처리처럼 고유한 문제까지 사라진 것은 아니었다. 처음부터 크로스 플랫폼으로 개발했다면 더 좋았겠지만, 네이티브 앱이 네 개라고 해서 기존 방식에서 예상하는 네 배의 부담이 생기는 것은 아니었다.

이런 차이를 차분히 설명하자 그도 내 판단을 받아들였고, 원만하게 업무를 맡길 수 있었다.

개발 환경이 크게 달라진 만큼, 그동안의 경험을 바탕으로 형성된 판단 기준도 새로운 환경에 맞게 갱신해야 한다.

이것은 한 사례에 불과하지만, AI 에이전트를 효과적으로 활용하는 데 필요한 능력은 직접 구현하는 능력과 조금 달랐다. 내가 지켜본 범위에서는 주어진 일을 직접 처리하는 데 익숙한 개발자보다, 업무를 정의하고 나누어 맡긴 뒤 결과를 검토해 온 사람이 AI 에이전트에 더 빠르게 적응했다. 팀장이라는 직급 때문이라기보다, 평소 일을 위임하고 검증해 온 경험의 차이에 가까웠다.

그 외에도 구체적인 내용은 기억나지 않지만 Android 개발자에게 AI 코딩 방식에 적응할 것을 몇 번인가 요구했었는데 그게 무리라는 것은 당시에도 알고 있었다.

단지 새로운 도구의 사용법을 익히는 정도가 아니라, 사고의 전환이 필요한 일이기에 충분한 시간이 필요했을 것이다. 그러나 이미 여러차례 시행착오를 겪은 작은 스타트업에 개인의 사정을 기다려줄 만한 여유는 없었다.

그래서였을까. 수습 평가를 앞두고 Android 개발자가 퇴사하게 된다.

### AI 에이전트로 1인 개발을 시작하다

Android 개발자가 퇴사 의사를 밝혔을 때, 차라리 잘됐다는 생각이 들었다. 팀원들에게 업무의 맥락과 의도를 설명하고, 진행 상황을 조율하고, 전달 과정에서 어긋난 결과를 다시 수정하는 비용은 당시 상황에서 너무 컸다. 그리고 개발자는 감정을 갖고 있기에 일주일에 몇 시간은 잔소리/조언/상담으로 시간을 보내야 했다. 이런 모든 시간을 고려하면 사람을 거치지 않고 내가 직접 AI 에이전트에 업무를 맡긴 뒤 결과를 검증하는 편이 더 효율적일 것 같았다.

나는 대표에게 퇴사자의 공백을 메우지 않고 1인 개발 체제로 운영하는 편이 좋겠다고 말했다. 그때는 몰랐지만, 대표는 개발팀이 무너져 사업을 접어야 하는 것은 아닌지 고민했다고 한다. 그러나 개발팀은 건재했다. 우수한 팀장(나)과 성실한 팀원들(AI 에이전트)이 있었기 때문이다.

진행되던 프로젝트를 모두 떠맡게 됐을 때 github의 저장소는 백엔드/안드로이드 키오스크/ios 키오스크/안드로이드 키오스크의 백엔드(JSP)/안드로이드 pos/android 사용자 앱/ios 사용자 앱/백오피스 등 8개 정도였다. 여기에 별도 행사를 위한 프로젝트가 있었고 flutter로 새로 개발 중인 사용자 앱이 있었다.

난 2001년에 처음 실무를 시작해서 지금까지 25년이 흘렀지만 백엔드 자바는 경험이 없었다. JSP 업로드 컴포넌트를 만들기는 했지만 백엔드라고 할 수는 없었다. 난 ios에 익숙했을 뿐이고 안드로이드 프로젝트 경험은 한 번 뿐이었다. 어떤 기술이든 필요해지면 금방 적응하고 무리없이 개발할 자신은 있었다. 지금까지 수행했던 프로젝트 중 상당수는 해보지 않았던 기술이나 도메인이었으니까 말이다. 그러나 경험 없는 기술을 동시에 두 개 세 개 커버해야 하는 상황은 거의 없었다(딱 한 번 있었는데, 미친 듯이 바빴고 성공한 것이 기적에 가까웠다.).

그렇지만 과거 1개의 기술을 학습해야 하는 상황 보다 부담이 없었다. 위의 플러터로 사용자 앱을 만들고 Nextjs로 백오피스를 만들면서 AI 에이전트의 능력을 충분히 경험했기 때문이다. 단 한 줄도 코딩할 필요가 없다면 기술은 중요하지 않았다.

이런 상황에서 내가 제일 먼저 한 일은 개발환경을 구축하는 것이었다. Flutter와 별도 행사 프로젝트는 내가 계속 진행하던 것이어서 그대로 두고 떠맡게 된 8개의 저장소는 웹과 안드로이드로 구분해서 2개의 모노레포로 구성했다. 모노레포로 모아놓으니 에이전트에게 일을 맡기기 수월했다.

마음 같아서는 2개가 아니라 1개에 모두 넣고 싶었지만 웹은 vscode로 실행과 검증을 하지만 안드로이드는 안드로이드 스튜디오를 사용해야 했기 때문에 1개로 합치는 것은 좋지 않다고 판단했다.

그렇게 일주일 정도의 시간이 흐르고 새로 구축한 개발 환경에 익숙해지자 확신할 수 있었다. 일정 규모까지는 혼자 개발하는 것이 생산성이 훨씬 높았다. 일정 규모라는 것이 애매한 표현인데 이것은 개발자의 역량에 따르는 것 같다. 뒤에서 자세히 얘기하겠지만 소프트웨어 공학 지식이 탄탄하고 개발 방법론에 능숙하다면 더 큰 규모의 프로젝트도 혼자 감당 가능할 것 같다.

그렇게 개발환경을 구축하고 ios/안드로이드 네이티브로 만들던 사용자 앱은 버려지게 되었고 현장에서 꼭 필요하다고 했던 pos와 발권 키오스크, 입장 키오스크,백오피스,백엔드 이렇게 5개로 범위를 축소해서 4월 말에 마무리 할 수 있었다.

시간이 흘러 위기를 넘긴 지금, 대표는 AI 에이전트들을 ‘클 이사’와 ‘코 부장’이라 부르며 모시고 있다. 당분간은 개발자를 추가로 채용하지 않아도 되겠다는 것이 나와 대표의 판단이다.

### AI 에이전트로 비개발자가 개발을 시작했다

중요 문제가 마무리 되고 드디어 품질 개선에 힘을 쏟을 여유가 생겼다고 기뻐하려던 첫 날 대표가 부드럽게 웃으며 말을 세 번 정도 돌린다. 싸늘했다. 가슴에 비수가 꽂히는 것 같았다. 이건 분명 안 좋은 신호였다. 뭘까? 대표는 무슨 아쉬운 얘기를 하려는 걸까?

대표는 4월 초부터 한 달 동안 AI 에이전트로 개발을 해오고 있었다. AI 에이전트가 추천해준 개발스택으로 진행하고 있었는데 백엔드는 supabase에 백오피스는 nextjs로 개발해서 vercel로 배포하고 있었다.

나는 이때 퇴사를 생각했다. 개발 경험이 없는 대표가 아무런 협의 없이 만든 서비스에, 대표가 정한 방식대로 키오스크를 붙이고 그가 만들던 백엔드와 백오피스까지 마무리하라는 요구였다. AI 에이전트와 한 달간 혼자 개발하면서 대표는 개발에 상당한 자신감이 붙은 듯했다. 내가 아무리 설명해도 대표는 내 판단보다 AI의 제안을 더 신뢰했다. 마치 처음 주식을 시작하자마자 하이닉스와 삼성전자로 원금을 열 배쯤 불린 초보 투자자에게 위험을 설명하는 전문가의 심정이랄까? 그러나 10배의 도파민에 중독된 주린이에게 무슨 말인들 귀에 들어올까.

예를 들어 대표는 키오스크와 사용자 앱을 RN으로 개발하려고 했다. AI가 이렇게 선택한 이유는 대표의 요구사항 중에 자유롭게 배포해야 한다는 조건이 있었기 때문이다. 그러나 RN을 선택한다고 해서 앱 전체를 자유롭게 배포할 수 있는 것은 아니었다. 일부 UI 변경을 빠르게 배포할 여지는 있어도 네이티브 모듈이나 하드웨어 연동까지 자유롭게 바꿀 수 있는 것은 아니었다.

내 경험에서 RN은 개발 환경을 구성하고 디버깅하기도 까다로웠다. Android와 iOS의 네이티브 UI로 렌더링하기 때문에 같은 코드를 사용해도 플랫폼별 동작 차이는 남았다. 내가 다룬 화면에서는 같은 스크롤 상태를 나타내는 값이 Android에서는 0.xx 범위로, iOS에서는 1xx대 정수로 전달되는 경우도 있었다. 결국 UI를 구현할 때마다 Android와 iOS에서 모두 확인해야 했다.

사용자 앱처럼 Android와 iOS를 모두 지원해야 한다면 플러터 같은 크로스 플랫폼 프레임워크를 고려할 수 있다. 그러나 대표가 새로 만들려던 키오스크는 Android 단일 기기에서만 동작했다. 굳이 네이티브 플랫폼과 애플리케이션 사이에 RN이라는 계층을 하나 더 두어 구조를 복잡하게 하고 오류가 발생할 지점을 늘릴 이유가 없었다.

키오스크는 제한된 메모리와 저가의 CPU를 사용하고, 프린터와 스캐너 같은 하드웨어와도 긴밀하게 연결된다. 이런 환경에서 RN을 사용하려면 실제 단말기의 성능과 장시간 실행 안정성, 플랫폼별 하드웨어 연동을 별도로 검증해야 했다.

보통의 개발자라면 제안하지 않았을 선택이고 설령 그랬다 하더라도 간단하게 한 마디면 납득할 수 있는 일인데 대표는 AI의 제안을 더 신뢰하고 있었기 때문에 한참을 설명해야 했다.
대표가 AI를 신뢰하면서 내가 AI에게 지시를 내리는게 아니라 내가 AI의 지시를 따라야 하는 처지가 됐다.
처음 얘기가 나왔던 날에는 대표의 지시를 받아들일 수 없었다. 대표는 포기하지 않았고 다음 주에 다시 이 문제를 거론했다.

아마 내가 주니어 개발자라면 별 생각이 없었을지도 모르겠다. 그러나 팀을 리드하는 역할이라고 생각했던 나에게 받아들이기 힘든 변화였다.

글을 쓰고 있는 지금 다시 생각해도 울컥한다.

--------------

이미 상당한 기능이 구현된 상황에서 별도의 개발이 필요하다고 설득하는 일은 쉽지 않다. 나는 AI가 정리한 분석 결과를 바탕으로 기존 시스템에서 마무리할 부분과 별도로 만들어야 할 부분을 나눠 설명했다. 내가 기존 개발에 뒤늦게 합류해 몇 가지 기능을 보완하는 것만으로는 남은 기간 안에 운영 준비를 마칠 수 없다는 점에 대표도 동의했다.

새 백엔드의 시작은 순조로웠다. 기존에 만들어 놓은 시드 프로젝트가 있었는데 여기에는 커버리지 100%의 통합 테스트와 약간의 유닛 테스트가 있었다. 이것을 복사해서 사용자와 인증과 같은 기본적인 기능을 쉽게 구현할 수 있었다. 물론 이 때 AI의 역할이 컸는데 시드 프로젝트에서 UsersService 같은 특정 서비스를 새 백엔드에 맞게 커스터마이징 하고 테스트도 그에 맞게 변경하는 일이 거의 자동으로 이루어졌다.

문제는 새 백엔드가 아니라 기존 프로젝트에 있었다. 대표가 원하는 바를 팀원들은 각자 해석해서 작업하고 대표는 결과물을 확인하고 원하던 것과 다르다고 수 차례 얘기한다. 대표와 팀원들은 지역적으로 분리되어 있었고 긴밀한 협의가 이루어지기 힘든 환경이었다. 대표와 두 명의 팀원을 이어줄 중간 관리가 필요했다.

처음에는 github의 프로젝트에 테스크를 등록하고 관리하도록 했다. 대표도 개발팀이 할 일을 테스크에 등록하고 개발팀도 테스크를 보고 작업 후에 결과나 공유할 정보를 댓글로 달도록 했다. 그러나 딱 하루만 제대로 돌아갔을 뿐 대표는 지금까지 해왔던 대로 요구사항을 다양한 채널로 전달했고 팀원들은 작업 결과를 테스크에 추가하지 않았다.

결국 구성원들이 이 개발 시스템에 적응할 때 까지 내가 직접 테스크 하나하나 관여해야 했고 새 백엔드 개발을 진행할 여유는 점점 사라졌다

--------------

이번 프로젝트에서 개발자들에게 가장 아쉬웠던 것은 기능을 적당히 구현한다는 것이다. 특히 개발팀장과 백엔드는 정도가 심했는데 대충 만들어 놓고 다 됐다고 보고하는 일이 빈번해서 만들어 놓은 것을 제거하고 다시 만들게 되는 번거로움을 여러차례 겪었다.

API를 만들어서 전달하고 버그가 발견되면 아무렇지 않게 생각한다. 버그가 있는 건 당연한 것이고 상대방에게 피해를 주는 행위라고 생각하지 않는 것 같다.

--------------

AI가 구현 비용을 낮춘다면 대학 교육도 프로그래밍 언어나 프레임워크의 사용법에서 한 단계 위로 올라가야 한다. 개발 방법론과 소프트웨어 아키텍처, 요구사항 분석, 검증과 운영처럼 프로젝트 전체를 판단하는 능력을 가르칠 필요가 있다.

그러나 이런 판단은 이론만으로 가르치기 어렵다. 다양한 규모의 프로젝트를 실제로 이끌고 실패와 운영을 경험한 교수자가 필요하지만, 그런 역량을 갖춘 대학은 많지 않을 것이다. 필요한 변화는 교육의 수직적 확장이지만, 현실에서는 기존 학과의 과목을 연결하는 수평적 확장이 더 빠르게 일어날 가능성이 크다. 소프트웨어 공학에 경제·디자인·건축 같은 다른 전공의 커리큘럼을 결합해 더 넓은 문제 영역을 다루는 방식이다.

이런 수평 확장 자체는 나쁘지 않다. AI 시대의 개발자는 구현뿐 아니라 도메인을 이해하고 문제를 정의할 수 있어야 하기 때문이다. 다만 소프트웨어 공학의 깊이를 갖추지 못한 채 영역만 넓히면, AI가 만든 결과를 판단하거나 책임지지 못하는 중계자만 양산할 수 있다.

더 큰 문제는 수평적 확장이 컴퓨터공학과의 정체성을 흐릴 수 있다는 것이다. 경제·디자인·건축을 이해하면서 AI로 소프트웨어를 만드는 것이 교육의 중심이 된다면, 굳이 컴퓨터공학과에서 4년을 배워야 하는지 의문이 생길 수밖에 없다. 각 전공이 자신의 도메인 지식 위에 AI 활용법을 더하는 편이 더 효율적으로 보일 수 있기 때문이다.

컴퓨터공학은 원래 프로그래밍 언어나 도구의 사용법만 가르치는 학문이 아니다. 컴퓨터공학과가 존재 이유를 유지하려면 수평적으로 영역을 넓히기 전에 다른 전공이 대신하기 어려운 깊이를 제공해야 한다. 알고리즘과 운영체제 같은 기초지식뿐 아니라 요구사항을 시스템으로 구조화하고, 아키텍처를 설계하며, 성능·보안·신뢰성을 검증하고, AI가 만든 결과를 책임질 수 있는 능력이다. 다른 학문과의 결합은 이 핵심 위에 놓여야 한다. 핵심을 세우지 못한 채 영역만 넓히면 융합이 아니라 정체성의 해체가 될 수 있다.

이 논리를 개인에게 적용하면 기술적 깊이가 없는 개발자 역시 존재 이유를 의심받게 된다. 구현 장벽이 높았던 과거에는 요구사항을 코드로 옮기는 능력만으로도 충분한 가치가 있었다. 그러나 AI가 그 변환 비용을 크게 낮추면 상황이 달라진다. 문제를 정의하는 일은 도메인 전문가가 더 잘하고, AI가 만든 결과를 설계하고 검증하는 일은 기술적 깊이를 갖춘 개발자가 더 잘한다.

기술적 판단 능력도 도메인에 대한 주도권도 없는 개발자는 그 사이에서 요구사항과 AI의 결과를 전달하는 중계자에 머문다. 그런데 AI가 가장 먼저 줄이는 것이 바로 이런 전달 비용이다. 결국 사라지는 것은 개발자라는 직업이 아니라, 구현 외에는 맡을 것이 없는 개발자의 자리일 가능성이 크다.
