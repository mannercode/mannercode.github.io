# 프로젝트 기술 위험 평가

가장 큰 위험은 프로젝트가 당장 멈추는 것이 아니라, 겉으로는 계속 기능이 추가되고 테스트도 통과하지만 결제·환불·입장 데이터의 신뢰성이 조금씩 무너지는 것이다.

현재 소스가 완전히 무질서한 상태는 아니다. 모든 공개 테이블에 기본 키와 행 단위 보안이 있고, 마이그레이션도 빈 데이터베이스에서 끝까지 적용된다. 주요 데이터베이스 함수에는 잠금과 멱등성 처리도 있다. 문제는 개별 방어는 많지만 시스템 전체의 상태 규칙을 보장하는 중심 구조가 없다는 점이다.

| 위험 | 영향 | 계속될 경우 |
|---|---|---|
| 결제·환불·입장 상태 충돌 | 매우 큼 | 돈은 환불됐지만 입장한 티켓, 리포트와 실제 상태의 불일치 |
| 특권 데이터베이스 접근 남용 | 매우 큼 | 누락된 권한 검사 하나가 다른 조직의 데이터 변경으로 연결 |
| 누적형 데이터베이스 구조 | 큼 | 변경할수록 컬럼·함수·보정 마이그레이션이 늘어남 |
| 테스트의 허위 신뢰 | 큼 | 테스트는 통과하지만 실제 동시성·외부 연동 장애에서 사고 발생 |
| 거대 파일과 중복 구현 | 큼 | 한 경로만 수정되고 다른 경로에는 결함이 남음 |
| 배포·복구 복잡성 | 큼 | 작은 데이터베이스 실수가 전체 서비스 장애와 수동 복구로 확대 |
| 기술 리뷰 부재 | 매우 큼 | 코드 양은 늘지만 전체 불변조건을 책임지는 사람이 없어짐 |

## 1. 금전과 입장 상태가 서로 다른 체계로 움직인다

환불은 다음과 같이 세 단계로 처리된다.

```text
데이터베이스 선점 → 외부 결제 취소 → 데이터베이스 확정
```

입장은 별도의 데이터베이스 함수에서 처리된다. 그러나 입장 쪽은 진행 중인 환불 선점을 확인하지 않고, 환불 확정 쪽은 이미 입장한 티켓인지 다시 검사하지 않는다.

이것은 발견된 한 건의 결함보다 더 큰 구조적 신호다. 티켓, 주문, 결제, 환불 요청, 입장 로그가 각각 상태를 가지고 있지만 허용되는 상태 전이를 한곳에서 강제하지 않는다.

계속되면 다음과 같은 희귀하지만 치명적인 사건이 반복될 수 있다.

- 환불 후 입장
- 입장 후 환불
- 외부 결제 시스템에서는 취소됐지만 내부 원장은 보류된 상태
- 주문 상태와 개별 티켓 상태의 불일치
- 고객 응대·정산·회계 리포트가 서로 다른 값을 표시하는 상황

발생 확률은 운영 데이터 없이는 계산할 수 없다. 그러나 한 번 발생하면 고객·운영사와 어느 기록이 맞는지 다투게 된다는 점이 문제다.

## 2. 권한 경계가 행 단위 보안보다 애플리케이션 코드에 의존한다

관리 및 운영 애플리케이션은 각각 100개가 넘는 테이블에 직접 접근하고, 행 단위 보안을 우회하는 특권 클라이언트도 광범위하게 사용한다. 따라서 실제 보안은 각 서버 작업의 사전 검사에 크게 의존한다.

데이터베이스 클라이언트에는 생성된 스키마 타입이 연결되지 않아 다음 문제도 컴파일 단계에서 충분히 잡히지 않는다.

- 존재하지 않는 컬럼
- 잘못된 데이터베이스 함수 인자
- 변경된 상태 값
- 반환 자료형 불일치

현재까지 사고가 없더라도 기능과 서버 작업이 늘수록 조직 범위 검사 한 줄의 누락이 데이터 격리 사고로 이어질 가능성이 누적된다.

## 3. 데이터베이스가 확장보다 누적에 가까워졌다

현재 최종 스키마에는 공개 테이블 222개와 공개 함수 301개가 있다.

특히 다음과 같은 특징이 확인된다.

- 중심 행사 테이블: 97개 컬럼, JSON 계열 컬럼 15개
- 주문 테이블: 58개 컬럼
- 검증되지 않은 제약 조건 23개
- 상태처럼 사용되지만 검사 제약이나 외래 키가 없는 텍스트 컬럼 다수
- 자식 방향 인덱스가 없는 외래 키 150개
- 유사한 목적을 가진 테이블과 로그의 병행 구조
- 동일 개념을 여러 세대의 필드로 표현하는 구조

이 방향이 계속되면 새 기능을 추가할 때 기존 구조를 정리하지 못하고 버전 필드, JSON 컬럼, 동기화 트리거, 호환 함수를 하나씩 더 얹게 된다. 결과적으로 다음 문제가 생긴다.

1. 어느 컬럼이 정본인지 불명확해진다.
2. 데이터를 수정할 때 여러 표현을 함께 갱신해야 한다.
3. 오래된 데이터에 제약 조건을 적용하기 어려워진다.
4. 쿼리 성능 문제를 해결하기 위한 인덱스가 쓰기 성능에 미치는 영향도 커진다.
5. 정상적인 구조 개선보다 과거 구조를 건드리지 않는 패치만 가능해진다.

## 4. 테스트 숫자가 실제 안전성을 과장한다

2,300개가 넘는 테스트가 통과하는 것은 긍정적이다. 그러나 상당수는 실행 동작이 아니라 다음을 검사한다.

- 소스 문자열의 존재 여부
- 호출문이 파일에 배치된 순서
- 설정 파일의 형태
- 정규식으로 확인한 마이그레이션 내용

반면 핵심 위험인 다음 영역의 검증은 약하다.

- 두 데이터베이스 세션의 실제 경합
- 환불과 입장의 교차 상태
- 외부 결제 취소 성공 후 내부 확정 실패
- 고객별 데이터 마이그레이션의 실제 대상 분기
- 실제 브라우저·보안 정책·스토리지 통합 흐름

기본 테스트 명령에서 빠진 테스트 파일도 있었고, 이를 별도로 실행했을 때 현재 구현과 맞지 않는 실패 테스트가 확인됐다. 즉 테스트가 실패하지 않는 것과 모든 테스트가 실행되는 것도 서로 다른 문제다.

계속되면 테스트 수는 늘지만 통과 결과가 실제 견고함으로 오해될 수 있다. 이는 코드가 적고 테스트가 부족한 상황보다 더 위험할 수 있다.

## 5. 수정의 파급 범위를 예측하기 어렵다

이미 수천 줄에 이르는 파일들이 존재한다.

- 생산 배포 스크립트: 약 4,100줄
- 운영 애플리케이션의 외부 판매 모듈: 약 1,900줄
- 행사 입력 화면: 약 1,800줄
- 장비 관련 API 서비스: 약 1,700줄

외부 결제와 티켓 전달 코드에는 애플리케이션 간 복제도 있다. 같은 결제 취소 기능이라도 경로에 따라 멱등 처리와 재시도 수준이 다르다.

이 상태에서는 어떤 문제를 수정해도 같은 기능의 다른 구현에 동일하게 적용됐는지 확인해야 한다. 계속될수록 수정 자체보다 누락 여부를 확인하는 비용이 더 커진다.

## 6. 고객별 작업이 전역 스키마 이력에 쌓인다

특정 고객의 좌석 활성화 작업은 대상 개수와 사후조건을 비교적 엄격하게 검사한다. 그러나 일부 외부 전송 설정과 할인 데이터 변경은 특정 식별자를 전역 마이그레이션에 직접 넣고, 대상이 없어도 조용히 성공한다.

고객별 작업이 이런 방식으로 계속 쌓이면 다음 문제가 생긴다.

- 새 환경에서 실행 결과가 환경마다 달라진다.
- 어떤 고객 데이터가 어느 마이그레이션에 의존하는지 찾기 어려워진다.
- 운영 데이터 수정과 스키마 변경의 경계가 흐려진다.
- 과거 고객 작업 때문에 전체 마이그레이션 체인을 영구적으로 유지해야 한다.

별도의 마이그레이션 체인을 만들 필요는 없지만, 고객 데이터 작업에는 대상 개수, 재현 가능한 입력 데이터, 사후조건을 일관되게 적용해야 한다.

## 7. 비개발자가 기술 변경을 단독 승인할 때의 위험

문제는 특정 개인의 코드 작성 여부보다 누가 시스템 불변조건을 책임지느냐다.

이 프로젝트의 기술 검토에는 단순한 화면 확인을 넘어 다음 판단이 필요하다.

- 외부 결제와 데이터베이스 사이의 분산 상태 처리
- 데이터베이스 잠금 순서와 동시성
- 행 단위 보안과 특권 접근의 권한 경계
- 단계적 마이그레이션 호환성
- 과거 데이터의 제약 조건 검증
- 결제·입장·정산 상태 전이

이 역량 없이 테스트 통과, 코드 형태, 예외처리 개수를 기준으로 승인하면 자동화 도구나 개발자가 만든 변경을 실질적으로 검증할 사람이 없다.

같은 방식이 지속되면 다음 과정이 예상된다.

1. 초기에는 기능 출시 속도가 빠르게 보인다.
2. 드문 상태 불일치와 수동 정산 건이 생긴다.
3. 사건마다 컬럼·함수·테스트가 추가된다.
4. 구조는 더 복잡해지고 테스트는 더 피상적으로 늘어난다.
5. 배포할 때마다 영향 범위를 자신할 수 없게 된다.
6. 정상적인 개선보다 장애 회피용 패치가 우선된다.

## 결론

현재 가장 시급한 것은 대규모 재작성보다 결제·환불·입장·정산의 상태 전이를 데이터베이스 수준에서 정의하고 실제 동시성 테스트로 강제하는 것이다.

그다음에는 다음 조치가 필요하다.

1. 특권 데이터베이스 접근 경계를 줄인다.
2. 데이터베이스 스키마 타입을 애플리케이션에 연결한다.
3. 모든 테스트가 자동 발견되고 정상 검증 관문에서 실행되도록 한다.
4. 고객별 데이터 작업에 대상 확인과 사후조건을 의무화한다.
5. 데이터베이스 구조가 더 증가하지 않도록 정리 기준을 세운다.
6. 핵심 기술 변경을 책임질 숙련된 기술 검토자를 지정한다.

이 통제가 없다면 프로젝트는 기능 부족으로 실패하기보다 돈과 입장 기록을 신뢰할 수 없어 운영 비용이 감당되지 않는 시스템으로 변할 가능성이 가장 크다.

## 평가 범위

이 문서는 최종 소스코드와 최종 데이터베이스 스키마만을 기준으로 작성했다. 버전 관리 이력, 작성자 정보, 운영 트래픽, 실제 기능 활성 상태, 장애 기록은 평가에 사용하지 않았다. 따라서 발견된 구조적 결함의 실제 발생 빈도는 별도 운영 데이터 없이는 판단할 수 없다.
