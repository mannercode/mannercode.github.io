## 1편 원고에서 남은 확인 사항

2026년 9월 26일 수정본의 편집 주석을 제거하면서 남긴 확인 항목이다. 이후 수정본을 정식 원고로 통합했다. 편집 결정은 [문장 검토 기록](./04_sentence_review.md)에 보존한다.

- **5.5 사례:** 저자가 제공한 [메시지 요금 차감과 발권 중단](./01_experiences.md#case-11-unused-features)을 반영했다. 구체적인 발생 시점·행사·시스템과 중단 시간, 복구 방법은 미확인이다. 안내 문자 기능 추가는 설명을 위한 가정으로 유지한다.
- **4.2 업무 배분:** 구체적인 지원·교육 내용, 네 앱에서 실제 처리한 범위, Android 개발자의 퇴사 이유는 확인되지 않았다. 업무량에 관한 저자의 판단을 상대방의 역량이나 퇴사 원인에 대한 결론으로 넓히지 않는다.
- **5.2 기술 선택과 성능:** Next.js·MongoDB 비교는 당시의 판단이라는 점이 확인됐다. 실제 비용 비교, 지연의 최초 발생 시점, 요청 종류와 반복 측정 결과, 자체 호스팅에서의 지연 구간, 교체 후 개선 효과는 미확인이다. RN 추천 당시 AI에게 전달한 조건과 답변의 전제도 따로 확인해야 한다.
- **5.4 배포 경위:** 당시 검증 범위와 완료 기준, 배포 결정권과 승인 과정은 더 확인할 수 있다. 공동 검증에서 누락을 놓친 사실과 저자가 비난받았다는 경험을 구분하며, 승인 절차가 없었다거나 전체 책임이 누구에게 있다는 새 판단을 덧붙이지 않는다.
- **5.5 이후 경과:** 롤백 이후 실제 운영 시스템, 새 시스템의 재배포 여부, 남은 문제, 의사결정·검증 방식의 변화는 미확인이다. Supabase 제거 작업이 진행 중이라는 사실을 재배포 완료나 갈등 해결로 확대하지 않는다.

## 2편 원고 검토 — 2026년 9월 27일

[2편 원고](../../ai_coding_part2.md)를 현재 1편, 경험·원칙 메모, DB 스키마 검토와 9월 4일 전체 검토 보고서에 대조했다. 제품 코드나 실제 운영 환경을 다시 검증한 작업은 아니다.

- **근거와 검증 범위:** 기본 단위 테스트 1,328개, 권한 검사 주석 처리 후 관련 테스트 21개 통과, 전화번호 검증 비활성화와 롤백 테스트 9개 통과 사례는 전체 검토 보고서와 일치한다. 주석에 숨겨져 있던 검증 범위를 본문에 드러내고, 결제 취소 사례는 코드와 호출 경로를 확인한 결과임을 밝혔다.
- **1편과의 연결:** 사라진 `scope-and-environment`, `april-focused-work` 앵커를 현재 1편 4.4절로 연결했다. 현재 1편에는 아홉 애플리케이션과 기존 사용자 앱 개발 중단을 설명하고 있어, 2편의 연결 문장도 특정한 다섯 영역 대신 당장 필요한 기능에 집중했다는 내용으로 정리했다. 과거 자료의 다섯 영역 분류 자체가 잘못됐다는 판정은 아니다.
- **주장의 범위:** 비개발자의 기술 선택이 틀릴 가능성이 크다는 표현을, 조건 전달과 추천 검토가 부족할 때 생기는 문제로 구체화했다. 문서·테스트 등 개발 절차의 기원을 모두 분업으로 설명하던 문장은 협업에서 수행하는 역할로 바꿨다. 과거 학생들의 학습 조건이 공평했다는 평가도 로컬 구현 연습의 반복 사용료 부담에 관한 설명으로 좁혔다.
- **개발자의 성장:** “AI 이상의 능력”, “통찰을 보여줄 때 비로소 의미가 있다”는 표현은 결과의 전제 검토와 대안 제시 능력을 기르는 내용으로 바꿨다. AI가 못한 판단을 개발자가 보탠다는 문제의식은 유지하며, 요구사항·실패 조건 정의, 설계 대안 비교, 테스트 검출력 확인, 변경과 실패를 통한 학습 방법을 기존 원칙 메모에서 보강했다.
- **결제 대안:** 경험 메모의 해결 방향을 바탕으로 요청 식별자 저장·반환, 서버의 주문·결제 ID 검증, 재시도 중복 방지를 구분했다. 실제로 수정·검증을 완료한 결과로 서술하지 않았다.
- **학생 실습비:** 저자는 이번 검토에서 “현재 기준으로 최소 100달러이고 200달러는 되어야 여유가 좀 생길 것 같다”고 설명했다. 월 15만 원과 월 200달러를 함께 제시하던 문장을 월 100달러 최소·월 200달러 정도면 사용량에 여유가 생길 것이라는 판단으로 정정하고, 연간 금액도 1,200~2,400달러로 맞췄다. 현재 사용 경험에 기댄 추정이며 검증된 교육비 기준은 아니다.

[Azure Speech 공식 문서](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-translation)의 음성 스트림 번역과 중간 결과 반환 설명을 확인했다. 이 기능의 존재가 당시 행사의 대상 언어·지연·번역 품질 요구까지 충족했다는 증거는 아니므로, 원고의 대안 검토 표현을 유지했다. 당시 사용 API와 실제 변경 결과는 여전히 미확인이다.

리팩터링의 테이블 증가 60개와 “3주치 토큰”은 저자의 회고로 유지했다. 비교 시점과 사용량 기준, 실제 구조 개선 완료 범위는 이번 검토에서도 확인하지 못했다.

## 2편 초안 정리 — 2026년 10월 26일

[2편 작업 원고](../../ai_coding_part2.md)를 「AI 코딩 이해하기: 검증과 설계, 개발자의 역할」이라는 제목의 초안으로 정리했다. 기존 여섯 가지 사례와 해결 방향을 유지하고, 개발 방법·개발자의 성장·학생 지원을 7~9장으로 이어 썼다. 어셈블리어 도입은 유지하며 줄였고, 빠른 성과와 만능감은 전문가 참여 절로 옮겼다. 동시번역의 기술 설명은 해당 사례에 모으고, 팀장의 역할 설명도 합쳤다.

이번에 대조한 자료는 현재 1편, 기존 2편 메모, 경험·원칙 메모, DB 검토 기록과 9월 4일 프로젝트 전체 검토 보고서다. 제품 코드와 운영 환경을 새로 실행한 검토는 아니다.

- **전체 검토 사례:** 기본 단위 테스트 1,328개 통과, 권한 검사 주석 처리 후 관련 테스트 21개 통과, 전화번호 검증 비활성화 후 7개 통과, 롤백 테스트 9개 통과 수치를 보고서와 대조했다. DB 함수의 소유자 권한 실행 설명을 보강했다. 격리 DB 재현·로컬 재현·코드 확인의 범위는 본문에 유지했다.
- **해결 방향:** 검증할 입력과 기대 결과를 표로 정리하고, 요청 식별·거래 확인·재시도 중복 방지·상태 재조회를 구분했다. 단말 검증 자동화와 DB 전환 완료 기준도 구체화했다. 모두 필요한 개선 방향이며, 실제 구현·검증·배포를 마친 결과로 서술하지 않았다.
- **기술 선택과 구조 개선:** 초기 선택에 필요한 조건을 설명하되, 전체 검토의 결함을 특정 스택 탓으로 돌리지 않았다. 검토서가 현재 스택에서 공통 인가와 주문·발권·환불 경로를 점진적으로 정리하도록 제안한 점을 반영했다.
- **동시번역:** [Azure Speech 공식 문서](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-translation)를 다시 열어 오디오 스트림 번역과 발화 중 중간 결과 반환을 확인했다. 당시 행사의 대상 언어·지연·품질 요구를 충족했는지, 실제로 방식을 변경했는지는 확인하지 않았다.
- **학생 실습비:** [공식 요금 문서](https://learn.chatgpt.com/docs/pricing)는 이번 확인 시점에 Pro 월 100·200·500달러 선택지를 안내한다. 본문의 월 100~200달러는 저자가 9월에 설명한 작업 규모와 사용 경험에 따른 추정으로 유지했다. 현재 가격 확인으로 9월의 요금·한도를 소급 검증한 것은 아니며, 학생 실습의 사용량을 측정한 교육비 기준도 아니다.
- **남은 확인:** 하루 약 100개 커밋, DB 테이블 60개 증가, 일주일 동안 “3주치 토큰” 사용은 저자의 회고다. 비교 시점과 범위, 토큰 사용량의 기준은 이번에도 확인하지 못했다. 테이블 수만으로 복잡도 악화를 입증하지 않도록 문장을 보완했다. 결제 식별자 누락으로 실제 취소가 발생했는지, 각 개선안을 어디까지 적용했는지도 기존 확인 항목으로 남긴다.

본문 말미의 집필용 사례 메모는 이곳으로 옮겼다. [PROJECT_REVIEW_2026-09-04.md](../../references/PROJECT_REVIEW_2026-09-04.md)는 비개발자가 AI로 만든 시스템을 전체적으로 검토한 자료이며, 구체적인 관찰과 증거 범위는 [사례 15](./01_experiences.md#case-15)에 정리돼 있다. 유효한 테스트와 안전장치가 있었지만 권한·결제·환불·복구 규칙이 모든 실행 경로에 연결되지는 않았고, 중요한 동작을 깨뜨려도 관련 테스트가 통과한 점을 다룬다. 검토일은 2026년 9월 4일이며, 실제 운영 사고나 수정 완료를 기록한 자료는 아니다.

## 2편 새 도입 검토 — 2026년 10월 28일

저자가 처음부터 다시 작성하는 [part2.md](../../part2.md)의 도입을 검토했다. 이번 검토 대상은 개발자의 고민, 갑자기 생긴 팀원 10명의 비유, 작업 목표와 추가 정보 수집에 관한 문단이다. 저자가 새 원고에서 제외한 기존 네 단계 설명은 복원하지 않았다.

- “빠르고 고품질의 코드”는 모든 결과의 품질을 전제하므로 코드 작성 속도에 관한 표현으로 좁혔다. 개발자의 고민도 무엇을 맡기고 어디까지 확인할지로 구체화했다.
- 고민의 원인을 “갑자기 생긴 큰 힘을 다루는 데 익숙하지 않기 때문”으로 단정하던 문장은, 그 힘을 활용하려면 일을 맡기는 방식도 살펴야 한다는 글의 논점으로 바꿨다.
- 제목에 맞춰 목표를 받고 도구로 작업하며 실행 결과를 다음 작업에 반영하는 에이전트의 동작을 짧게 설명했다. “일을 잘하는 개발팀원”이라는 비유는 유지했다.
- 목표를 몇 문장으로 전달하는 것과 그 문장에 작업에 필요한 모든 정보가 들어 있는 것을 구분했다. 사람이 기존 맥락을 활용하고 다른 관계자에게 물어 정보를 보충한다는 저자의 설명을 유지했다.
- “AI 에이전트는 다른 곳에서 추가 정보를 얻을 수 없다”는 주장은 수정했다. [Anthropic의 에이전트 설명](https://www.anthropic.com/research/building-effective-agents)은 검색·도구 사용과 실행 피드백, 필요한 정보나 판단을 사람에게 요청하는 방식을 설명한다. 도구로 정보를 얻을 수 있다는 사실이 조직의 모든 맥락을 알고 있다는 뜻은 아니므로, 접근 가능한 자료와 공유된 맥락을 확인해야 한다는 논점으로 정리했다.

공식 자료는 에이전트가 정보를 수집하고 질문할 수 있다는 기술 설명의 근거다. 개발자들이 고민하는 원인의 비중이나 모든 에이전트의 행동을 측정한 자료로 사용하지 않았다. 이번에는 제품 코드나 실제 프로젝트의 실행 결과를 새로 검증하지 않았다.

### 에이전트 설명의 확장 — 2026년 10월 28일

저자의 요청으로 [part2.md](../../part2.md)의 에이전트 설명을 작동 방식, 능력을 결정하는 조건, 장점, 한계의 네 절로 작성했다. 저자가 추가한 ‘AI 코딩의 이해’ 도입은 유지했다.

- [Anthropic의 에이전트 설명](https://www.anthropic.com/research/building-effective-agents)에서 도구 실행 결과를 활용하는 반복 작업과 사용자에게 정보·판단을 요청하는 방식을 확인했다. 특정 제품의 최신 기능이나 성공률을 설명하는 근거로 사용하지 않았다.
- [Anthropic의 맥락 관리 설명](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)에서 작업 중 필요한 정보를 검색하는 방식, 도구의 역할, 정보가 길어질 때 필요한 내용을 놓칠 수 있는 문제를 확인했다. 모델·정보·도구·환경의 네 구분은 본문 설명을 위한 편집상의 분류다.
- 오류 수정의 진행 순서와 구현·테스트가 같은 조건을 빠뜨리는 상황은 일반적인 설명용 예시다. 저자가 실제로 겪은 사건을 추가한 것이 아니며, 모든 에이전트가 같은 순서로 작업하거나 같은 실수를 한다는 주장으로 쓰지 않는다.

<a id="part2-reasoning-review-2026-10-28"></a>

### 에이전트의 논리력에 관한 문장 검토 — 2026년 10월 28일

저자는 새 원고에서 “그러나 논리력은 부족하다. AI 에이전트가 버그를 해결하는 것을 보면 인간 수준의 논리력을 가진 것처럼 보이지만 그건 단지 지식으로 축적된 경험일 뿐이다”라고 작성했다. 지식의 양과 판단의 정확성을 구분하려는 문제의식은 유지하고, 모든 버그 해결을 축적된 지식의 재현으로 설명하는 단정은 수정했다.

- [GSM-Symbolic 연구](https://arxiv.org/abs/2410.05229)는 평가한 모델들이 수학 문제의 수치 변경이나 불필요한 조건 추가에 영향을 받는 현상을 보고했다. 저자들이 제시한 ‘학습한 추론 단계의 재현’이라는 설명은 원인에 대한 가설이다. 이 결과로 모든 모델의 추론 능력 부재나 실제 버그 수정의 내부 원인을 확정하지 않는다.
- [DeepSeek-R1 연구](https://arxiv.org/abs/2501.12948)는 사전 학습한 모델에 사람의 추론 과정 예시를 직접 지도하지 않는 강화학습을 적용해 수학·코딩 등 검증 가능한 과제의 성능을 높였다고 보고했다. 이 결과 역시 인간과 동일한 사고 방식이나 모든 문제에 대한 일반화를 입증하지 않는다. 학습으로 얻은 능력이라는 사실만으로 새로운 문제에서의 추론을 부정할 수는 없다는 점을 구분했다.
- 본문은 개별 버그 해결의 성공이 복잡한 설계 전반의 판단을 보장하지 않으며, 가정이나 조건을 놓칠 수 있다는 설명으로 좁혔다. 연구에서 실제 프로젝트의 설계 능력이나 인간 개발자와의 우열을 측정했다고 쓰지 않는다. 이번에는 논문의 초록과 기존 집필 메모를 대조했으며, 모델을 직접 평가하거나 저자의 프로젝트 코드를 재검증하지 않았다.

이후 저자는 “추론 능력이 보기보다 떨어진다는 설명”이 필요하다고 집필 의도를 구체화했다. 현재 본문은 풍부한 지식과 능숙한 설명을 보고 기대하는 추론의 정확성과, 실제 판단에서 전제나 모순을 놓치는 문제 사이의 차이를 설명한다. ‘높게 평가하기 쉽다’는 표현은 이 글의 사용 경험을 해석하는 관점이며, 사용자의 과대평가 정도를 측정한 연구 결과로 제시하지 않는다. AI가 인간보다 항상 논리력이 낮다거나 추론이 모두 모방이라는 주장으로 확대하지 않는다.

<a id="part2-agent-characteristics-review-2026-10-28"></a>

### 에이전트의 특성과 작업 방식의 연결 — 2026년 10월 28일

저자가 장점·한계 목록이 피상적이라고 지적해, 가능한 작업의 나열을 줄이고 지식의 범위·실험에 드는 부담·병렬 실행이 작업 방식에 주는 영향을 설명하도록 고쳤다.

- 역할의 범위와 동작하는 초안을 보며 요구사항을 정한 경험은 [1편](../../../_posts/2026-09-20-ai-coding-part1.md)의 2.2~2.4와 5.3을 대조했다. 모든 프로젝트에서 같은 생산성 향상이 난다거나 특정 직군이 불필요해진다는 주장으로 쓰지 않는다.
- 리팩터링과 사후 검토가 근본적인 개선안으로 이어지지 못했다는 설명은 저자가 제공한 회고와 [기존 검토 기록](#refactoring-claims-review)에 근거한다. 이 사례는 현재 1편 본문에는 없으며, 이번에도 당시 모델의 입력·설정이나 프로젝트 코드를 다시 검증하지 않았다.
- 구현·테스트·설명 문서가 같은 가정을 공유하는 상황은 검증의 한계를 설명하기 위한 예시다. 특정 프로젝트에서 세 산출물을 대조해 원인을 입증했다는 의미가 아니다.
- [Anthropic의 맥락 관리 설명](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)에서 대화 압축과 외부 메모를 통한 맥락 유지를 확인했다. 에이전트가 기억할 수 없다거나 학습하지 못한다는 절대적인 한계로 서술하지 않았다.
- 병렬 작업과 조율의 관계는 [Anthropic의 다중 에이전트 사례](https://www.anthropic.com/research/multi-agent-research-system)도 참고했다. 본문의 검증 병목은 1편 4.4에 기록된 저자의 네 에이전트 운영 경험이며, 네 개가 보편적인 한계라는 뜻은 아니다. 외부 사례의 성능·토큰 수치를 코딩 생산성으로 옮기지 않았다.

이후 저자는 장점을 ‘여러 분야의 많은 지식, 빠른 구현·생성 속도, 목표를 향한 능동적인 실행’으로 정리했고, 한계도 같은 수준에서 다시 검토하도록 요청했다. 한계는 추론과 자기 검증, 유지할 수 있는 맥락, 목표 해석의 세 항목으로 바꿨다. 검증·통합의 부담과 네 에이전트 운영 사례는 개발자의 역할 중 ‘결과를 판단하는 방법’으로 옮겼다. 리팩터링과 사후 검토의 상세 경험은 이 도입 목록에서 덜어 내고 기존 집필 자료에 유지한다.

‘구조를 단순하게 만들라는 요청을 파일을 잘게 나누라는 뜻으로 받아들인다’는 문장은 목표 해석의 차이를 보여 주는 가정적인 예시다. 저자의 실제 리팩터링 지시나 당시 에이전트의 사고 과정을 재구성한 것이 아니다. 추론 실패에 관한 연구를 인간보다 항상 논리력이 낮다는 주장으로 확대하거나, 능동적인 작업이 반드시 목표 달성으로 이어진다고 서술하지 않는다.

[사례 메모](./01_experiences.md#case-11-translation) | 아예 말을 하지 않았거나 역할 확인도 하지 않은 것으로 서술하지 않는다. 행사 시점, 당시 사용한 API와 대상 언어, 이후 실제 변경 여부는 미기재다. 저자가 말한 품질 개선은 발언 종료 후 수동 전송을 발언 중 연속 전송·번역으로 바꾸는 동작 설계를 가리킨다. |

### 리팩터링과 AI 능력에 관한 주장 검토

2026년 9월 8일, 저자가 의견을 무비판적으로 반영하지 말고 타당성을 검토해 달라고 요청해 다음을 확인했다. 아래는 집필을 위한 검토 메모이며, 저자가 당시 수행한 분석이나 발언으로 옮기지 않는다.

- **이 사례가 뒷받침하는 범위:** 저자의 회고와 에이전트 검토에 따르면 수행된 리팩터링은 필요한 구조 개선에 미치지 못했다. 저자는 이후 검토를 맡긴 에이전트도 개선이 미미하다고 지적했지만 더 근본적인 방안을 제시하지 못했다고 추가 설명했다. 따라서 문제 진단을 근거로 전략 수립 능력까지 입증됐다고 해석하지 않는다. 처음의 전략이 부족했고 사후 검토도 근본적인 대안으로 이어지지 못했다는 비판은 이 경험으로 뒷받침되지만, AI 전반의 영구적인 능력 한계나 학습 데이터에 의한 원인까지 확정하지는 않는다. 당시 모델·입력·지침·실행 설정·계획과 완료 보고 전문, 후속 검토의 요청 범위는 확인하지 못했으며, 비용을 아끼려 했다는 원인도 입증되지 않았다.
- **규모와 속도:** 넓은 구조를 개선하는 전략과 작은 단계로 변경하는 방법은 함께 사용할 수 있다. 리팩터링의 목적은 이해와 변경을 쉽게 만드는 것이며, 작업량 자체가 성과의 기준은 아니다. 기능 생성 속도가 구조 악화로 이어진다는 설명에는 검토와 정리가 그 속도를 따라가지 못했다는 조건이 필요하다. 이 조건은 편집상의 인과 구분이며 해당 프로젝트에서 속도와 복잡도를 계량한 결과가 아니다. [Martin Fowler의 정의](https://martinfowler.com/bliki/DefinitionOfRefactoring.html)와 [작은 단계로 구조를 바꾸는 사례](https://martinfowler.com/articles/preparatory-refactoring-example.html)를 참고했다.
- **계획과 자기 검토:** GPT-4를 사용한 2023년 연구에서는 계획의 자기 비판이 성과를 악화시키고 잘못된 승인을 내는 문제가 보고됐다. 반면 2025년 공개된 다른 연구에서는 2024년 10월 모델들을 대상으로 Blocksworld·Logistics·Mini-grid의 계획 성능을 자기 비판으로 개선했다. 모델과 방법에 따른 결과를 구분해야 하며, 이 연구들로 2026년 특정 모델의 실제 프로젝트 설계 능력을 확정할 수 없다. [2023년 계획 검증 연구](https://arxiv.org/abs/2310.08118), [2025년 계획 개선 연구](https://arxiv.org/abs/2512.24103).
- **학습과 추론:** 학습으로 얻은 능력이라는 사실과 새로운 문제에서 추론할 수 있는지는 서로 다른 질문이다. DeepSeek-R1 연구는 사전 학습한 모델에 사람의 추론 과정 예시를 직접 지도하지 않는 강화학습을 적용해 수학·경쟁 프로그래밍 등 검증 가능한 과제의 추론 성능을 높였다고 보고했다. 이 결과는 인간 데이터의 단순 모방으로 모든 전략적 한계를 설명하기 어렵다는 근거이며, 실제 소프트웨어 아키텍처에서 인간보다 우월하다는 증거로 쓰지 않는다. [Nature 논문, 2025](https://www.nature.com/articles/s41586-025-09422-z).
- **GPT 6.0과 AGI:** 확인한 [GPT-6 Astra 공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-astra)와 [공식 모델 안내](https://developers.openai.com/api/docs/guides/latest-model)에서는 “AGI의 시작”이라는 주장을 확인하지 못했다. 이를 그런 발언이 어디에도 없었다는 뜻으로 확대하지 않는다. AGI 여부를 논하려면 발언 출처와 평가 기준이 별도로 필요하며, 이 프로젝트의 실패만으로 결론을 내릴 수 없다.

### 1편 대조 검토와 정정 — 2026년 9월 9일

저자가 과장·없는 발언·추측이 들어갔는지 전체 검토를 요청했고, 이어 감상적인 제목과 꾸민 문장도 줄여 달라고 했다. 경험담 원문, 통합 초안, 기존 원칙 초안과 현재 확인 가능한 대화 내용을 대조했다. 대화 전체의 원문을 빠짐없이 확인한 검토는 아니므로, 문서에 없는 내용의 출처까지 모두 판별했다고 할 수 없다. DB 전환과 9월 검토의 세부 내용은 각 검토 자료의 근거와 범위를 확인했다.

검토 과정에서 보관 문서에서 찾지 못한 내용을 AI의 추가로 단정해 삭제하는 오류가 있었다. 저자는 머메이드 그림을 직접 요청했다고 확인했다. 그림과 함께, 같은 이유로 삭제했던 시스템 분석 내용·백오피스 개발 당시의 기대·수면 중 행동도 복원했다. 뒤의 세 항목은 출처가 확인됐다는 뜻이 아니라, 삭제 근거가 부족해 기존 원고를 보존한 것이다.

참고자료에 같은 설명이 반복된다는 사실만으로 독립적인 근거가 늘어난 것으로 보지 않는다. 사건을 외부에서 입증하거나 제품 코드를 다시 검증한 작업도 아니다.

## 3. 문장 차이를 넘어 입장이 달라진 부분

단순한 중복으로 지우면 저자가 고민하던 논점까지 사라질 수 있어 별도로 남긴다. 특히 최근 2편 메모의 주장을 기존 통합본의 표현으로 덮어쓰지 않았다.

| 논점 | 초안별 차이 | 집필에서 정할 부분 |
| --- | --- | --- |
| AI보다 뛰어나야 하는가 | 통합본은 모든 기술을 AI보다 잘 알 필요가 없다고 설명. 최근 2편 메모는 “AI 이상의 능력”, AI가 생각하지 못한 논리와 통찰을 강조 | 기술 리더에게 필요한 우위가 개별 구현, 기술 판단, 문제 발견, 통합 중 무엇인지 구체화 |

| 주니어 비유 | 기존 초안은 유능한 주니어에 비유하며 능력·맥락·책임의 차이를 설명. 최근 메모는 팀원으로 표현 | “주니어”가 전달하려는 특성, 사람이 성장하며 책임을 축적하는 차이를 어디까지 설명할지 |

| 기술 자체는 중요하지 않은가 | 경험담 원문에는 한 줄도 코딩할 필요가 없다면 기술은 중요하지 않았다고 기록. 통합본은 당시 생각이 절반만 맞았다고 회고 | 당시 느낀 해방감과 이후 기술 판단의 필요성을 깨달은 경험을 연결할 근거 |
| 책임감과 성장 | 원문은 검증하지 않은 팀원의 태도를 강하게 평가. 통합본은 경험 부족과 책임 회피를 구분하고 회사의 육성 책임까지 확장 | 실제 행동·검증 기준·피드백을 바탕으로 인물 평가와 성장 문제의 범위를 정하기 |
| 개발자의 일자리 | 경험담 말미·통합본은 구현 외에 맡을 일이 없는 개발자의 자리가 줄 수 있다고 주장. 기존 README는 자기 범위에서 기술 리더 역할을 연습하는 데 집중 | 개인의 준비에 관한 주장과 채용·고용 전망을 구분해 어느 편에서 다룰지 |

2편 메모의 “AGENTS.md를 잘 쓰는 것과 개발자의 통찰은 다르다”는 문제의식도 유지한다. 이를 단순한 프롬프트·지침 작성 요령으로 바꾸지 않고, 어떤 공학적 판단이 필요했는지 사례와 연결할 수 있다.

## 4. 후속 글로 넓힐 수 있는 논점

### 기업과 주니어의 성장 경로

출처: 통합 초안 「주니어의 성장 경로를 다시 설계해야 한다」, 기존 원칙 초안 4.4와 후속 논점.

저자의 2026년 9월 16일 집필 의도: 최근 주니어의 업무 태도 때문에 가급적 채용을 피하고 싶다는 이야기를 자주 듣고, 왜 채용을 꺼리게 되는지 자신의 경험을 사례로 보여 주려 한다. 1편에서 팀원의 태도를 다루는 목적에는 일을 맡긴 뒤에도 검증과 수습을 다른 사람이 계속 떠안아야 했던 부담을 설명하는 것이 포함된다.

같은 날 저자는 몇 달 전 짧게 근무한 회사에서 만난 주니어와 지금도 연락하며, 어른스럽고 일을 맡기면 믿음이 가는 사람이라고 설명했다. 한편 최근 6개월 동안 만난 주니어 10명 중 자신 있게 추천할 수 있는 사람은 두 명 정도라고 평가했다.

- 잘 정의된 구현 업무가 회사에 대한 기여이자 학습 경로였다. AI가 이를 수행하면 입문자의 연습 기회와 채용 이유가 함께 줄어들 수 있다는 문제의식이다.
- 시니어가 직접 AI로 처리하는 비용보다 주니어에게 설명하고 결과를 다시 검토하는 비용이 클 때, 작은 스타트업의 채용이 어려워질 수 있다는 주장이 있다.
- 회사가 미래의 숙련자를 필요로 한다면 작은 기능의 요구사항부터 배포·운영·장애 회고까지 책임질 기회와 피드백을 제공해야 한다는 제안도 있다.
- 실제 채용 시장의 변화는 한 팀의 경험만으로 확정하지 않는다. 개인의 연습 방법은 [성장 원칙](./02_principles.md#principle-12)에 두고 제도·비용 문제를 여기서 확장할 수 있다.

### 역할 전환을 AI 코딩의 어려움과 연결한 자료

2026년 11월 4일 저자는 AI가 구현을 맡으면서 개발자의 역할이 달라지는 것이 어려움의 근본 원인이라고 설명하는 글이나 영상을 요청했다. 역할 변화의 전망만 제시한 자료보다, 전환 과정의 혼란·검토 부담·새 역량의 필요성을 직접 다룬 자료를 우선 확인했다.

- [Dave Bresci, 「Navigating the Shift to Agentic AI」](https://www.pagerduty.com/eng/navigating-the-shift-to-agentic-ai/), PagerDuty, 2026-05-07: 코드 작성에서 명세 작성으로 전환하는 데 AI에 긍정적인 개발자도 어려움을 겪는다고 설명한다. 직접 작성하지 않은 코드를 검토하는 부담과 코딩에서 얻던 만족의 변화도 다룬다. 엔지니어링 현장·라운드테이블에 기반한 해석이며, 어려움의 원인별 비중을 측정한 연구는 아니다.
- [Eirini Kalliamvakou, 「The new identity of a developer: What changes and what doesn’t in the AI era」](https://github.blog/news-insights/octoverse/the-new-identity-of-a-developer-what-changes-and-what-doesnt-in-the-ai-era/), GitHub, 2025-12-08: AI 활용 경험이 많은 미국 소프트웨어 엔지니어 22명의 인터뷰를 바탕으로, 구현에서 의도 정의·위임·검증으로 일의 중심이 이동하는 과정과 시행착오를 설명한다. 전체 개발자를 대표하는 표본이나 역할 변화의 인과 효과를 입증한 실험으로 해석하지 않는다.
- [Annie Vella, 「The Software Engineering Identity Crisis」](https://annievella.com/posts/the-software-engineering-identity-crisis/), 2025-03-21: 직접 만드는 일에서 조율·감독하는 일로 이동하는 변화를 자신의 관리직 전환 경험과 연결한다. 개발자가 코딩에 부여해 온 정체성과 만족의 변화를 중심으로 다룬 글이다. 이 관점이 모든 개발자의 설계 능력 부족을 뜻하지는 않는다.
- [Tech Lead Journal #223, 「The Software Engineer Identity Crisis in the AI-Driven Future」](https://techleadjournal.dev/episodes/223/), 2025-07-07: Annie Vella 인터뷰. 게시자가 제공한 목차와 전문에서 14:29 역할 변화, 38:51 개발자 정체성의 혼란 구간을 확인했다. 영상 자체를 재생해 검증한 것은 아니다. [YouTube 영상](https://www.youtube.com/watch?v=F5nz4miV4Fc).
- [「The Work Behind Delegation: A Framework for Supervising AI Coding Agents」](https://arxiv.org/abs/2609.24234), 2026-09-21 제출: 초록에서 숙련 개발자 19명의 관찰·작업 흐름도와 Reddit 논의를 활용해 AI 감독 업무를 분석했다고 설명한다. 확인 당시 심사 중인 사전 공개 논문이며, 이번에는 초록과 제출 정보를 확인했다.

이 자료들은 역할 전환이 어려움과 혼란을 설명하는 중요한 관점이라는 점을 뒷받침한다. AI 코딩의 모든 어려움이 역할 변화라는 단일 원인에서 비롯된다고 입증한 자료로 쓰지 않는다.

같은 날 저자는 추상적인 요구사항의 모델링과 프로젝트에 맞는 아키텍처의 구성·유지에는 설계 역량과 유연한 사고가 필요하며, 탑다운 개발 역량의 부족이 AI 코딩을 어렵게 한다고 설명했다. 2편 1.1에는 설계 역량이 부족할 때 작업 목표와 검증 기준을 구체화하지 못하고 수정을 반복하게 되는 경로를 반영했다. 다만 위 자료들은 개발자들의 탑다운 개발 역량이나 부족한 사람의 비율을 측정하지 않았으므로, “대부분의 개발자가 탑다운 개발 능력이 부족하다”는 일반화의 근거로 쓰지 않는다.

후속 그림 검토에서 저자는 비교할 대상을 설계만 검토·수정한 뒤 구현을 맡기는 흐름과, 설계부터 구현까지 맡긴 뒤 결과를 보며 반복해서 고치는 흐름으로 구체화했다. Top-down/Bottom-up이라는 설계 방향과 작업 목표의 명확성을 같은 기준으로 취급하지 않도록, 1.1의 제목과 설명을 구현에 앞서 설계를 구체화하는 역량에 맞췄다. 구현 전에 확인할 수 있었던 조건을 뒤늦게 추가하면서 생기는 재작업을 다루며, 탐색적 구현이나 피드백에 따른 설계 개선 전체를 비효율로 단정하지 않는다.

### AI 활용 요령과 기본기의 학습 우선순위

2026년 11월 4일 저자는 AI의 출력 품질을 높이는 하네스나 팁을 익히는 데 시간을 쓰기보다 기본에 충실해야 한다는 논점을 제안했다. 현재 2편 4.1에 학습 우선순위로 반영하고, 모든 하네스와 팁이 금방 구식이 되거나 비효율적이라는 일반화는 하지 않았다. [Anthropic의 하네스 개발 사례](https://www.anthropic.com/research/harness-design-long-running-apps)는 모델 변경에 따라 일부 절차를 제거했지만 계획·평가 등 도움이 되는 구성은 유지했다고 설명한다. 특정 환경의 개발 사례이며, 모든 활용법의 수명이나 기본기 학습 대비 투자 효과를 측정한 연구는 아니다. 하네스에 포함되는 테스트 실행·작업 관리와 특정 모델의 약점을 보완하는 요령을 구분해, 2장의 테스트 환경·자동화 권고와도 일관성을 유지한다.

### 대학 교육의 수직·수평 확장

출처: 경험담 원문 말미의 대학 교육 메모, 통합 초안 「대학은 무엇을 가르쳐야 하는가」와 「기술적 깊이를 바탕으로 영역을 넓힌다」.

- 수직 확장은 구현에서 요구사항·아키텍처·검증·운영·기술 리더십까지 판단과 책임의 범위를 넓히는 것이다.
- 수평 확장은 경제·디자인·건축 등 다른 도메인으로 문제 이해의 범위를 넓히는 것이다.
- 프로젝트의 전체 생애주기를 가르치려면 실제 개발·실패·운영 경험을 가진 교수자와 오래 유지되는 프로젝트가 필요하다는 주장이 있다.
- 대학이 이런 조건을 충분히 마련하기 어려워 기존 전공을 연결하는 수평 확장이 먼저 일어날 수 있다는 전망은 원문의 가설이다.
- 컴퓨터공학의 깊이를 갖추지 못한 채 도메인과 AI 활용만 가르친다면 각 도메인 전공에서 AI를 배우는 것과 차이가 무엇인지 묻게 된다는 문제의식이 있다. “정체성의 해체”라는 강한 표현도 이 논점에 포함된다.
- 원문은 알고리즘·자료구조·언어·운영체제·네트워크·DB라는 기반 위에 설계·성능·보안·신뢰성·운영 판단을 연결할 것을 제안한다. 대학의 현재 역량과 교육 성과는 별도의 근거가 필요한 부분이다.

2026년 11월 4일 저자는 대학이 소프트웨어 공학을 실제 프로젝트에 적용하는 경험을 충분히 제공하지 못하면, 졸업 후 인턴십이나 전문학원에서 이를 보완하는 경우가 늘 수 있다는 전망을 제시했다. 현재 2편 4.6은 필요한 교육, 이를 제공하기 위한 조건, 졸업 후 실무 교육의 역할을 구분한다. [SSAFY 공식 지원 안내](https://www.ssafy.com/ksp/jsp/swp/apply/swpApplyProcess.jsp)에서 대학 졸업자·졸업예정자를 대상으로 한 별도 교육 과정의 존재를 확인했다. 이 사실은 대학 교육의 부족이 수강 원인이라는 증거나 AI 도입 후 수요가 증가했다는 통계가 아니다. 인턴십 기회의 증감과 교육 효과도 확인하지 않았으며, 본문의 수요 확대는 대학에서 관련 경험을 충분히 제공하지 못할 경우의 전망으로 유지한다.

### 학생의 AI 학습 비용과 실습 기회

저자가 추가한 논점은 [2편 메모 「학생의 AI 학습에는 금전적 지원도 필요하다」](../../ai_coding_part2.md#student-ai-access)에 정리했다. 컴퓨터 구입 이후 반복 연습에 추가 사용료가 거의 들지 않던 조건과, AI를 충분히 사용하며 시행착오를 겪는 데 지속적인 비용이 드는 조건의 차이를 다룬다. 개인의 성장 방법에 더해 학교·기업 등의 학습 비용 지원을 논의할 수 있다.

저자는 2026년 9월 27일, 현재 기준으로 이런 실습에 월 100달러는 최소한 필요하고 월 200달러 정도면 사용량에 조금 여유가 생길 것 같다는 뜻이라고 정정했다. 이 설명이 이전의 월 15만 원 추정보다 우선한다. 여러 프로젝트의 개발과 분석·검토를 한 달 정도 함께 맡겨 본 경험에서 나온 판단이며, 필요한 사용량을 측정해 산출한 금액이나 검증된 학습 기준으로 서술하지 않는다.

상품 가격은 [OpenAI 공식 요금 안내](https://learn.chatgpt.com/docs/pricing)에서 2026년 9월 7일 확인했다. Pro 20x의 월 200달러라는 가격에 대한 출처로 인용하며, 그 정도 요금제의 사용량이 실습에 필요하다는 저자의 추정을 입증하는 자료로 사용하지 않는다. 과거의 공평성은 도구 비용과 반복 연습의 조건에 한정하며, 사용량이 많다는 사실만으로 학습 성과가 높아진다고 단정하지 않는다.

### 기획자·디자이너·비개발자의 역할

출처: 경험담 원문의 커뮤니케이션 비용·대표 사례, 통합 초안의 역할 경계, 기존 원칙 초안의 후속 질문. 최근 생각은 [2편 메모](../../ai_coding_part2.md)의 「비개발자는 처음의 선택을 검증하기 어렵다」를 참고한다.

- 기획 의도에서 동작하는 결과물을 빠르게 만들 수 있을 때 기획자·디자이너는 어떤 판단과 완료 기준을 맡는가?
- 백엔드·프론트엔드·UX가 책임 범위를 넓히는 일과 전문성의 필요성을 어떻게 함께 설명할 것인가?
- 비개발자도 첫 서비스를 만들 수 있지만, 어떤 조건을 고려해야 하는지 모르면 AI가 제안한 기술 스택과 도구를 평가하기 어렵다는 주장이 있다.
- 프로젝트가 커진 뒤 드러나는 운영·성능·연동·변경 비용과 초기 선택을 연결해 설명할 수 있다.
- [프로젝트 전체 검토 자료](../../references/PROJECT_REVIEW_2026-09-04.md)가 추가됐고, [사례 15](./01_experiences.md#case-15)에 관찰과 증거 범위를 정리했다. 저자가 5월 초에 처음 본 뒤 약 네 달이 지난 9월 초에 검토한 자료라고 확인했다. 격리 환경 재현과 코드 검토를 실제 운영 사고나 수정 완료로 확대해 쓰지 않는다.
