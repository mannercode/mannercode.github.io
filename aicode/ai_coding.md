# AI 코딩을 대하는 개발자의 자세

## 들어가며

C를 본격적으로 공부하기 시작한 것은 1995년 무렵이었다. 당시에는 “프로그래밍을 제대로 알려면 어셈블리어를 알아야 한다”는 말을 종종 들었다. 실제로 C 코드 사이에 어셈블리어가 섞여 있는 소스도 심심찮게 볼 수 있었다.

그래서 어셈블리어를 잔뜩 설명해 놓은 책에도 도전했다. 그러나 GW-BASIC 정도밖에 모르던 내게는 무슨 말을 하는지 이해하기 어려웠다. 더하기 한 번을 하는 데도 왜 값을 레지스터에 넣었다가 다시 꺼내야 하는지부터 납득되지 않았다.

결국 책을 끝까지 읽지 못했다. 그때 도전했던 책은 30년이 지난 지금도 구석 어딘가에 잠들어 있다.

![당시 도전했던 『마이크로소프트 매크로 어셈블러 바이블』](./scm544242603556.jpg)

어셈블리어를 알았다면 하드웨어의 동작과 C 코드가 기계에서 실행되는 방식을 더 깊이 이해할 수 있었을 것이다. 성능이 중요하거나 하드웨어를 세밀하게 제어해야 하는 상황에서도 도움이 됐을 것이다.

하지만 어셈블리어로 범용 애플리케이션을 개발하기에는 생산성이 너무 낮았고 이식성과 유지보수에도 불리했다. C와 컴파일러가 발전하면서 개발자는 모든 명령을 직접 작성하지 않고도 더 많은 일을 빠르게 구현할 수 있게 됐다. 어셈블리어는 사라지지 않았지만, 대부분의 개발자가 매일 직접 다루는 작업에서는 한 단계 아래로 내려갔다.

그 뒤에도 컴파일러가 만든 코드를 믿지 못하거나, 제대로 된 프로그램은 어셈블리어로 직접 작성해야 한다고 생각하는 개발자들이 있었다. 특정 영역에서는 타당한 태도였지만, 모든 애플리케이션을 그렇게 개발하기에는 생산성 차이가 너무 컸다.

30여 년이 지난 지금, AI 코딩을 둘러싼 반응에서 비슷한 기시감을 느낀다. AI가 작성한 코드는 믿기 어렵고, 직접 작성해야만 제대로 이해할 수 있다는 이유로 AI 도입을 주저하거나 제한적으로 사용하는 개발자들이 있다. 이런 우려에는 근거가 있다. AI는 그럴듯하지만 잘못된 코드를 만들 수 있다.

물론 컴파일러와 AI는 전혀 다르게 동작한다. 컴파일러는 형식 언어로 작성된 소스를 정해진 규칙에 따라 변환하지만, AI는 자연어 요구와 프로젝트 맥락을 바탕으로 결과를 생성한다. 그 결과가 개발자의 의도를 보존한다는 보장은 없으므로 별도의 검증이 필요하다. 테스트가 통과했다는 이유만으로 요구사항을 충족했다고 단정해서도 안 된다.

둘이 닮은 점은 작동 방식이나 신뢰성이 아니다. 개발자가 모든 구현 세부를 직접 작성하지 않고도 더 넓은 문제를 다룰 수 있게 한다는 점이다.

여기서 말하는 AI 에이전트는 채팅창에서 코드 조각만 답해 주는 도구가 아니다. 프로젝트 저장소를 탐색하고 파일을 수정하며, 명령을 실행해 빌드와 테스트 결과까지 확인한다. 새로운 기술을 조사하고 요구사항을 정리하며, 설계안과 코드, 테스트, 문서도 작성한다.

나 역시 2025년 말까지는 코딩을 직접 주도하고 AI에는 검토와 보완을 주로 맡겼다. AI가 작성한 코드를 내가 직접 작성한 코드만큼 신뢰하기 어려웠기 때문이다.

그러나 2026년 초부터 AI 에이전트를 실제 프로젝트에 본격적으로 적용하면서 생각이 달라졌다. AI에게 구현의 상당 부분을 맡기고 내가 요구사항과 방향을 정한 뒤 결과를 검증하는 방식으로도 개발을 진행할 수 있었다. 무엇보다 직접 모든 코드를 작성할 때보다 내가 동시에 다룰 수 있는 문제의 범위가 크게 넓어졌다.

AI에는 여전히 분명한 한계가 있다. 잘못된 전제를 바탕으로 멀쩡해 보이는 코드를 만들거나 프로젝트 전체의 맥락을 놓칠 수 있고, 결과를 검증하는 데도 비용이 든다. 그럼에도 실제 프로젝트에서 체감한 생산성 향상은 이런 한계와 검증 비용을 감수할 가치가 있을 만큼 컸다.

AI와 어떻게 일할 것인가. 무엇을 맡기고 무엇을 직접 판단할 것인가. AI가 만든 결과를 어떻게 검증하고, 그 결과에 대해 누가 책임질 것인가.

이 글은 7개월 동안 AI 에이전트와 함께 프로젝트를 진행하며 이 질문들에 대한 답을 찾아간 경험담이다.

## 출시 6주 전, 프로젝트에 합류하다

2026년 1월, 나는 팀장 한 명과 팀원 두 명으로 구성된 개발팀에 합류했다. 팀은 미술관에서 사용할 이벤트·티켓 서비스를 개발하고 있었고, 정식 운영까지 남은 기간은 불과 6주였다.

합류 직후 가장 먼저 프로젝트의 진행 상황과 시스템 구성을 파악했다. 당시 개발팀이 담당하던 제품과 구현 방식은 다음과 같았다.

| 구성 요소 | 당시 구현 형태 |
| ------- | ------------------------------------------------ |
| 서비스 백엔드 | Java |
| 입장 키오스크 | iOS 네이티브 앱 |
| 발권 키오스크 | Android 앱에서 서버가 JSP로 렌더링한 웹 화면을 표시 |
| POS | Android 네이티브 앱 |
| 사용자용 앱 | iOS와 Android 네이티브 앱으로 각각 개발 |
| 백오피스 | JSP로 화면과 서버 로직을 함께 구현한 별도 애플리케이션. 서비스 백엔드와 DB 공유 |

인력 구성도 불안정했다. 팀장이 퇴사를 앞두고 있어 서비스 백엔드는 주니어 개발자 한 명이 사실상 전담하고 있었다. 다른 팀원 한 명은 사용자용 iOS 앱뿐 아니라 Android 기반 발권 키오스크까지 담당하고 있었다. 사용자용 Android 앱은 팀장이 직접 개발하고 있었지만, Android 개발 경험은 이번 프로젝트가 처음이었다.

시스템 구성을 살펴보면서 가장 먼저 확인한 문제는 제품별 기술과 개발 방식이 지나치게 분산돼 있다는 점이었다.

사용자용 앱은 iOS와 Android 네이티브로 각각 개발되고 있어 동일한 기능을 두 번 구현하고 검증해야 했다. 입장 키오스크는 iOS, 발권 키오스크와 POS는 Android로 구성돼 전용 단말조차 하나의 개발·배포 체계로 관리하기 어려웠다.

발권 키오스크는 Android 앱 내부에서 JSP 화면을 표시하는 구조였다. 하나의 기능을 수정하려면 Android 앱과 서버 화면을 함께 확인해야 했고, 문제가 발생했을 때도 앱과 서버 양쪽을 오가며 원인을 추적해야 했다. 백오피스는 JSP로 화면과 서버 로직을 함께 구현한 별도 애플리케이션이었지만, 서비스 백엔드와 동일한 DB를 직접 사용하고 있었다. 이 때문에 한 시스템의 변경이 다른 시스템에 미치는 영향을 통제하기도 어려웠다.

세 명뿐인 개발팀이 서로 다른 기술로 구현된 여러 제품을 동시에 개발하고 운영해야 하는 상황이었다. 제품별 기술 선택은 분산돼 있었고, 팀 전체가 공유하는 개발 기준이나 출시 이후의 운영 계획도 명확하지 않았다.

남은 6주 안에 모든 기능을 완성하는 것만으로는 부족했다. 실제 현장에서 안정적으로 운영할 수 있는 구조를 만들어야 했다. 일정 지연과 운영 장애 가능성이 모두 높은 상태였기 때문에, 상황을 파악한 첫날부터 우선순위를 다시 정하고 즉시 작업에 착수했다.

### AI 에이전트로 프로젝트를 분석하다

그날 밤부터 AI 에이전트를 활용해 프로젝트를 구체적으로 파악하기 시작했다.

AI에게 구현된 REST API를 목록으로 만들고 기능별로 분류하게 했다. 그런 다음 각 API가 어떤 역할을 하는지 분석하게 하고, 이해하기 어려운 요청 인자가 나오면 관련 코드를 추적해 용도를 확인하게 했다. 서비스에 어떤 기능이 구현돼 있고 서로 어떻게 연결되는지에 대한 전체적인 윤곽을 파악하는 데 하루가 걸렸다.

물론 그날 얻은 분석이 모두 정확했던 것은 아니다. 이후 실제 개발을 진행하며 다시 확인해 보니, AI가 구현된 것으로 파악한 API 중에는 개발하다 중단된 것도 있었고, API의 이름을 바탕으로 추정한 용도가 실제 동작과 전혀 다른 경우도 있었다. 그럼에도 짧은 시간 안에 전반적인 기능을 파악하는 데는 충분히 큰 도움이 됐다. 같은 수준의 분석을 기존 방식으로 진행했다면 아마 일주일은 필요했을 것이다.

조사 결과 백엔드에는 많은 기능이 구현돼 있었다. 그러나 DB 스키마와 REST API의 구조와 이름만으로는 각 요소의 역할과 연결 관계를 파악하기 어려웠다. 일부 API에는 별도의 암호화·복호화 로직이 들어가 있었지만 적용 기준이 일관되지 않았고, 같은 종류의 데이터도 API에 따라 처리 방식이 달랐다. 다른 시스템과 연동하거나 문제의 원인을 추적하기 어려운 구조였다.

사용자용 앱은 Android와 iOS 네이티브 코드베이스로 나뉘어 있었다. 같은 기능과 화면을 플랫폼별로 따로 구현하고 테스트해야 했기 때문에 작은 팀이 감당해야 할 작업도 그만큼 늘어났다. 키오스크와 POS 역시 실제 운영을 위한 완성품이라기보다 각 기능의 동작 가능성을 확인하기 위한 시제품에 가까웠다.

그렇다고 아무것도 동작하지 않는 것은 아니었다. 개별 화면과 API는 동작했기 때문에, 기능 단위의 시연만으로는 프로젝트가 마무리 단계처럼 보였다.

하지만 데모가 가능한 것과 실제 서비스를 운영할 수 있는 것은 달랐다. 사용자가 처음부터 끝까지 서비스를 이용할 수 있도록 기능들이 연결돼 있지 않았다. 출시를 앞둔 하나의 제품이라기보다 여러 시제품이 한 프로젝트 안에 모여 있는 상태에 가까웠다.

개발팀장은 2월 출시에 필요한 작업을 자신이 마무리하겠다고 했다. 그러나 나는 기존 시스템만으로 6주 뒤 서비스를 안정적으로 운영하기는 어렵다고 판단했다. 개발팀장의 의지와는 별개로, 일정 안에 실행할 수 있는 대응책이 필요했다.

### AI 에이전트로 백오피스를 다시 만들다

기존 시스템에 대한 1차 분석을 마친 뒤, 나는 프로젝트 전체 일정과 출시 범위를 관리하는 한편, JSP로 개발된 백오피스를 Next.js로 다시 만들기로 했다. 이유는 크게 세 가지였다. 우선 백오피스는 전체 구성 요소 가운데 완성도가 가장 낮았다. 또한 화면과 서버 로직이 뒤섞인 기존 JSP 구조는 기능을 빠르게 추가하기 어려웠고, 이후 유지보수에도 불리했다. 더 많은 기능이 쌓이기 전에 교체하는 편이 낫다고 판단했다. 서비스 백엔드와 백오피스가 동일한 DB에 각각 직접 접근하는 구조도 정리할 필요가 있었다.

내가 마지막으로 백오피스를 직접 개발한 것은 2년 전이었다. 당시에도 Next.js를 사용했으며, 개발 속도를 높이기 위해 React UI 컴포넌트 라이브러리인 MUI 기반의 유료 템플릿을 구매해 사용했다.

그러나 AI 에이전트로 백오피스를 개발해 보니, 과거에는 효율적이라고 생각했던 템플릿 수정 방식조차 상대적으로 비효율적으로 느껴졌다. 필요한 메뉴와 각 화면에 보여 줄 데이터를 간략히 설명하면, AI 에이전트는 그 요구를 바탕으로 백오피스의 기본 구조와 주요 화면을 빠르게 구현했다.

급박한 일정에서 백오피스의 시각적 완성도는 고려 대상이 아니었다. 그럼에도 결과물은 별도의 유료 템플릿이 필요 없을 만큼 완성도가 높았다.

### AI에게 맡기고 검토하지 않다

백오피스 개발은 순조로웠다. 백엔드 API 연동을 시작하기 전까지는.

백엔드를 담당한 개발자는 경력 3년 차였다. 경험은 많지 않았지만 그동안 요구사항을 곧잘 구현했기 때문에, API 개발도 무리 없이 맡길 수 있다고 생각했다.

나는 백오피스에 필요한 API를 요청하고 연동을 시작했다. 그러나 과정은 매끄럽지 않았다. 구현됐다는 API를 호출하면 동작하지 않았고, 수정했다는 말을 듣고 다시 확인하면 또 다른 오류나 누락이 드러났다. 하나의 API를 연동하는 과정에서 세 차례나 문제가 반복되자, 이 방식으로 연동 작업을 계속하는 것은 무리라고 판단했다.

나는 백엔드 개발자에게 AI가 만든 코드를 직접 검토했는지 물었다. 돌아온 답은 충격적이었다. 구현 결과를 검토하지 않았을 뿐 아니라, AI가 설계한 API조차 확인하지 않았다. 백엔드 개발자가 한 일은 내가 전달한 요구사항을 그대로 AI 에이전트에 입력하고, 에이전트가 작업을 완료했다고 답하면 그 말을 나에게 전달하는 것이 전부였다.

그 답을 듣고 나자, 나는 그에게 개발 업무를 계속 맡겨도 되는지 의문을 품기 시작했다.

왜 이런 일이 발생했을까?

내가 내린 결론은 책임감과 검증 능력이 모두 부족했다는 것이었다. 경험이 부족한 개발자에게 AI가 만든 API를 검토하는 일은 쉽지 않다. 요구사항부터 API 설계, 정상 동작과 예외 상황까지 하나씩 따져봐야 하기 때문이다. 경험으로 빠르게 판단할 수 없다면 그만큼 더 많은 시간과 집중력을 들여야 한다. 긴장되고 피곤한 작업이지만, 바로 그것이 개발자가 해야 할 일이다.

그 과정을 생략한 채 AI의 완료 보고만 전달한다면, 구현만 AI에게 맡긴 것이 아니라 개발자가 수행해야 할 판단과 검증의 의무까지 AI에게 떠넘긴 셈이다.

이것은 엄청난 비효율이었다. 나는 개발자에게 요구사항의 배경과 의도, 구현 방향과 주의사항을 설명하는 데 많은 시간을 썼다. 그러나 정작 개발자는 그 내용을 바탕으로 판단하거나 결과를 검증하지 않았다. 내 요구사항을 AI 에이전트에 전달하고, AI의 완료 보고를 다시 나에게 전달했을 뿐이다.

그 과정에서 요구사항의 의도는 구현에 제대로 반영되지 않았고, 나는 아무런 판단도 더하지 않는 중계자를 이해시키는 데 시간을 쓰고 있었다. 그렇다면 차라리 내가 직접 AI 에이전트에게 일을 맡기는 편이 더 효율적이지 않을까?

더 경악스러웠던 것은 하나의 애플리케이션에 AI 에이전트를 서너 개씩 동시에 투입하고 있었다는 사실이었다. 기존 기능이 반복해서 깨지고 매출 통계가 계속 맞지 않아, 작업 방식을 확인하던 중 알게 됐다.

여러 에이전트를 동시에 사용하는 것 자체가 문제는 아니다. 작업 범위와 변경 사항을 분리하고 각 결과를 검토한 뒤 통합한다면 병렬 개발의 효과를 얻을 수 있다. 그러나 그는 작업 간 충돌과 회귀 오류를 통제할 방법도 없이 여러 에이전트가 같은 애플리케이션을 동시에 수정하게 하고 있었다.

이런 방식은 토큰을 불필요하게 소모했을 뿐 아니라, 충돌과 오류를 확인하고 다시 수정하는 데 다른 개발자들의 시간까지 계속 낭비하게 했다.

이후에도 그가 다른 개발자와 키오스크 연동을 진행하면서 같은 API를 여러 차례 다시 만드는 모습을 보았다. 프로젝트가 급박한 상황이라 그때마다 깊이 개입할 여유는 없었다. 그러다 그가 한 말이 결정적이었다.

“큰 회사에서도 기획자들이 몇 명이 붙어서 검증해도 완벽하기 어려운데, 이 작은 회사에서 어떻게 팀장님 기준에 맞출 수 있겠어요?”

내가 요구한 것은 완벽함이 아니었다. 구현을 완료했다고 보고하기 전에 요구사항을 확인하고, API가 실제로 동작하는지 테스트하라는 것이었다. 오류가 발생할 수 있다는 사실과 검증을 생략해도 된다는 것은 전혀 다른 문제였다.

그 말을 듣고 나는 그가 단순히 경험이 부족한 것이 아니라, 자신이 완료했다고 보고한 결과물을 검증하는 일을 개발자의 의무로 받아들이지 않는다고 판단했다. 그는 팀에 기여하지 못했을 뿐 아니라 다른 개발자의 발목까지 잡고 있었다. 프로젝트가 급박했지만, 남겨 둘 이유는 없었다. 미련 없이 다음 날 해고를 통보했다.

### AI를 쓰면서도 과거의 기준으로 판단하다

3월 초, 서비스는 가까스로 출시됐다. 같은 시기 iOS 개발자의 계약이 끝나면서, 그가 맡던 iOS 키오스크와 사용자 앱을 새로 채용한 Android 개발자에게 맡기기로 했다.

처음 이야기를 꺼냈을 때 그는 강하게 거부했다. 이미 Android 키오스크와 사용자 앱을 담당하고 있는데, iOS 키오스크와 사용자 앱까지 어떻게 맡느냐는 것이었다. 예상했던 반응이었다. 기존 방식으로 생각하면 한 사람이 네 개의 애플리케이션을 관리하는 것은 결코 가벼운 일이 아니었다.

그러나 AI 에이전트를 전제로 하면 업무량을 계산하는 방식이 달라진다. 개발자가 모든 코드를 직접 작성하는 대신, 요구사항을 정리해 에이전트에게 전달하고 결과를 검증하는 일이 중심이 된다. 플랫폼별 문법과 프레임워크의 세부를 모두 숙달해 직접 구현해야 하는 부담도 크게 줄었다.

iOS와 Android라는 플랫폼의 차이는 있었지만 구현해야 할 기능은 대부분 같았다. 구현 자체는 AI 에이전트가 매우 빠르게 처리했기 때문에, 실제 병목은 사람이 요구사항을 파악하고 결과를 검증하는 단계로 옮겨갔다. 물론 플랫폼별 빌드와 배포, 권한 처리처럼 고유한 문제까지 사라진 것은 아니었다. 처음부터 크로스 플랫폼으로 개발했다면 더 좋았겠지만, 네이티브 앱이 네 개라고 해서 기존 방식에서 예상하는 네 배의 부담이 생기는 것은 아니었다.

이런 차이를 차분히 설명하자 그도 내 판단을 받아들였고, 원만하게 업무를 맡길 수 있었다.

개발 환경이 크게 달라진 만큼, 그동안의 경험을 바탕으로 형성된 판단 기준도 새로운 환경에 맞게 갱신해야 한다.

이것은 한 사례에 불과하지만, AI 에이전트를 효과적으로 활용하는 데 필요한 능력은 직접 구현하는 능력과 조금 달랐다. 내가 지켜본 범위에서는 주어진 일을 직접 처리하는 데 익숙한 개발자보다, 업무를 정의하고 나누어 맡긴 뒤 결과를 검토해 온 사람이 AI 에이전트에 더 빠르게 적응했다. 팀장이라는 직급 때문이라기보다, 평소 일을 위임하고 검증해 온 경험의 차이에 가까웠다.

그 외에도 구체적인 내용은 기억나지 않지만 Android 개발자에게 AI 코딩 방식에 적응할 것을 몇 번인가 요구했었는데 그게 무리라는 것은 당시에도 알고 있었다.

단지 새로운 도구의 사용법을 익히는 정도가 아니라, 사고의 전환이 필요한 일이기에 충분한 시간이 필요했을 것이다. 그러나 이미 여러차례 시행착오를 겪은 작은 스타트업에 개인의 사정을 기다려줄 만한 여유는 없었다.

그래서였을까. 수습 평가를 앞두고 Android 개발자가 퇴사하게 된다.

### AI 에이전트로 1인 개발을 시작하다

Android 개발자가 퇴사 의사를 밝혔을 때, 차라리 잘됐다는 생각이 들었다. 팀원들에게 업무의 맥락과 의도를 설명하고, 진행 상황을 조율하고, 전달 과정에서 어긋난 결과를 다시 수정하는 비용은 당시 상황에서 너무 컸다. 그리고 개발자는 감정을 갖고 있기에 일주일에 몇 시간은 잔소리/조언/상담으로 시간을 보내야 했다. 이런 모든 시간을 고려하면 사람을 거치지 않고 내가 직접 AI 에이전트에 업무를 맡긴 뒤 결과를 검증하는 편이 더 효율적일 것 같았다.

나는 대표에게 퇴사자의 공백을 메우지 않고 1인 개발 체제로 운영하는 편이 좋겠다고 말했다. 그때는 몰랐지만, 대표는 개발팀이 무너져 사업을 접어야 하는 것은 아닌지 고민했다고 한다. 그러나 개발팀은 건재했다. 우수한 팀장(나)과 성실한 팀원들(AI 에이전트)이 있었기 때문이다.

진행되던 프로젝트를 모두 떠맡게 됐을 때 github의 저장소는 백엔드/안드로이드 키오스크/ios 키오스크/안드로이드 키오스크의 백엔드(JSP)/안드로이드 pos/android 사용자 앱/ios 사용자 앱/백오피스 등 8개 정도였다. 여기에 부산에서 열리는 이벤트를 위한 별도의 프로젝트가 있었고 flutter로 새로 개발 중인 사용자 앱이 있었다.

이런 상황에서 내가 제일 먼저 한 일은 개발환경을 구축하는 것이었다. flutter/부산이벤트는 내가 계속 진행하던 것이어서 그대로 두고 떠맡게 된 8개의 저장소는 웹과 안드로이드로 구분해서 2개의 모노레포로 구성했다. 모노레포로 모아놓으니 에이전트에게 일을 맡기기 수월했다.

마음 같아서는 2개가 아니라 1개에 모두 넣고 싶었지만 웹은 vscode로 실행과 검증을 하지만 안드로이드는 안드로이드 스튜디오를 사용해야 했기 때문에 1개로 합치는 것은 좋지 않다고 판단했다.

그렇게 일주일 정도의 시간이 흐르고 새로 구축한 개발 환경에 익숙해지자 확신할 수 있었다. 일정 규모까지는 혼자 개발하는 것이 생산성이 훨씬 높았다. 일정 규모라는 것이 애매한 표현인데 이것은 개발자의 역량에 따르는 것 같다. 뒤에서 자세히 얘기하겠지만 소프트웨어 공학 지식이 탄탄하고 개발 방법론에 능숙하다면 더 큰 규모의 프로젝트도 혼자 감당 가능할 것 같다.

그렇게 개발환경을 구축하고 백엔드 개발자가 해결하지 못한 부정확한 통계 문제를 포함하여 2월 말에 서비스 런칭 후 나온 대부분의 중요 요구사항을 모두 처리할 수 있었다. 이 때가 4월 초였을 것이다.

시간이 흘러 위기를 넘긴 지금, 대표는 AI 에이전트들을 ‘클 이사’와 ‘코 부장’이라 부르며 모시고 있다. 당분간은 개발자를 추가로 채용하지 않아도 되겠다는 것이 나와 대표의 판단이다.

### AI 에이전트로 비개발자가 개발을 시작하다

중요 문제가 마무리 되고 드디어 품질 개선에 힘을 쏟을 여유가 생겼다고 기뻐하려던 첫 날 대표가 조심스럽게 말을 꺼내기 시작한다. 싸늘했다. 가슴에 비수가 꽂히는 것 같았다. 이건 분명 안 좋은 신호였다. 뭘까? 대표는 무슨 아쉬운 얘기를 하려는 걸까?



--------------

이미 상당한 기능이 구현된 상황에서 별도의 개발이 필요하다고 설득하는 일은 쉽지 않다. 나는 AI가 정리한 분석 결과를 바탕으로 기존 시스템에서 마무리할 부분과 별도로 만들어야 할 부분을 나눠 설명했다. 내가 기존 개발에 뒤늦게 합류해 몇 가지 기능을 보완하는 것만으로는 남은 기간 안에 운영 준비를 마칠 수 없다는 점에 대표도 동의했다.

marksman의 시작은 순조로웠다. 기존에 만들어 놓은 seed 프로젝트(nest-seed)가 있었는데 여기에는 커버리지 100%의 통합 테스트와 약간의 유닛 테스트가 있었다. 이것을 복사해서 사용자와 인증과 같은 기본적인 기능을 쉽게 구현할 수 있었다. 물론 이 때 AI의 역할이 컸는데 nest-seed에서 UsersService 같은 특정 서비스를 marksman에 맞게 커스터마이징 하고 테스트도 그에 맞게 변경하는 일이 거의 자동으로 이루어졌다.

문제는 marksman이 아니라 기존 프로젝트에 있었다. 대표가 원하는 바를 팀원들은 각자 해석해서 작업하고 대표는 결과물을 확인하고 원하던 것과 다르다고 수 차례 얘기한다. 대표와 팀원들은 지역적으로 분리되어 있었고 긴밀한 협의가 이루어지기 힘든 환경이었다. 대표와 두 명의 팀원을 이어줄 중간 관리가 필요했다.

처음에는 github의 프로젝트에 테스크를 등록하고 관리하도록 했다. 대표도 개발팀이 할 일을 테스크에 등록하고 개발팀도 테스크를 보고 작업 후에 결과나 공유할 정보를 댓글로 달도록 했다. 그러나 딱 하루만 제대로 돌아갔을 뿐 대표는 지금까지 해왔던 대로 요구사항을 다양한 채널로 전달했고 팀원들은 작업 결과를 테스크에 추가하지 않았다.

결국 구성원들이 이 개발 시스템에 적응할 때 까지 내가 직접 테스크 하나하나 관여해야 했고 marksman을 진행시킬 여유는 점점 사라졌다.
