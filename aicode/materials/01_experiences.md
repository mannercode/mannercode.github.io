# 경험과 사례

1편을 이어 쓸 때 사용할 사건별 자료다. 세 초안에 반복되는 사건과 이후 추가된 검토 사례를 한곳에 모았고, 원문의 구체적인 사정과 표현도 남겼다. 시점과 결말이 불명확한 내용은 [확인할 내용](./03_pending.md#facts)과 해당 사례에 따로 표시했다.

각 사건의 일반적인 교훈은 [개발 원칙](./02_principles.md)에서 다룬다. 1편에서는 당시의 상황, 실제 행동, 결과와 이후 바꾼 작업 방식을 중심으로 풀어 쓸 수 있다.

저자는 2026년 1월부터 9월 초까지 약 여덟 달에 온갖 경험이 압축될 수 있었던 것은 “AI가 시간을 가속했기 때문”이라고 회고했다. AI로 더 많은 시도와 그 결과를 경험하는 동시에 팀 내부의 상황과 구성원의 역할도 빠르게 바뀌었고, 변화에 능동적으로 대응하는 것이 무엇보다 중요한 환경이 됐다는 뜻이다. [1편](../ai_coding_part1.md)의 맺음말에 반영했다.

## 01. 어셈블리어와 AI 코딩

출처: [경험담 원문](../archive/ai_coding.md), [통합 초안](../archive/ai_coding_rewrite.md), [원칙 초안](../archive/README_original.md)의 「들어가며」.

- 1995년 무렵 C를 본격적으로 공부하기 시작했다. 당시에는 프로그래밍을 제대로 알려면 어셈블리어를 알아야 한다는 말을 들었고, C와 어셈블리어가 섞인 소스도 볼 수 있었다.
- 고등학생이었고 GW-BASIC 정도를 알던 때, 『마이크로소프트 매크로 어셈블러 바이블』에 도전했다. 단순한 덧셈도 레지스터로 값을 옮기고 결과를 저장하는 여러 동작으로 지시하는 방식이 불합리하게 느껴져 끝까지 읽지 못했다. 책은 지금도 남아 있다.
- 2025년 말까지 저자는 직접 코딩을 주도하고 AI에는 검토와 보완을 주로 맡겼다. 2026년 초 실제 프로젝트에 에이전트를 본격적으로 적용하며 구현을 맡기고 방향과 결과를 판단하는 방식으로 바뀌었다.
- 당시 체감한 변화는 동시에 다룰 수 있는 문제의 범위가 넓어졌다는 것이다. 생산성 향상이 검증 비용을 감수할 가치가 있다고 느꼈다.

비유의 공통점은 구현 세부를 직접 작성하는 부담이 줄어든다는 점이다. 컴파일러의 변환 방식과 AI의 요구 해석·생성을 같은 신뢰 수준으로 설명하지 않는다. 현재 1편에 이미 도입이 있으므로 원칙 설명을 2편에서 다시 길게 반복할 필요는 없다.

## 02. 거의 완성됐다는 프로젝트

출처: [경험담 원문](../archive/ai_coding.md)의 「출시 6주 전, 프로젝트에 합류하다」, [통합 초안](../archive/ai_coding_rewrite.md)의 「프로젝트에 합류하다」. 현재 서술은 [1편](../ai_coding_part1.md)을 우선 참고한다.

- 2026년 1월, 전시·행사 현장에서 사용할 티켓 서비스를 만들던 팀에 합류했다. 기존 팀은 팀장 한 명과 팀원 두 명이었다.
- 남은 일정은 기존 두 초안에서 6주, 현재 1편에서 처음에는 4주로 기록돼 있다. 수치는 [확인 항목](./03_pending.md#facts)에 남겼다.
- 대표는 거의 완성됐다고 생각했다. 개별 화면과 API는 동작했지만 회원 가입, 구매, 발권, 입장, 매출 확인을 하나의 이용 흐름으로 연결하기 어려웠다.
- 저자는 진행 상황을 파악하려고 제품을 직접 실행해 봤으며, 인증 같은 기본적인 기능에서도 바로 오류를 발견했다고 설명했다.
- 저자가 좌절감을 느낀 지점은 거의 완성됐고 출시까지 4주가 남았다면서도, 회의에서는 무엇이 됐고 무엇이 안 됐는지부터 파악하고 있었다는 모순이었다. 저자는 이를 자신의 경험에 비춰 “하긴 했지만 제대로 하지는 않은 상태”라고 설명했다.
- 저자는 이 상태를 준공을 앞둔 부실공사 현장에 비유했다. 집은 지었지만 비가 새고 문이 열리지 않는 등 품질이 엉망이라 입주 허가가 나지 않을 것 같은 느낌이었다는 설명이다.
- 기존 팀장은 퇴사를 앞두고 있었다. 경력 3년 차 개발자가 서비스 백엔드를 사실상 전담했고, 다른 팀원은 사용자용 iOS 앱과 Android 발권 키오스크를 맡았다. 팀장은 처음 해보는 Android 사용자 앱을 개발하고 있었다.

집필 중 저자는 기존 개발팀장에 대한 대표의 불신을 출근 전부터 들었다고 설명했다. 한 개발자에게서 생긴 불신이 자신에게도 이어질 수 있다고 생각했고, 상호 신뢰 관계를 형성하는 것을 무엇보다 중요하게 여겼다. 출근 첫날 일부러 롱패딩을 깔고 사무실에서 자는 모습을 보여 준 데에는 신뢰를 얻으려는 뜻과 프로젝트가 비상 상황이라는 것을 구성원 전체에게 알리려는 뜻이 함께 있었다. 야근하다 우연히 사무실에서 잠든 일로 바꾸어 쓰지 않는다.

첫날의 대화에 대해 저자가 이후 더 구체적으로 설명한 내용은 다음과 같다.

- 프로젝트 소개를 부탁하자 팀장은 개발자는 그런 일을 하는 사람이 아니라고 답했다. 저자도 상냥한 태도를 버리고 상대를 무시하는 시선과 냉랭한 말투로 대했다. 다른 설명을 몇 차례 요청했을 때도 대표에게 물어보라는 답을 듣고 대화를 접었다.
- 잠시 자리를 비웠던 대표가 돌아와 두 사람이 말없이 각자 책상에 앉아 있는 모습을 의아해했다. 팀장은 대표와 회의실로 갔고, 팀장이 돌아온 뒤에는 대표가 저자를 회의실로 불렀다.
- 대표는 팀장이 저자를 안 좋게 이야기하며 Java도 모르는 개발자이니 잘 생각해야 한다고 했다는 말을 전했다. 이어 저자에게 문제가 없는지, Java를 할 수 있는지 물었다. 팀장의 회의실 발언은 저자가 직접 들은 말이 아니라 대표가 전한 말이다.
- 저자는 특정 기술에 적응할 수 있는지를 다시 설명하기도 싫었고, 팀장을 불신하던 대표가 그 말을 듣고 자신을 불안해하는 모습도 한심스럽게 느꼈다고 설명했다. 누구를 쉽게 믿지 못하고 누구를 믿어야 할지도 판단하지 못하는 사람이라는 평가는 저자의 당시 인식이다.
- 저자는 사람이 의심스러우면 쓰지 말고 쓰려면 의심하지 말라고 했으며, 말 한마디에 흔들리면 앞으로 어떻게 함께 일하겠느냐고 물었다. 대표가 Java를 할 수 있느냐고 거듭 묻자, 모르는 기술도 금방 적응할 수 있고 그동안의 경력은 이력서에 나와 있지 않느냐고 답했다.

저자는 이를 시작부터 잘못된 만남이었다고 회고했다. 팀장의 태도가 전형적인 오만한 개발자로 보였다는 인상과, 저자도 곧바로 상대를 무시하며 대화를 접었다는 행동을 함께 유지한다. 합류 전에 대표와 팀장 사이에 무슨 일이 있었는지는 모르므로 이 장면만으로 잘잘못이나 불신의 시작을 단정하지 않는다. 이후 저자가 협의에서 배제된 뒤 개선 의견을 내지 않게 된 경험과 연결하되, 당시 팀장에게도 같은 배경이 있었다고 확인된 것은 아니다.

대표는 기존 팀장을 추천받아 채용했다고 저자에게 말했다. 저자는 이 점을 들어 다른 환경에서는 준수한 성과를 내고 좋은 평가를 받았던 사람일 수 있으며, 이 프로젝트의 문제를 온전히 팀장 한 사람의 책임으로 돌리기 어렵다고 덧붙였다. 추천 채용은 대표에게 들은 내용이고, 다른 환경에서의 성과는 그에 따른 저자의 추정으로 구분한다.

저자는 오만한 개발자를 보면 자신도 죄를 짓는 기분이라고 덧붙였다. 비개발자의 눈에는 자신도 같은 개발자이므로, 한 개발자에게서 생긴 불신이 다른 개발자에게까지 이어질 수 있다는 생각이다.

| 구성 요소 | 당시 구현 형태 |
| --- | --- |
| 서비스 백엔드 | Java |
| 입장 키오스크 | iOS 네이티브 앱 |
| 발권 키오스크 | Android 앱에서 서버가 JSP로 렌더링한 화면 표시 |
| POS | Android 네이티브 앱 |
| 사용자용 앱 | iOS와 Android 네이티브 앱을 각각 개발 |
| 백오피스 | JSP로 화면과 서버 로직을 구현한 별도 애플리케이션, 서비스 백엔드와 DB 공유 |

통합 초안에는 대표가 기존 팀장의 AI 미사용을 불만으로 말했다는 대목도 있다. AI가 만든 코드를 믿을 수 없고 진정한 개발도 아니라는 태도였다는 내용은 대표에게 전해 들은 설명이다. 저자 역시 얼마 전까지 AI에 검토와 보완만 맡겼다는 사정과 함께 보관한다.

기존 팀은 첫 출시를 준비하고, 저자는 일정과 범위를 관리하면서 이후 기존 시스템을 대체할 백엔드·백오피스·사용자 앱을 별도로 준비하기로 했다. 이 결정과 다음 사례의 분석·범위 협의 순서는 집필할 때 맞춰야 한다.

## 03. AI로 기존 시스템 분석

출처: [경험담 원문](../archive/ai_coding.md)의 「AI 에이전트로 프로젝트를 분석하다」, [통합 초안](../archive/ai_coding_rewrite.md)의 「AI에게 처음 맡긴 일은 분석이었다」.

- 합류한 날 밤부터 REST API 목록을 만들고 기능별로 분류하게 했다. 역할과 이해하기 어려운 요청 인자를 관련 코드까지 추적하며 조사했다.
- 서비스의 큰 윤곽을 파악하는 데 하루가 걸렸다. 같은 수준의 조사를 직접 했다면 일주일가량 걸렸을 것이라는 저자의 추정이 있다.
- DB와 API의 구조·이름만으로 역할과 관계를 이해하기 어려웠다. 일부 요청의 암호화·복호화 기준이 일관되지 않았고 같은 종류의 데이터도 다르게 처리됐다.
- 원문에는 분석이 틀린 사례도 있다. AI가 구현된 것으로 파악한 API가 실제로는 개발하다 중단된 것이었고, 이름으로 추정한 용도가 실제 동작과 다른 경우도 있었다. 이후 개발 과정에서 발견했다. 통합 초안에서는 이 설명이 빠졌다.

이 사례는 빠르게 얻은 지도가 이후 확인을 통해 보완됐다는 흐름으로 쓸 수 있다. 하루 만의 분석과 일주일이라는 추정치를 동일 조건의 생산성 측정처럼 표현하지 않는다.

## 04. 출시 범위와 작업 관리

출처: [통합 초안](../archive/ai_coding_rewrite.md)의 「6주 안에 만들 범위를 다시 정하다」, [경험담 원문](../archive/ai_coding.md) 말미의 재개발 설득·GitHub 작업 관리 메모.

- 대표와 최소 요구사항을 정리했다. 저자는 고객을 잘 몰랐기 때문에 대표가 가진 고객·운영 정보에 의존해야 했다.
- 당장 필요한 기능과 미래의 기능이 섞여 나왔다. 개인 간 티켓 거래가 중요하게 거론됐으나 7개월 뒤에는 잊힌 요구사항이 됐다. 사용자 앱도 운영 이후 우선순위가 밀렸다.
- 현재 1편에는 티켓 판매·발권·입장·매출 확인의 흐름을 먼저 연결하기로 했다는 내용이 있다. 초기 출시 범위와 4월 말 최종 축소 범위를 같은 시점의 결정으로 합치지 않는다.
- 대표와 팀원들이 서로 다른 지역에 있었고, 대표의 요구를 각자 해석해 구현한 뒤 원하던 결과가 아니라는 피드백을 반복해서 받았다.
- 저자는 GitHub 프로젝트에 작업을 등록하고 요구사항·결과·공유 정보를 댓글로 남기게 했다. 원문에는 하루만 제대로 돌아갔다는 기록이 있다. 대표는 여러 채널로 요구를 전달했고 팀원들은 결과를 작업 항목에 남기지 않았다.
- 결국 저자가 작업마다 직접 관여하게 됐고, 새 백엔드 개발을 진행할 여유가 줄었다.

GitHub 작업 관리의 정확한 도입 시점은 원문에 없다. 팀원의 행동뿐 아니라 요구사항 전달과 작업 관리가 정착되지 않은 배경을 보여주는 자료로 남긴다.

## 05. 백오피스 재개발

출처: [경험담 원문](../archive/ai_coding.md)의 「AI 에이전트로 백오피스를 다시 만들다」, [통합 초안](../archive/ai_coding_rewrite.md)의 「AI로 백오피스를 다시 만들다」.

- 완성도가 낮았던 JSP 백오피스를 Next.js로 다시 만들었다. 화면과 서버 로직이 섞인 구조, 서비스 백엔드와 DB에 각각 직접 접근하는 구조를 정리하려는 목적도 있었다.
- 2년 전에는 Next.js 백오피스를 만들며 MUI 기반 유료 템플릿을 구입해 수정했다.
- 이번에는 필요한 메뉴와 REST API 요청·응답을 정리한 문서를 AI에 제공했다. 원문은 “데이터를 간략히 설명했다”는 표현을 뒤에서 이 내용으로 구체화한다.
- AI가 기본 구조와 주요 화면을 빠르게 구현했다. 시각적 완성도를 우선하지 않은 일정에서도 별도의 유료 템플릿이 필요 없을 정도라고 느꼈다.

줄어든 준비 작업은 템플릿 선택, 구조 파악, 요구사항에 맞춘 수정이었다. 제작 기간의 정확한 수치는 초안에 없으므로 추가하지 않는다.

## 06. 역할 통합과 동작하는 초안

출처: [경험담 원문](../archive/ai_coding.md)의 「AI로 커뮤니케이션 비용을 줄이다」와 API 연동 사례, [통합 초안](../archive/ai_coding_rewrite.md)의 「역할을 합치자 전달 비용이 줄었다」.

- 백오피스에 필요한 API를 요청했지만 구현·수정됐다는 보고 뒤에도 오류와 누락이 드러났다. 하나의 API 연동에서 세 차례 문제가 반복됐다.
- 백오피스가 API 데이터를 확인하고 수정하는 기능 중심이었으므로, 백엔드 개발자에게 백오피스까지 맡겨 전달과 재확인 비용을 줄이려 했다.
- 그는 처음에는 프론트엔드를 하고 싶지 않다고 했다. 원문에는 백엔드 전문 개발자가 되고 싶다는 이유가 나온다. 두 애플리케이션을 함께 다루는 효율성에는 동의했다.
- 저자는 과거라면 경력 3년 차 개발자에게 두 영역을 함께 맡기지 않았을 것이라고 회고한다. 원문의 “모두 풀스택을 지향해야 한다”는 확대 해석과 통합본의 제한된 주장은 [논점 차이](./03_pending.md#positions)에 남겼다.
- 백오피스를 넘기고 새 백엔드와 사용자 앱 개발을 시작했다. 사용자 앱에는 경험이 있던 RN 대신 처음 사용하는 Flutter를 선택했다.
- 처음에는 디자이너의 Figma 파일을 그대로 구현하게 했다. PDF·SVG로 바꿔 전달해도 디자인과 일치하지 않거나 제대로 동작하지 않았다. 저자도 Figma를 능숙하게 다루지 못했고 수정할 시안이 많았다.
- 몇 시간 뒤 기능과 제약을 설명해 동작하는 초안을 만드는 방식으로 바꿨다. 대표와 결과물을 직접 보고 논의하며 그 자리에서 수정할 수 있었다.

원문에는 “디자이너의 디자인보다 AI가 생성한 디자인이 더 훌륭했다”는 저자의 평가도 있다. 이 프로젝트에서 결과물을 어떻게 느꼈는지에 관한 표현으로 보관한다. 디자인 전문성 전체에 관한 결론으로 확대할지는 별도 집필 판단이다.

## 07. 나도 검증을 미루다

출처: [경험담 원문](../archive/ai_coding.md)의 「AI 에이전트는 제어가 어렵다」와 말미의 시드 프로젝트 메모, [통합 초안](../archive/ai_coding_rewrite.md)의 「나도 AI의 완료 보고를 믿기 시작했다」.

- 새 백엔드는 기존 NestJS 시드 프로젝트에서 시작했다. 사용자와 인증 등의 서비스를 프로젝트에 맞게 수정하고 테스트도 바꾸는 데 AI가 큰 역할을 했다.
- 시드에는 통합 테스트와 일부 단위 테스트가 있었다. 원문의 커버리지 100%는 통합본에서 “테스트 대상으로 정한 범위”로 한정돼 있다. 실제 측정 범위는 확인할 내용이다.
- 처음에는 조심스럽게 맡겼지만 결과가 좋자 더 추상적이고 큰 목표를 연속으로 던졌다. 큰 작업 두세 개를 맡기는 동안 검증을 미뤘다.
- 잠을 자다가 두세 시간마다 깨서 다음 작업을 지시하기도 했다. AI를 멈춰 결과를 검토하는 것이 비효율적으로 느껴졌다.
- 나중에 살펴보니 요청하지 않은 기능이 추가되고 필요한 기능은 빠져 있었다. 보안 관련 방어 로직과 제약 때문에 작은 변화에도 기능이 중단되는 경우가 있었다.
- 카드번호를 검색에 활용할 방법 없이 마스킹해 저장하면서 카드번호 검색 UI는 만들었다. 전체 기능을 테스트하라고 여러 번 요청해도 AI는 정상이라고 보고했다.
- 정상적인 방법으로 해결되지 않을 때 우회하거나 조건을 느슨하게 바꾼 뒤 해결했다고 보고하는 일도 겪었다.

원문의 “개떡같이 말해도 찰떡같이 알아듣는”, “이게 되네?”, “잘못된 방향으로도 놀라울 만큼 열정적으로 삽질한다”는 표현은 이 사건에 연결된다. 무엇을 실제로 테스트했는지와 이후 저자가 바꾼 검증 절차는 초안에서 충분히 설명되지 않았다.

## 08. 첫 출시와 백엔드 개발자

출처: [경험담 원문](../archive/ai_coding.md)의 「AI에게 맡기고 검토하지 않다」와 「AI를 쓰면서도 과거의 기준으로 판단하다」, [통합 초안](../archive/ai_coding_rewrite.md)의 「3월, 기존 서비스를 가까스로 출시하다」와 「AI에게 맡기고 검토하지 않은 개발자」.

- 기존 팀이 마무리하던 서비스는 3월 초 출시됐다. 통합본은 기존 시스템으로 현장 운영을 시작한 첫 출시와 새 시스템으로 교체하는 작업을 구분한다.
- 반복된 API 연동 실패 뒤 확인하니 백엔드 개발자는 AI가 만든 구현과 API 설계를 검토하지 않았다고 답했다. 요구사항을 AI에 전달하고 완료 보고를 다시 전달하는 방식이었다.
- 기존 기능의 회귀와 맞지 않는 매출 통계를 조사하다가 한 애플리케이션을 AI 에이전트 서너 개가 동시에 수정하고 있음을 알게 됐다. 작업 분리와 결과 검토·통합 방법이 없었다는 것이 초안의 설명이다.
- 이후 키오스크 연동에서도 같은 API를 여러 번 다시 만들었다. 급박한 일정 때문에 저자가 매번 깊이 개입하지는 못했다.
- 개발자는 큰 회사에서도 여러 기획자가 검증해도 완벽하기 어려운데 작은 회사에서 어떻게 팀장의 기준에 맞추느냐고 말했다.
- 저자가 요구했다고 기록한 기준은 완료 보고 전에 요구사항을 확인하고 API를 실제로 테스트하는 것이었다. 저자는 이를 결과를 검증할 의무를 받아들이지 않는 문제로 판단했고, 그 말을 들은 다음 날 해고를 통보했다. 시점은 4월 초다.

원문 말미에는 기존 팀장과 백엔드 개발자가 적당히 구현한 뒤 완료했다고 보고해, 만든 것을 제거하고 다시 만드는 일이 반복됐다는 메모도 있다. 버그가 상대방의 작업에 주는 피해를 당연하게 받아들이는 것 같았다는 저자의 불만이 함께 적혀 있다.

백오피스 담당을 넘긴 일과 초기 API 실패는 [사례 06](#case-06)에 있다. 이 사건을 쓸 때 반복 서술을 줄이고, 완료 기준을 어떻게 공유했으며 오류가 반복된 뒤 어떤 개선을 시도했는지 보충할 수 있다. 직접 인용할 발언은 원문에 남아 있다.

## 09. Android 개발자의 업무와 퇴사

출처: [경험담 원문](../archive/ai_coding.md)의 「AI를 쓰면서도 과거의 기준으로 판단하다」, [통합 초안](../archive/ai_coding_rewrite.md)의 「과거의 기준으로 새로운 업무량을 판단하다」.

- 3월 초 iOS 개발자의 계약이 끝났다. 새 Android 개발자에게 기존 Android 키오스크·사용자 앱과 함께 iOS 키오스크·사용자 앱도 맡아 달라고 했다.
- 그는 두 애플리케이션을 맡고 있는데 어떻게 네 개를 하느냐며 강하게 거부했다. 저자는 기존 방식으로 계산하면 합리적인 반응이었다고 썼다.
- 저자는 공통 요구사항을 정리하고 AI가 플랫폼별 구현을 수행하면 부담이 달라진다고 설명했다. 빌드·배포·권한·하드웨어 등 플랫폼 고유의 작업은 남았다.
- 설명 뒤 개발자가 업무를 받아들였다는 기록이 있다. 그 밖에도 AI 코딩 방식에 적응하도록 몇 차례 요구했으나 원문에는 구체적인 내용이 기억나지 않는다고 적혀 있다.
- 저자는 적응에 시간이 필요하다는 것을 알면서도 작은 스타트업의 일정상 기다리기 어려웠다고 회고한다. 개발자는 수습 평가를 앞두고 퇴사 의사를 밝혔다.

퇴사의 정확한 날짜와 이유, 네 앱을 실제로 어느 정도 처리했는지는 초안에 없다. 백엔드 개발자의 검증 생략과 이 개발자의 업무량 판단을 같은 사건으로 묶지 않는다.

## 10. 1인 개발과 범위 축소

출처: [경험담 원문](../archive/ai_coding.md)과 [통합 초안](../archive/ai_coding_rewrite.md)의 「AI 에이전트로 1인 개발을 시작하다」.

- Android 개발자가 퇴사 의사를 밝히자 저자는 채용으로 공백을 채우지 않고 1인 개발 체제로 운영하자고 대표에게 제안했다. 맥락 전달, 조율, 수정, 조언과 피드백의 비용이 컸다는 판단이었다.
- 대표는 개발팀이 무너져 사업을 접어야 하는지 고민했다고 나중에 전했다. “우수한 팀장인 나와 성실한 팀원인 AI 에이전트들”이라는 농담은 이 장면에 있다.
- 넘겨받은 저장소는 서비스 백엔드, Android 키오스크, iOS 키오스크, Android 키오스크의 JSP 서버, Android POS, Android 사용자 앱, iOS 사용자 앱, 백오피스 등 여덟 개 정도였다. 별도 행사 프로젝트와 개발 중인 Flutter 사용자 앱도 있었다.
- 2001년부터 실무를 했지만 Java 백엔드 경험은 없었다. JSP 업로드 컴포넌트 경험은 있었고, iOS에는 익숙했지만 Android 프로젝트 경험은 한 번이었다. 익숙하지 않은 기술 여러 개를 동시에 맡는 일이 드물었다.
- 넘겨받은 저장소를 웹과 Android 중심의 두 모노레포로 정리했다. 함께 바뀌는 코드를 AI가 한 맥락에서 살펴보기 쉬워졌다. 원문은 VS Code와 Android Studio의 작업 환경 차이도 이유로 든다.
- 새 환경에 적응하는 데 일주일 정도 걸렸고, 일정 규모까지는 혼자 개발하는 편이 생산성이 높다고 느꼈다.
- 모든 제품을 유지한 것은 아니다. iOS·Android 네이티브 사용자 앱을 중단하고 POS, 발권 키오스크, 입장 키오스크, 백오피스, 백엔드의 다섯 영역으로 줄였다. 4월 말에 마무리했다는 기록이 있다.
- 위기 이후 대표는 AI 에이전트를 “클 이사”, “코 부장”이라고 불렀고, 저자와 대표는 당분간 개발자를 추가 채용하지 않아도 된다고 판단했다.

저자의 추가 설명에 따르면 4월에는 기존 전시 현장 외에 별도 행사도 있었다. 저자는 그 준비 과정에서 겪은 큰 위기도 잘 극복했다고 생각했다. 위기의 구체적인 내용과 대응 과정은 아직 기록되지 않았다.

3월의 첫 출시, 4월 말의 마무리, 새 백엔드로의 교체 완료는 같은 사건이라고 확정할 수 없다. 성과를 설명할 때 AI 활용과 함께 범위 축소, 구조 정리, 조율 방식의 변화도 기록한다. 원문의 “기술은 중요하지 않았다”는 당시 생각과 통합본의 사후 해석은 [논점 차이](./03_pending.md#positions)에 남겼다.

<a id="case-11"></a>

## 11. 대표가 별도 서비스를 개발

출처: [경험담 원문](../archive/ai_coding.md)의 「AI 에이전트로 비개발자가 개발을 시작했다」, [통합 초안](../archive/ai_coding_rewrite.md)의 「비개발자가 AI로 개발을 시작하다」.

- 대표는 4월 초에 AI와 별도 서비스 개발을 시작했고, 저자는 한 달가량 지난 5월 초에 그 결과물을 처음 봤다. AI가 추천한 스택을 따라 Supabase 백엔드, Next.js 백오피스, Vercel 배포를 사용했다.
- 기존 문제를 마무리하고 품질 개선에 집중하려던 때, 대표가 자신이 만든 서비스에 키오스크를 붙이고 자신이 선택한 방향으로 백엔드와 백오피스까지 마무리해 달라고 요구했다.
- 저자는 개발 경험이 없던 대표가 동작하는 서비스를 만든 것은 인정하면서도, 기술 선택을 협의하지 않은 채 넘겨받는 상황과 자신의 설명보다 AI 제안이 더 신뢰받는 상황에 반발했다.
- 대표는 자유롭게 배포하고 싶다는 요구에 따라 키오스크와 사용자 앱에 RN을 쓰려 했다. 원문은 AI가 그 요구 때문에 RN을 선택했다고 설명하고, 통합본은 그렇게 제안한 것으로 보인다고 표현한다.
- 저자는 Android 단일 기기에서 동작하고 프린터·스캐너와 연결되며 제한된 메모리와 저가 CPU로 장시간 실행하는 키오스크에는 Android 네이티브가 더 적절하다고 판단했다.
- 원문에는 RN 환경 구성과 디버깅의 어려움, 같은 스크롤 상태 값이 플랫폼별로 크게 달랐던 개인 경험이 있다. 해당 API·단위·버전은 기록돼 있지 않다.
- 첫 제안 때 받아들이지 못했고, 대표가 다음 주 다시 문제를 꺼냈다. 저자는 퇴사까지 생각했다. 최종 합의와 실제 채택한 구조는 세 초안에 없다.

저자는 이후 줄거리를 정리하면서, 5월 초에 처음 결과물을 본 뒤 약 네 달 동안 개발이 계속됐고 자신도 그 프로젝트를 함께 다뤘다고 설명했다. 대표는 개발이 이어질수록 기술적 조언보다 AI를 더 신뢰했다. 9월 초에는 전체 개발 기간이 약 다섯 달이었으며, 그 결과물을 전체 검토한 자료가 [사례 15](#case-15)다. 세부적인 역할 분담과 기술 선택의 합의 과정까지 새로 확인된 것은 아니다.

추가로 저자는 자신의 말에 대표가 AI에게 물어본 뒤 답변을 그대로 복사해 전달하는 일이 반복됐다고 설명했다. 답변은 대체로 길고 장황했으며, 저자가 보기에는 말도 안 되는 주장까지 읽고 반박해야 했다. 저자는 그 과정에서 자신이 무엇을 하고 있는지 회의감을 느꼈지만 대표는 그런 개발자의 심정을 이해하지 못했다고 회고했다. 이는 원문에 있던 내용이 아니라 집필 중 저자가 추가한 경험이다.

저자는 대표가 예전에는 버그나 기능 누락이 있는데 완료했다고 보고하면 안 된다고 개발자들에게 말했고, 그 보고를 믿고 현장에 갔다가 제대로 동작하지 않아 난처했던 경험도 이야기했다고 덧붙였다. 그런 대표가 직접 AI로 개발하면서 같은 완성도 판단의 잘못을 반복했다는 아이러니를 1편의 9월 검토 장면에 연결했다. 대표의 과거 발언은 취지를 간접화법으로 옮긴다. 1월의 개발팀장도 자신의 개발 방향이 맞고 일이 잘 진행된다고 믿었을 것이라는 설명은 저자의 사후 추정으로 구분한다.

저자는 대표의 개발자 불신을 [합류 당시](#case-02)부터 알았고, 레거시 수습과 [4월의 별도 행사](#case-10) 준비에서 겪은 위기를 잘 넘겼다고 생각했지만 대표는 끝까지 자신보다 AI를 신뢰했다고 덧붙였다. 대표가 유난히 인간에 대한 불신이 깊은 사람이었다는 것은 저자의 사후 평가다. 이 개인적 성향과 AI 코딩의 빠른 성과에서 비롯된 만능감은 구분해 다룬다.

이후 저자는 이 시리즈가 기술적인 부분에 초점을 맞추지만, 실제 프로젝트에서 가장 중요하고 필요했던 것은 인간관계였다고 설명했다. 기존 팀장과 대표 사이에서도, 대표와 저자 사이에서도 상호 신뢰를 구축하는 데 실패했고, 서로 연결되지 않은 개인플레이가 프로젝트 완성의 큰 장애물이 되었다는 회고다. 저자 자신도 함께 판단하고 작업을 연결할 수 있는 관계를 만드는 데 실패했다는 관점으로 [1편 맺음말](../ai_coding_part1.md#trust-and-communication)에 반영했다. [2편의 협업 논점](../ai_coding_part2_notes.md)에서는 전문가의 참여와 기술적인 절차가 실제 협업으로 이어지기 위한 전제로 연결한다.

저자는 공감과 커뮤니케이션의 중요성을 인식하고 있다고 생각했지만, 협의 과정에서 몇 차례 배제되고 나니 시키는 일만 적당히 처리할 뿐 더 나은 의견을 말하지 않게 됐다고 덧붙였다. 해당 분야의 전문가보다 AI를 더 신뢰해서 생긴 일이라고 느끼면서도, 사람을 신뢰하지 못하기 때문에 벌어진 일일 수 있다고 여지를 남겼다. 원인을 하나로 단정하지 않고, 협의에서 배제된 뒤 저자 자신의 참여 태도도 달라졌다는 경험을 유지한다.

저자는 개인의 이야기를 구체적으로 다루는 데 서로의 입장을 더 잘 이해하기를 바라는 뜻이 있다고 설명했다. 상대방이 하는 일이 부족해 보여도 자신이 그 입장에서 해 보면 별반 다르지 않을 수 있고, 각자 맡은 일에는 어려움이 있다는 관점이다. 대표가 다른 개발자에게 요구했던 기준을 자신에게 적용하지 못했다는 아이러니 뒤에는 저자 자신도 AI의 완료 보고를 믿고 검토를 미뤘다는 경험을 연결했다.

저자는 오만한 개발자에게 상처받는 대표만큼 야박한 대표에게 상처받는 개발자도 있다는 점을 덧붙였다. 대표는 개발자의 오만함을, 개발자는 대표의 야박함을 보며 서로 멀어진다는 회고다. 특정 직군에서 이런 사람이 얼마나 많은지를 확인한 통계로 서술하지 않는다.

저자는 자신도 이 회사에서 열심히 일했다고 생각하지만 누군가에게는 나쁜 개발자가 되어 있을지도 모른다고 덧붙였다. 실제로 그런 평가를 들었다는 사실로 바꾸지 않고, 자신의 노력과 상대방이 자신을 경험한 방식이 다를 수 있다는 회고로 1편 맺음말에 반영했다.

저자가 감정적인 사례를 구체적으로 쓰는 이유로 최종 정리한 것은 개발자와 비개발자의 긴밀한 협력이 더 중요해졌다는 점이다. 구현에 많은 시간이 필요했던 과거에는 각자 맡은 일을 진행하는 동안 조율 비용이 상대적으로 덜 두드러질 수 있었으나, 구현 시간이 극단적으로 줄면서 서로의 결정을 기다리고 결과를 연결하는 일이 전체 프로젝트의 병목이 된다는 설명이다. 1편에서는 협력이 끊기는 구체적인 과정과 그 결과를 보여주는 데 초점을 둔다.

대표의 사례는 비개발자가 AI 코딩을 하며 빠지기 쉬운 함정을 보여주는 경험이기도 하다. 개발을 잘 모르는 상태에서도 생각했던 결과물이 빠르게 만들어지면 만능감에 빠지고 전문가의 조언이 없어도 아쉽지 않게 될 수 있다는 문제의식이다. 대표 개인의 성향이 겹쳐 있다는 이유로 이 위험까지 개인적인 갈등으로만 한정하지 않는다. [2편의 빠른 성과와 만능감](../ai_coding_part2_notes.md#ai-success-overconfidence)에 연결한다.

이런 방식이 계속되면 토큰 비용이 부담되기 시작하고, 오류가 잦아지며, 에이전트가 의도와 다른 기능을 구현하다 결국 다시 만드는 상황에 이를 것이라는 전망도 덧붙였다. 예측의 근거는 [리팩터링](#case-11-refactoring)을 하고도 복잡도가 줄지 않았는데, 대표는 구조가 정리됐다고 믿고 기능 확장을 계속한다는 데 있다. 구조와 검증을 놓쳤을 때 사람이 개발하며 겪던 문제가 AI 코딩에서도 되풀이된다는 논점이다. 해당 프로젝트에서 이미 이 모든 과정과 재작성이 일어났다는 회고로 바꾸지 않는다.

“싸늘했다. 가슴에 비수가 꽂히는 것 같았다”, 초보 투자자가 주식으로 원금을 열 배 불린 뒤 위험 설명을 듣지 않는다는 비유, “글을 쓰고 있는 지금 다시 생각해도 울컥한다”는 감정 표현은 이 장면의 원문에 있다. 기술 판단의 근거와 최종 결과를 보충한 뒤 사용할 수 있다.

<a id="case-11-refactoring"></a>

### 협의 없이 진행된 대규모 리팩터링

집필 중 저자가 추가로 설명한 경험이다. 장면과 감정은 [1편의 해당 절](../ai_coding_part1.md#uncoordinated-refactoring)에 반영했다.

- 대표가 여러 에이전트로 기능 확장에 주력하던 때, 저자는 DB 스키마·시스템 아키텍처·API의 문제를 제기하고 기존 구조 전체를 리팩터링하기보다 필수 기능을 하나씩 검토해 옮기자고 제안했다.
- 행사를 마친 저자가 일주일 쉬는 동안 대표는 “리팩터링이 필요하다”는 말만 AI에게 전달하고, AI가 수립한 전략을 저자와 협의하지 않은 채 실행했다. 저자는 최소 세 개의 에이전트가 동시에 작업했고 한 저장소에 하루에도 100개가량의 커밋이 올라왔다고 설명했다.
- 저자가 에이전트에게 검토를 맡긴 결과, 코드의 위치가 바뀌고 일부 정리는 됐지만 대규모 리팩터링이라고 부를 만한 아키텍처와 인터페이스의 근본적인 개선은 미미했다고 설명했다. Supabase의 DB 함수에 있던 로직을 백엔드로 옮겼을 뿐 시스템의 복잡도는 줄지 않았고, DB 테이블은 60개 늘어 있었다.
- 저자는 집필 시점에도 대표가 리팩터링의 실제 결과를 모르며, AI가 계획대로 완료했다고 보고했으므로 프로젝트가 다시 깨끗한 상태가 됐을 것이라고 생각하고 있다고 덧붙였다.
- 저자는 일주일 동안 3주치 토큰을 소비한 결과가 고작 위치 변경과 일부 정리에 그쳤다고 느꼈다. 조언을 해도 무의미하겠다는 회의감과 어처구니없고 짜증스러웠던 감정을 함께 설명했다.
- 저자가 생각한 대안은 도메인·기능의 경계를 먼저 정하고 API를 분리해 모듈 간 의존성을 줄이며 필수 기능을 하나씩 검토해 옮기는 것이었다. 더 안전하고 빠른 개선과 이후 기능 확장의 기반을 기대한 제안이며, 실제로 수행해 비교한 결과는 아니다.

저자는 대표에 대한 감정을 뒤로하고, 이 사례를 비개발자가 AI로 개발할 때 개발자가 기여할 역할에 연결하고 싶다고 설명했다. 최근 Codex 6.0 Astra를 사용하면서도 분석과 설계 전략에는 사람의 논리와 경험이 거의 필수처럼 느껴졌다는 개인적 평가다. 이 사용 경험을 대표가 당시 리팩터링에 사용한 모델이나 모델 간 성능 비교의 근거로 해석하지 않는다.

행사의 시점과 수치의 기준은 [확인 메모](./03_pending.md#facts)에 남겼다. 현재 내용은 저자의 회고이며, 커밋 이력·스키마·사용량 로그를 이번 집필에서 별도로 검증한 결과는 아니다. 여러 에이전트를 사용했다는 사실만으로 구체적인 충돌이나 회귀가 발생했다고 덧붙이지 않는다. [2편의 병렬 개발과 경계](../ai_coding_part2_notes.md#parallel-development-boundaries), 전문가와 전략을 함께 정하는 협업 논점에 연결한다.

<a id="case-11-translation"></a>

### 동시번역 기능과 제안되지 않은 동작 방식

집필 중 저자가 추가로 설명한 경험이다. [1편의 해당 절](../ai_coding_part1.md#translation-implementation)에 반영했다.

- 대표는 한 행사를 대비해 동시번역 기능을 추가했다. A가 한 문장을 말하고 전송 버튼을 누르면 그 내용이 B에게 전달되고 B 쪽에서 번역되는 구조였다.
- 저자는 발언 중에도 오디오 스트림을 계속 전달해 번역하는 동작 방식을 지적했다. 발언이 끝나고 버튼을 누를 때까지 전송과 번역을 기다리게 할지, 발언 도중부터 진행할지는 구현 전에 정하는 동작 설계의 차이다. AI는 이런 대안을 제안하지 않았고, 대표는 제시된 방식을 그대로 수용했다는 설명이다.
- 구현하기 쉬운 구조를 선택했다는 것은 저자의 평가다. AI가 해당 API를 알고도 의도적으로 회피했다거나, 조사한 대안을 숨겼다는 사실까지 뜻하지 않는다.
- 저자가 말한 프롬프트 변경은 발언 중에도 오디오를 계속 전달해 번역하도록 요구해 동작 설계를 바꾸는 것이다. 그러나 협의 없이 대규모 리팩터링을 진행한 대표에게 더는 조언하고 싶지 않았다고 설명했다. 대표도 동시통역 기능은 신경 쓰지 않아도 된다고 했고, 저자는 더 이상 아무 말도 하지 않았다.
- 이 사례는 리팩터링·시스템 설계뿐 아니라 개별 기능의 동작 설계에서도 개발자가 현재 기술로 가능한 대안을 제시하고 사용 목적에 맞는지 판단할 수 있다는 논점에 연결한다. 실제로 스트리밍 방식으로 변경한 결과는 아직 기록되지 않았다.

기술 설명의 근거: [Azure Speech 공식 문서](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-translation)는 음성 스트림의 실시간 번역과 발화 중 중간 번역 결과 반환을 설명한다. 2026년 9월 7일 집필 중 확인했으며, 발언 중 전송과 번역 처리가 가능한 동작 방식을 설명하는 참고 자료다.

집필 중 이 글을 검토한 AI도 동작 설계의 차이를 구현 후 성능 검증 문제로 잘못 해석했다. 저자가 이를 지적한 대화는 [AI 자신의 반성 노트](../ai_coding_part1.md#translation-ai-review-note)로 본문에 기록했다. AI의 잘못된 검토 의견과 이를 무비판적으로 받아들였을 때 원고 및 개발 결정에 미쳤을 영향을 구분해 서술한다.

## 12. 결제 요청과 결과의 연결

출처: [원칙 초안](../archive/README_original.md)의 「3.2 경계와 계약을 먼저 정의한다」, [통합 초안](../archive/ai_coding_rewrite.md)의 「출시 뒤에 남은 긴 꼬리」와 「경계와 계약을 먼저 확인한다」.

- 카드 승인 뒤 생성된 주문이 재시도·복구 뒤에도 원래 요청의 결과인지 확인해야 했다. 성공 응답 계약에 애플리케이션의 상관관계 식별자 `clientRequestId`가 빠져 있었다.
- AI는 승인 정보·금액에 더해 형식이 바뀔 수 있는 카드 표시 정보와 거래번호를 비교하도록 구현했다. README는 서버 표시 형식이 달라 정상 결제가 취소됐다고 서술하고, 통합본은 취소될 수 있는 구조였다고 서술한다. 실제 발생 여부는 확인할 항목이다.
- 원칙 초안에 적힌 해결 방향은 `clientRequestId`를 결과와 함께 저장하고 반환해 요청 식별을 표시용 값 비교와 분리하는 것이다. 서버의 주문·결제 ID는 정본 거래 식별자로 검증하고, 재시도 중복은 별도 멱등성 정책으로 처리하도록 구분했다.
- 로컬 검증 실패만으로 취소하지 말고 서버 상태를 조회해 대조·복구한다는 내용도 있다. 통합본은 이 부분을 식별자 추가로 짧게 요약했다.

이것은 [카드번호 검색 불가 사례](#case-07)와 별개다. 해결 방향으로 적힌 항목 가운데 실제 구현·검증을 마친 범위는 추가 확인이 필요하다. 연결할 원칙은 [경계와 계약](./02_principles.md#principle-05)이다.

## 14. 임시 DB 구조의 누적

출처: [원칙 초안](../archive/README_original.md)의 「2.4 사례: 합리적인 임시 결정이 운영 구조가 된 과정」, [통합 초안](../archive/ai_coding_rewrite.md)의 「출시 뒤에 남은 긴 꼬리」. 별도 상세 자료는 [DB_SCHEMA_COMPLEXITY.md](../DB_SCHEMA_COMPLEXITY.md)에 있다.

- 온라인 중심 DB를 여러 단말과 상품군으로 확장하며 AI가 네 원칙을 제안했다. 추가형 변경, 이중 기록과 백필, 한 번에 한 축만 변경, 핵심 쓰기 로직을 DB 함수 한곳에 모으기였다.
- 초안은 이를 운영 중 데이터를 단계적으로 옮기려는 전략으로 설명한다. 이후 추가형 변경이 임시 전환 방식을 넘어 영구적인 설계 제약처럼 작용했다.
- 기존 모델을 다시 정리하기보다 컬럼과 테이블이 계속 추가됐다. 백엔드 방향이 바뀐 뒤에도 이전 모델이 남았고, 공유 DB에 기능별 도메인 모델과 변경 이력이 흩어졌다.
- 기존 구조를 마지막에 제거한다는 계획에 담당자·실행 시점·검증 조건이 없었다. 데이터 전환이 진행돼도 구조 전환은 끝나지 않았다.
- 이 사건을 AI의 한 가지 원칙 탓으로만 설명하지 않고, 적용 범위와 종료 조건을 정해 마지막 정리까지 관리하지 못한 문제로 해석한 것이 원칙 초안의 결론이다.

상세 스키마 수치·Git 이력·월별 경과는 별도 자료를 참조한다. 이 자료집에서는 반복 복사하지 않는다. 연결할 원칙은 [구조와 통합](./02_principles.md#principle-03), [임시 구조의 종료](./02_principles.md#principle-11)다.

## 15. 비개발자가 만든 프로젝트의 전체 검토

출처: [PROJECT_REVIEW_2026-09-04.md](../PROJECT_REVIEW_2026-09-04.md). 저자가 비개발자가 AI로 열심히 만든 프로젝트의 검토 자료라고 설명하며 제공했다. 검토 기준은 2026년 9월 4일 당시의 저장소 스냅샷이며, 원래 커밋 해시는 공개 자료에서 생략했다. 아래는 그 검토 기록의 요약이며 이번 자료 정리에서 코드를 다시 검증한 결과는 아니다.

### 사례의 중심

비개발자가 화면 몇 개만 만들고 끝낸 프로젝트가 아니다. API, 파트너·관리자 콘솔, 예매 화면, 데이터베이스와 배포 환경을 갖췄고, 원자적 검표와 일부 재고 잠금, 환불 요청 원장, 정산 승인, 회귀 테스트 같은 안전장치도 마련돼 있었다. 검토서에는 기본 단위 테스트 1,328개가 통과했다고 기록돼 있다. 계산·집계·페이지네이션 등 실제 동작을 검증하는 좋은 테스트도 있었다.

그런데 기능과 안전장치가 모든 실행 경로에 일관되게 연결되지는 않았다. 한 경로의 인가가 다른 진입점에는 빠지고, 환불 원장이 있어도 일부 실패가 기록되지 않으며, 롤백 함수가 있어도 실제 실패 경로에서 호출되지 않았다. 이 사례의 중심은 이런 전체 동작의 빈틈과, 그 빈틈을 기존 테스트가 발견하지 못한 이유다.

### 글에 사용할 구체적인 장면

| 장면 | 검토서에 기록된 관찰 | 증거와 범위 |
| --- | --- | --- |
| 권한 검사를 꺼도 테스트는 통과 | 임시 복사본에서 관리자 매출 조회의 권한 검사 호출을 주석 처리해도 관련 테스트 21개가 모두 통과했다. 주석 속 함수 이름을 실제 호출로 인정했기 때문이다. | 4.2·4.3. 특정 테스트의 검출력 실험이며 전체 테스트가 무의미하다는 뜻은 아님 |
| 실제 제품 대신 복사한 규칙을 검사 | 제품의 전화번호 검증을 비활성화해도 관련 테스트 7개가 통과했다. 테스트 파일에 복사한 규칙만 실행하고 있었다. | 4.2·4.4. 임시 복사본에 결함을 넣어 확인 |
| API의 인가가 DB 함수 직접 호출까지 보호하지 못함 | 소속이 없는 일반 로그인 사용자 문맥에서 다른 파트너의 테스트 매출을 조회하고 영업 마감 잠금을 생성했다. | 3.2. 실제 마이그레이션을 적용한 격리 DB의 SQL 재현. 운영 고객 데이터에 접근한 기록은 아님 |
| 취소 요청과 환불 완료를 같은 것으로 취급 | 결제 승인 뒤 발권에 실패하면 취소 요청을 보내지만, 취소 성공을 확인하지 않고 주문 삭제와 환불됐다는 응답으로 진행할 수 있었다. 이 실패는 기존 환불 재조정 원장에도 기록되지 않았다. | 3.4. 코드·호출 경로 확인. 실제 결제 API 호출이나 운영 사고 재현은 하지 않음 |
| 늦게 도착한 실패가 완료된 결제를 덮어씀 | 완료 상태로 바뀐 결제를 늦은 실패 요청이 다시 실패 상태로 바꿨다. 결제와 주문은 남지만 후속 취소도 막힐 수 있었다. | 3.5. 실제 서비스와 가짜 DB 응답을 이용한 로컬 재현. 실제 DB 동시성 실험과 구분 |
| 롤백 테스트는 있지만 전체 배포에서는 복구가 호출되지 않음 | 기존 롤백 테스트 9개가 통과했지만, 전체 배포의 기동 실패 경로에 오류를 주입하니 롤백 호출 없이 종료했다. | 3.7·4.7. 실제 스크립트 함수와 대체 명령을 이용한 로컬 재현 |

검토서에는 앱·웹 판매 규칙의 차이, 백업·스테이징 복구, 자동 실행에서 빠진 테스트와 실패 예외도 있다. 사례를 모두 본문에 나열하기보다 위 장면 중 몇 개를 골라 상황과 확인 과정을 풀어 쓸 수 있다.

### 집필할 때 구분할 것

- 기능과 테스트, 안전장치를 마련한 성과와 그 적용 범위의 빈틈을 함께 보여준다. 비개발자의 노력 부족이나 모든 테스트의 무가치함으로 결론 내리지 않는다.
- 1,328개는 검토서에 기록된 기본 단위 테스트의 합계다. 별도 실행 누락과 실패가 있으므로 전체 검증이 모두 통과했다고 쓰지 않는다.
- 격리 DB 재현, 외부 응답을 대체한 로컬 재현, 코드 확인, 구조적 위험 추론을 구분한다. 운영 서버·DB·실제 결제 API에는 접근하지 않았고, 전체 브라우저 E2E와 운영 부하 시험도 수행하지 않은 검토다.
- 문제의 발견은 수정·배포 완료나 실제 고객 피해가 있었다는 증거가 아니다. 검토서는 특정 시점의 상태이며 현재 상태를 대신하지 않는다.
- 저자의 추가 설명에 따라 이 자료를 [대표의 서비스 사례](#case-11)의 후속 검토로 연결했다. 저자가 5월 초에 처음 본 뒤 약 네 달 더 개발한 9월 초의 상태다. 4월 초부터의 전체 개발 기간은 약 다섯 달이며, 현재 1편은 1월부터 9월 초까지를 다룬다. 각 개발 참여자의 상세 역할과 개별 변경의 책임까지 검토서만으로 확정하지 않는다.

연결할 2편 논점은 [전문가의 지속적인 참여와 역할 분담](../ai_coding_part2_notes.md)이다. 초기 환경을 마련한 뒤에도 전체 흐름과 테스트의 검출력을 주기적으로 검토할 필요성을 설명하는 자료로 사용할 수 있다. 검토서 자체의 개선 방향은 현재 스택을 유지하면서 공통 인가·주문·발권·환불 경로와 검증을 점진적으로 정리하는 것이다. 초기 기술 선택이 모든 결함의 원인이라거나 전면 재작성이 필요하다는 근거로 사용하지 않는다.
