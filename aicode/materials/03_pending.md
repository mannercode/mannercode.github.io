# 확인할 내용과 후속 논점

초안을 합치면서 사실이 달라지거나 주장의 범위가 넓어지는 부분을 모았다. 아래 항목은 집필하면서 보완할 메모이며, 기존 기록만으로 결말이나 원인을 새로 확정하지 않았다.

참고 원문: [경험담](../archive/ai_coding.md), [통합 초안](../archive/ai_coding_rewrite.md), [기존 원칙 초안](../archive/README_original.md). 현재 작업본은 [1편](../ai_coding_part1.md)과 [2편 메모](../ai_coding_part2_notes.md)다.

## 1. 사실과 시간 흐름

| 항목 | 자료에 있는 내용 | 집필할 때 확인할 것 |
| --- | --- | --- |
| 합류 당시 남은 기간 | 기존 경험담·통합본은 6주, 현재 1편은 처음에는 4주 | 초기 예정일과 일정 변경 경과. 현재 1편을 6주로 되돌리지 않는다. |
| 7개월의 범위 | 2026년 1월부터 7개월이라고 소개하지만 날짜가 붙은 서사는 대부분 4월까지 | 회고의 종료 시점과 5~7월의 주요 사건. 상세 DB 자료의 월별 기록을 사용할 경우 같은 프로젝트·시스템인지도 확인한다. |
| 분석과 별도 개발 결정 | 현재 1편은 별도 개발 결정을 먼저 소개한 뒤 합류 첫날 밤의 분석으로 돌아감 | 처음의 대응 방침과 분석 이후 확정한 범위를 구분할지, 서술 순서를 옮길지 |
| 첫 출시와 교체 | 3월 초 기존 서비스 출시, 4월 말 다섯 영역 마무리라는 기록 | 4월 말 실제 배포·운영된 구성과 새 백엔드 교체 완료 여부. 두 날짜를 같은 출시로 합치지 않는다. |
| 사용자 앱의 상태 | 초기에는 필요했으나 우선순위가 밀림. iOS·Android 네이티브 사용자 앱 중단. Flutter 앱은 별도 개발 중이었다고 기록 | 네이티브 앱 중단 시점과 Flutter 앱의 이후 상태. 사용자 앱 전체가 같은 때 중단됐다고 쓰지 않는다. |
| 인력 변화 | iOS 계약 종료는 3월 초, 백엔드 개발자 해고는 4월 초, Android 개발자는 수습 평가 전 퇴사 의사 | Android 개발자의 합류·퇴사 시점, 담당을 넘긴 순서, 1인 체제의 시작 |
| GitHub 작업 관리 | 요구·결과를 작업 항목에 남기려 했으나 하루만 돌아갔다는 원문 메모 | 도입 시점과 이후 개선 여부. 저자의 새 백엔드 작업이 줄어든 시기와 연결 |
| 대표의 별도 서비스 | 4월 초부터 한 달 개발. Supabase·Next.js·Vercel. RN 선택을 둘러싼 갈등 | 최종 합의, 채택한 스택, 기존 시스템과의 관계, 저자가 실제 맡은 범위와 결과 |
| 카드번호 검색 | 검색할 수 없게 마스킹해 저장하면서 검색 UI를 만듦. 반복해서 정상이라고 보고 | 실제 테스트 시나리오와 결과, 원인 확인, 이후 바꾼 검증 방법 |
| 결제 응답 식별자 | 기존 README는 정상 결제가 취소됐다고 서술. 통합본은 취소될 수 있었다고 서술 | 실제 장애였는지 코드 검토에서 찾은 위험인지. 발생·재현 증거와 해결 완료 범위 |
| 키오스크 검증 | 에뮬레이터만 사용, 사람이 단말에 설치해 확인. README에는 이틀 동안 끝내지 못했다고 기록 | 실기기 환경을 어떻게 개선했는지, 최종 해결 여부와 시점 |
| DB 전환 | 임시 모델·이중 기록·추가형 변경이 누적됐고 제거 조건이 없었다는 설명 | 어떤 시스템의 전환인지, 실제로 제거·검증한 범위와 아직 남은 작업 |

통합 초안은 카드번호 검색 오류의 이유를 구현과 테스트가 같은 전제를 공유했기 때문이라고 설명한다. 경험담 원문에 직접 적힌 관찰은 검색 불가 상태와 반복된 정상 보고다. 실제 테스트를 확인한 결론인지 사후 해석인지 구분해야 한다.

## 2. 경험치와 인과관계

| 주장·표현 | 현재 근거 | 보완할 내용 |
| --- | --- | --- |
| AI 분석 하루, 직접 했다면 일주일 | 실제 분석 시간과 저자의 반사실적 추정 | 분석이 틀린 부분도 있었음을 함께 유지. 동일 조건의 측정으로 바꾸지 않는다. |
| 커버리지 100% | 시드 프로젝트에 통합 테스트와 일부 단위 테스트가 있었다는 기록 | 측정 항목, 대상 모듈, 제외 규칙. 전체 기능이 검증됐다는 뜻으로 사용하지 않는다. |
| 구조가 나쁘면 변경 비용 세 배 | 기존 README 2.3의 개인 경험 | 시간·토큰·재작업 중 무엇을 비교했는지와 대상. 자료가 없으면 체감으로 표현한다. |
| 혼자 개발하는 편이 더 생산적 | AI 활용 뒤 1인 개발이 가능해졌다는 경험 | 기능 축소, 모노레포 정리, 의사결정·조율 방식도 함께 바뀌었다. 같은 범위·조건의 인원 비교인지는 별개다. |
| 네 앱이어도 업무량은 네 배가 아님 | 공통 요구사항과 AI 구현을 전제로 한 저자의 판단 | 실제 검증·빌드·배포·하드웨어 업무와 수행 결과. 거부나 퇴사만으로 적응 실패를 확정하지 않는다. |
| AI를 쓰지 않은 것이 기존 팀의 문제 | 대표가 전한 태도와 저자의 프로젝트 평가 | 기술 분산, 요구사항·일정 관리, 완성도 판단 등의 문제도 있었다. AI 미사용을 모든 실패의 원인으로 묶지 않는다. |
| 대표가 AI의 지시를 따르게 했다 | 저자의 제안보다 AI 제안이 신뢰받았다는 갈등 | 제품·사업·기술 결정권의 합의와 실제 판단 근거. 대표도 사업의 결과를 감수하므로 책임 유무만으로 기술 결정권을 설명하기 어렵다. |
| RN의 플랫폼 차이·배포·성능 | 원문의 개인 경험과 해당 키오스크의 제약 | 구체 API·단위·버전·배포 방식·단말 조건. 일반적인 프레임워크 평가가 필요할 때 별도로 확인한다. |
| 기존 기술 스택에 팀장 선호가 반영됨 | 통합본의 저자 평가 | 당시 요구·제약과 선택 이유가 확인된 사실인지, 구조를 본 뒤의 추정인지 구분 |

직접 들은 말과 전해 들은 말도 구분한다. 해고 통보의 계기가 된 발언은 저자가 직접 들은 것으로 기록돼 있고, 기존 팀장의 AI 태도와 사업을 접을까 했다는 대표의 생각은 대표에게 들은 설명이다. 정확한 대화를 인용할지는 원문과 기억을 대조해 결정한다.

## 3. 문장 차이를 넘어 입장이 달라진 부분

단순한 중복으로 지우면 저자가 고민하던 논점까지 사라질 수 있어 별도로 남긴다. 특히 최근 2편 메모의 주장을 기존 통합본의 표현으로 덮어쓰지 않았다.

| 논점 | 초안별 차이 | 집필에서 정할 부분 |
| --- | --- | --- |
| AI보다 뛰어나야 하는가 | 통합본은 모든 기술을 AI보다 잘 알 필요가 없다고 설명. 최근 2편 메모는 “AI 이상의 능력”, AI가 생각하지 못한 논리와 통찰을 강조 | 기술 리더에게 필요한 우위가 개별 구현, 기술 판단, 문제 발견, 통합 중 무엇인지 구체화 |
| 남는 일과 역할 | 기존 원칙·통합본은 작업 종류로 역할을 고정하지 않으며 결과 책임을 강조. 최근 메모는 AI가 못 하거나 놓친 일을 찾아 직접 처리하는 팀장의 역할을 강조 | 추상적인 책임과 실제로 채워야 하는 역량·일을 어떻게 연결할지 |
| 주니어 비유 | 기존 초안은 유능한 주니어에 비유하며 능력·맥락·책임의 차이를 설명. 최근 메모는 팀원으로 표현 | “주니어”가 전달하려는 특성, 사람이 성장하며 책임을 축적하는 차이를 어디까지 설명할지 |
| 모두 풀스택이 되어야 하는가 | 경험담 원문에는 풀스택을 지향해야 한다는 표현. 통합본은 밀접한 기능과 작은 팀에서 책임 범위를 넓히는 것으로 한정 | 보편적인 진로 주장인지, 해당 프로젝트에서 분업 비용이 바뀐 경험인지 |
| 기술 자체는 중요하지 않은가 | 경험담 원문에는 한 줄도 코딩할 필요가 없다면 기술은 중요하지 않았다고 기록. 통합본은 당시 생각이 절반만 맞았다고 회고 | 당시 느낀 해방감과 이후 기술 판단의 필요성을 깨달은 경험을 연결할 근거 |
| 책임감과 성장 | 원문은 검증하지 않은 팀원의 태도를 강하게 평가. 통합본은 경험 부족과 책임 회피를 구분하고 회사의 육성 책임까지 확장 | 실제 행동·검증 기준·피드백을 바탕으로 인물 평가와 성장 문제의 범위를 정하기 |
| 개발자의 일자리 | 경험담 말미·통합본은 구현 외에 맡을 일이 없는 개발자의 자리가 줄 수 있다고 주장. 기존 README는 자기 범위에서 기술 리더 역할을 연습하는 데 집중 | 개인의 준비에 관한 주장과 채용·고용 전망을 구분해 어느 편에서 다룰지 |

2편 메모의 “AGENTS.md를 잘 쓰는 것과 개발자의 통찰은 다르다”는 문제의식도 유지한다. 이를 단순한 프롬프트·지침 작성 요령으로 바꾸지 않고, 어떤 공학적 판단이 필요했는지 사례와 연결할 수 있다.

## 4. 후속 글로 넓힐 수 있는 논점

### 기업과 주니어의 성장 경로

출처: 통합 초안 「주니어의 성장 경로를 다시 설계해야 한다」, 기존 원칙 초안 4.4와 후속 논점.

- 잘 정의된 구현 업무가 회사에 대한 기여이자 학습 경로였다. AI가 이를 수행하면 입문자의 연습 기회와 채용 이유가 함께 줄어들 수 있다는 문제의식이다.
- 시니어가 직접 AI로 처리하는 비용보다 주니어에게 설명하고 결과를 다시 검토하는 비용이 클 때, 작은 스타트업의 채용이 어려워질 수 있다는 주장이 있다.
- 회사가 미래의 숙련자를 필요로 한다면 작은 기능의 요구사항부터 배포·운영·장애 회고까지 책임질 기회와 피드백을 제공해야 한다는 제안도 있다.
- 실제 채용 시장의 변화는 한 팀의 경험만으로 확정하지 않는다. 개인의 연습 방법은 [성장 원칙](./02_principles.md#principle-12)에 두고 제도·비용 문제를 여기서 확장할 수 있다.

### 대학 교육의 수직·수평 확장

출처: 경험담 원문 말미의 대학 교육 메모, 통합 초안 「대학은 무엇을 가르쳐야 하는가」와 「기술적 깊이를 바탕으로 영역을 넓힌다」.

- 수직 확장은 구현에서 요구사항·아키텍처·검증·운영·기술 리더십까지 판단과 책임의 범위를 넓히는 것이다.
- 수평 확장은 경제·디자인·건축 등 다른 도메인으로 문제 이해의 범위를 넓히는 것이다.
- 프로젝트의 전체 생애주기를 가르치려면 실제 개발·실패·운영 경험을 가진 교수자와 오래 유지되는 프로젝트가 필요하다는 주장이 있다.
- 대학이 이런 조건을 충분히 마련하기 어려워 기존 전공을 연결하는 수평 확장이 먼저 일어날 수 있다는 전망은 원문의 가설이다.
- 컴퓨터공학의 깊이를 갖추지 못한 채 도메인과 AI 활용만 가르친다면 각 도메인 전공에서 AI를 배우는 것과 차이가 무엇인지 묻게 된다는 문제의식이 있다. “정체성의 해체”라는 강한 표현도 이 논점에 포함된다.
- 원문은 알고리즘·자료구조·언어·운영체제·네트워크·DB라는 기반 위에 설계·성능·보안·신뢰성·운영 판단을 연결할 것을 제안한다. 대학의 현재 역량과 교육 성과는 별도의 근거가 필요한 부분이다.

### 기획자·디자이너·비개발자의 역할

출처: 경험담 원문의 커뮤니케이션 비용·대표 사례, 통합 초안의 역할 경계, 기존 원칙 초안의 후속 질문. 최근 생각은 [2편 메모](../ai_coding_part2_notes.md)의 「비개발자는 처음의 선택을 검증하기 어렵다」를 참고한다.

- 기획 의도에서 동작하는 결과물을 빠르게 만들 수 있을 때 기획자·디자이너는 어떤 판단과 완료 기준을 맡는가?
- 백엔드·프론트엔드·UX가 책임 범위를 넓히는 일과 전문성의 필요성을 어떻게 함께 설명할 것인가?
- 비개발자도 첫 서비스를 만들 수 있지만, 어떤 조건을 고려해야 하는지 모르면 AI가 제안한 기술 스택과 도구를 평가하기 어렵다는 주장이 있다.
- 프로젝트가 커진 뒤 드러나는 운영·성능·연동·변경 비용과 초기 선택을 연결해 설명할 수 있다.
- 최근 메모의 결제·환불·입장 상태, 권한, DB 구조와 피상적 테스트 사례에는 나중에 실제 프로젝트 파일로 근거를 보충한다는 표시가 있다. 아직 근거가 첨부된 사례로 취급하지 않는다.

### 소프트웨어 산업과 아키텍처 선택

별도 초안 [AI_AFTER_SOFTWARE.md](../AI_AFTER_SOFTWARE.md)에 이미 모여 있다. 생산 비용 하락과 프로젝트 수요, MSA와 모듈러 모놀리스의 선택 기준을 다룬다. 이곳에 본문을 다시 복사하지 않고 후속 글 자료로 연결한다.
