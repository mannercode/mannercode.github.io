# 확인할 내용과 후속 논점

초안을 합치면서 사실이 달라지거나 주장의 범위가 넓어지는 부분을 모았다. 아래 항목은 집필하면서 보완할 메모이며, 기존 기록만으로 결말이나 원인을 새로 확정하지 않았다.

참고 원문: [경험담](../archive/ai_coding.md), [통합 초안](../archive/ai_coding_rewrite.md), [기존 원칙 초안](../archive/README_original.md). 현재 작업본은 [1편](../ai_coding_part1.md)과 [2편 메모](../ai_coding_part2_notes.md)다.

| 분석과 별도 개발 결정 | 현재 1편은 합류 첫날 밤의 분석 뒤에 출시 범위와 별도 개발 결정을 배치함 | 이후 편집에서도 분석·범위 결정·개발 착수의 흐름을 유지한다. |

| 초기 범위 결정과 AI 활용 | 원문에는 대표와 최소 요구사항을 정리하고, AI의 기존 시스템 분석 결과를 재개발 설명에 활용했다는 기록이 있음 | 구체적인 초기 출시 기능 목록은 미확인이다. AI가 요구사항 정리나 범위별 계획에 도움을 줄 수 있다는 일반론을 실제로 수행한 일로 바꾸지 않는다. [사례 04](./01_experiences.md#case-04) 참조. |
| 첫 출시와 교체 | 3월 초 기존 서비스 출시. 저자의 추가 설명에 따라 4월 말의 다섯 영역 마무리를 레거시 안정화로 서술 | 당시 실제 배포·운영된 세부 구성과 새 백엔드 교체 완료 여부는 별개다. 두 날짜를 같은 출시로 합치지 않는다. |
| 4월의 별도 행사 | 저자가 추가로 밝힌 경험. 기존 전시 현장 외의 행사 준비에서 큰 위기를 겪었고, 저자는 잘 극복했다고 평가 | 구체적인 위기의 내용과 대응은 아직 기록되지 않아 현재 1편에서는 생략했다. 보완할 때 행사·장소는 익명화한다. |
| 4월의 작업과 수면 | 저자는 하루 18시간씩 일했던 것 같다고 회고. 세 시간 수면과 여덟 시간 정도의 작업을 한 달 동안 반복했고, 할 일이 명확하고 커뮤니케이션이 거의 필요 없어 코드에 집중할 수 있었다고 설명 | 정확한 근무 시간 집계가 아닌 회고다. 세 시간은 한 번에 잔 시간이며 하루 총수면 시간으로 쓰지 않는다. 새 백엔드·사용자 앱 개발 때 두세 시간마다 깨서 AI에게 다음 일을 지시한 사례와 임의로 합치지 않는다. |
| 5월 이후 효율과 의욕의 변화 | 저자는 대표의 빠른 기능 구현에 보조를 맞추는 상황이 되면서 효율과 의욕이 급감했다고 설명. 일하는 방식과 협업 방식이 프로젝트 전체에 영향을 줬다는 회고 | 효율 변화는 저자의 체감이며 수치로 측정한 비교가 아니다. 4월의 장시간 작업만으로 생산성 향상을 설명하지 않고, 업무 범위의 명확성과 조율 방식도 함께 다룬다. |
| 사용자 앱의 상태 | 초기에는 필요했으나 우선순위가 밀림. iOS·Android 네이티브 사용자 앱 중단. 별도로 개발하던 Flutter 앱은 이후 대표가 가져온 프로젝트 때문에 폐기했다고 저자가 확인 | 네이티브 앱 중단의 정확한 시점은 별도 확인 대상이다. 네이티브 앱 중단과 Flutter 앱 폐기를 같은 사건으로 합치지 않는다. |
| 별도로 준비하던 NestJS·Flutter 프로젝트의 이후 상태 | 저자는 기존 서비스 수습과 병행해 NestJS 백엔드와 Flutter 앱을 별도로 준비했다. 2026년 9월 10일, 대표가 새로 가져온 프로젝트 때문에 둘 다 폐기했고 이후 개발은 대표가 주도했다고 설명 | 폐기 여부와 이유, 이후 개발의 주체는 저자의 설명으로 확인했다. 1편의 ‘대표가 개발을 주도하다’에 반영했다. 레거시 안정화를 NestJS·Flutter로 교체한 결과로 서술하지 않는다. |
| 인력 변화 | iOS 계약 종료는 3월 초, 백엔드 개발자 해고는 4월 초, Android 개발자는 수습 평가 전 퇴사 의사 | Android 개발자의 합류·퇴사 시점, 담당을 넘긴 순서, 1인 체제의 시작 |
| 저자의 해고 | 저자는 결국 자신도 해고됐다고 추가로 설명. 현재 1편 맺음말에 사실을 반영 | 해고 통보와 실제 근무 종료 시점, 대표가 설명한 이유와 저자의 해석은 미기재다. 9월 검토와의 선후 관계나 해고가 불가피했다는 판단을 임의로 덧붙이지 않는다. |
| GitHub 작업 관리 | 요구·결과를 작업 항목에 남기려 했으나 하루만 돌아갔다는 원문 메모 | 도입 시점과 이후 개선 여부. 저자의 새 백엔드 작업이 줄어든 시기와 연결 |
| 대표의 별도 서비스 | 4월 초부터 한 달가량 개발한 결과물을 5월 초에 처음 봄. 저자가 별도로 개발하던 NestJS·Flutter는 폐기됐고, 이후 개발은 대표가 주도했으며 저자는 기능 추가에 보조를 맞춤. 약 네 달 뒤인 9월 초에 전체 검토 | 2026년 9월 10일 저자의 명시적인 정정을 우선한다. 저자가 개발을 주도했다고 쓴 이전 해석은 잘못이었다. 초기 기술 선택과 이후 협의 과정, 개별 변경의 담당은 별도로 구분한다. |
| 5월 첫 실행과 기능 확장 | 저자는 대표가 다 됐다고 한 프로젝트를 5월 초 직접 실행했을 때 1월 프로젝트와 비슷한 완성도였다고 평가. 당장 사용하지 않을 기능까지 실제 시스템에 붙이고, 충분히 검증하지 않은 채 대충 동작하면 완료로 받아들인 것을 가장 큰 잘못으로 지적 | 5월의 구체적인 결함과 당장 운영에 쓰지 않을 기능 목록은 미기재다. 9월에 확인한 결함을 5월에도 확인했다고 소급하지 않는다. 대표가 이 평가를 인정하지 않으리라는 말은 저자의 생각이다. |
| 세일즈 요구와 목업 대안 | 대표는 몇 개 없는 기능으로는 세일즈를 할 수 없다고 설명. 저자는 그 판단을 받아들여도 프론트엔드에서만 동작하는 목업으로 보여 주고 백엔드·DB 연결을 뒤로 미룰 수 있었다고 평가 | 목업을 실제로 구현했거나 당시 대표에게 제안했는지는 미기재다. 세일즈에 필요한 기능의 수나 영업 성과를 저자가 검증한 사실로 쓰지 않는다. |
| 협의 없이 진행된 리팩터링 | 저자가 행사를 마치고 일주일 쉬는 동안 대표가 AI의 전략으로 여러 에이전트를 돌렸다는 추가 회고. [사례 11의 후속 경험](./01_experiences.md#case-11-refactoring) | 5월 초 첫 결과물을 본 뒤 이어진 개발 과정의 사건이다. 정확한 행사와 리팩터링의 시점은 아직 기록되지 않아 현재 본문에는 월을 붙이지 않았다. |
| 동시번역 기능의 동작 설계 | 대표가 행사를 대비해 문장 단위 발화·수동 전송·수신 측 번역 기능을 추가했고, AI가 발언 중 연속 전송·번역 방식을 제안하지 않았다는 저자의 설명. 저자는 대표에게 동시번역을 어떻게 할 것인지, 자신이 없는 동안 많이 진행된 것 같은데 자신이 신경 써야 하는지 물었고, 대표는 신경 쓸 필요 없다고 답했다. [사례 메모](./01_experiences.md#case-11-translation) | 아예 말을 하지 않았거나 역할 확인도 하지 않은 것으로 서술하지 않는다. 행사 시점, 당시 사용한 API와 대상 언어, 이후 실제 변경 여부는 미기재다. 저자가 말한 품질 개선은 발언 종료 후 수동 전송을 발언 중 연속 전송·번역으로 바꾸는 동작 설계를 가리킨다. |
| 카드번호 검색 | 검색할 수 없게 마스킹해 저장하면서 검색 UI를 만듦. 반복해서 정상이라고 보고 | 실제 테스트 시나리오와 결과, 원인 확인, 이후 바꾼 검증 방법 |
| 결제 응답 식별자 | 기존 README는 정상 결제가 취소됐다고 서술. 통합본은 취소될 수 있었다고 서술 | 실제 장애였는지 코드 검토에서 찾은 위험인지. 발생·재현 증거와 해결 완료 범위 |
| 키오스크 검증 | 에뮬레이터만 사용, 사람이 단말에 설치해 확인. README에는 이틀 동안 끝내지 못했다고 기록 | 실기기 환경을 어떻게 개선했는지, 최종 해결 여부와 시점 |
| DB 전환 | 임시 모델·이중 기록·추가형 변경이 누적됨. 상세 검토에는 안정화 뒤 제거한다는 기술적 조건은 있었으나 담당자·실행 시점·대조 기준·제거 후 테스트가 부족했다고 기록 | 조건이 전혀 없었다고 확대하지 않는다. 실제로 제거·검증한 범위와 아직 남은 작업은 별도로 확인한다. |

통합 초안은 카드번호 검색 오류의 이유를 구현과 테스트가 같은 전제를 공유했기 때문이라고 설명한다. 경험담 원문에 직접 적힌 관찰은 검색 불가 상태와 반복된 정상 보고다. 실제 테스트를 확인한 결론인지 사후 해석인지 구분해야 한다.

## 2. 경험치와 인과관계

| 주장·표현 | 현재 근거 | 보완할 내용 |

### 리팩터링과 AI 능력에 관한 주장 검토

2026년 9월 8일, 저자가 의견을 무비판적으로 반영하지 말고 타당성을 검토해 달라고 요청해 다음을 확인했다. 아래는 집필을 위한 검토 메모이며, 저자가 당시 수행한 분석이나 발언으로 옮기지 않는다.

- **이 사례가 뒷받침하는 범위:** 저자의 회고와 에이전트 검토에 따르면 수행된 리팩터링은 필요한 구조 개선에 미치지 못했다. 저자는 이후 검토를 맡긴 에이전트도 개선이 미미하다고 지적했지만 더 근본적인 방안을 제시하지 못했다고 추가 설명했다. 따라서 문제 진단을 근거로 전략 수립 능력까지 입증됐다고 해석하지 않는다. 처음의 전략이 부족했고 사후 검토도 근본적인 대안으로 이어지지 못했다는 비판은 이 경험으로 뒷받침되지만, AI 전반의 영구적인 능력 한계나 학습 데이터에 의한 원인까지 확정하지는 않는다. 당시 모델·입력·지침·실행 설정·계획과 완료 보고 전문, 후속 검토의 요청 범위는 확인하지 못했으며, 비용을 아끼려 했다는 원인도 입증되지 않았다.
- **규모와 속도:** 넓은 구조를 개선하는 전략과 작은 단계로 변경하는 방법은 함께 사용할 수 있다. 리팩터링의 목적은 이해와 변경을 쉽게 만드는 것이며, 작업량 자체가 성과의 기준은 아니다. 기능 생성 속도가 구조 악화로 이어진다는 설명에는 검토와 정리가 그 속도를 따라가지 못했다는 조건이 필요하다. 이 조건은 편집상의 인과 구분이며 해당 프로젝트에서 속도와 복잡도를 계량한 결과가 아니다. [Martin Fowler의 정의](https://martinfowler.com/bliki/DefinitionOfRefactoring.html)와 [작은 단계로 구조를 바꾸는 사례](https://martinfowler.com/articles/preparatory-refactoring-example.html)를 참고했다.
- **계획과 자기 검토:** GPT-4를 사용한 2023년 연구에서는 계획의 자기 비판이 성과를 악화시키고 잘못된 승인을 내는 문제가 보고됐다. 반면 2025년 공개된 다른 연구에서는 2024년 10월 모델들을 대상으로 Blocksworld·Logistics·Mini-grid의 계획 성능을 자기 비판으로 개선했다. 모델과 방법에 따른 결과를 구분해야 하며, 이 연구들로 2026년 특정 모델의 실제 프로젝트 설계 능력을 확정할 수 없다. [2023년 계획 검증 연구](https://arxiv.org/abs/2310.08118), [2025년 계획 개선 연구](https://arxiv.org/abs/2512.24103).
- **학습과 추론:** 학습으로 얻은 능력이라는 사실과 새로운 문제에서 추론할 수 있는지는 서로 다른 질문이다. DeepSeek-R1 연구는 사전 학습한 모델에 사람의 추론 과정 예시를 직접 지도하지 않는 강화학습을 적용해 수학·경쟁 프로그래밍 등 검증 가능한 과제의 추론 성능을 높였다고 보고했다. 이 결과는 인간 데이터의 단순 모방으로 모든 전략적 한계를 설명하기 어렵다는 근거이며, 실제 소프트웨어 아키텍처에서 인간보다 우월하다는 증거로 쓰지 않는다. [Nature 논문, 2025](https://www.nature.com/articles/s41586-025-09422-z).
- **GPT 6.0과 AGI:** 확인한 [GPT-6 Astra 공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-astra)와 [공식 모델 안내](https://developers.openai.com/api/docs/guides/latest-model)에서는 “AGI의 시작”이라는 주장을 확인하지 못했다. 이를 그런 발언이 어디에도 없었다는 뜻으로 확대하지 않는다. AGI 여부를 논하려면 발언 출처와 평가 기준이 별도로 필요하며, 이 프로젝트의 실패만으로 결론을 내릴 수 없다.

### 1편 대조 검토와 정정 — 2026년 9월 9일

저자가 과장·없는 발언·추측이 들어갔는지 전체 검토를 요청했고, 이어 감상적인 제목과 꾸민 문장도 줄여 달라고 했다. 경험담 원문, 통합 초안, 기존 원칙 초안과 현재 확인 가능한 대화 내용을 대조했다. 대화 전체의 원문을 빠짐없이 확인한 검토는 아니므로, 문서에 없는 내용의 출처까지 모두 판별했다고 할 수 없다. DB 전환과 9월 검토의 세부 내용은 각 검토 자료의 근거와 범위를 확인했다.

검토 과정에서 보관 문서에서 찾지 못한 내용을 AI의 추가로 단정해 삭제하는 오류가 있었다. 저자는 머메이드 그림을 직접 요청했다고 확인했다. 그림과 함께, 같은 이유로 삭제했던 시스템 분석 내용·백오피스 개발 당시의 기대·수면 중 행동도 복원했다. 뒤의 세 항목은 출처가 확인됐다는 뜻이 아니라, 삭제 근거가 부족해 기존 원고를 보존한 것이다.

참고자료에 같은 설명이 반복된다는 사실만으로 독립적인 근거가 늘어난 것으로 보지 않는다. 사건을 외부에서 입증하거나 제품 코드를 다시 검증한 작업도 아니다.

| 1장 시스템 그림 | 저자가 요청한 그림을 보관 문서에서 설명을 찾지 못했다는 이유로 근거 없는 추가로 판단했다. | 저자의 확인에 따라 기존 머메이드 그림과 연결 경로 설명을 복원했다. |
| 1장 AI 분석 | DB 테이블·API·호출 앱을 연결해 분석했다는 문장의 대화 출처를 확인하지 못했다. AI가 추가했다고 단정한 판정은 철회한다. | 삭제했던 문장을 복원했다. 출처는 확인 대상으로 남긴다. |
| 2·4장 백엔드 개발자 | 원문에서 초기 API 연동 직후 나온 검토 여부 확인 대화가, 현재 구성에서는 3월 출시 뒤에 처음 한 대화처럼 읽혔다. | 2장 초기 연동 장면으로 옮기고, 4장에서는 앞서 확인한 사실임을 밝혔다. |
| 2장 백오피스 개발 당시의 기대 | 혼자서 많은 일을 할 수 있으리라 기대했다는 문장의 대화 출처를 확인하지 못했다. AI가 보탰다고 단정한 판정은 철회한다. | 삭제했던 문단을 복원했다. 출처는 확인 대상으로 남긴다. |
| 3장 수면 중 행동 | 자다 깨어 완료 보고를 확인하고 다시 잤다는 세부 행동과 동기의 대화 출처를 확인하지 못했다. AI가 보탰다고 단정한 판정은 철회한다. | 수정 전 두 문단을 복원했다. 출처는 확인 대상으로 남긴다. |
| 5장 DB 전환 | 담당자·실행 시점·검증 조건이 정해지지 않았다고 뭉뚱그렸다. 상세 검토에는 안정화 뒤 제거한다는 기술적 조건은 있었다고 기록돼 있다. | 조건의 존재와 운영상 준비 부족을 구분하고 검토 자료를 연결했다. |
| 5장 대표에 대한 평가 | 대표가 결과를 모른다거나 개발자의 심정을 이해하지 못한다고 내면을 확정하는 표현이 있었다. | 저자의 인식과 추측임을 드러냈다. |
| 5장 동시번역 | 요구사항을 바꾸는 대안을 실제로 동작 설계를 바꿀 수 있었다는 결과처럼 단정했다. 실제 변경·검증 기록은 없다. | 검토할 수 있었던 대안으로 표현했다. 저자가 역할을 물었고 대표가 신경 쓸 필요 없다고 답한 대화는 유지했다. |
| 6장 작업 주체 | 대표가 5개월 동안 기능·테스트·운영 장치를 만들었다는 문장이 개별 작업을 모두 대표에게 귀속하는 것으로 읽힐 수 있었다. | 당시 저자가 개발을 주도했다고 고친 것도 잘못된 해석이었다. 9월 10일 저자의 정정에 따라 대표가 개발을 주도하고 저자는 그 작업에 보조를 맞춘 것으로 바로잡았다. 개별 변경의 담당은 추가하지 않았다. |
| 제목·문장 | 감상적인 부제, 긴 수식, 반복되는 결론과 교훈이 많았다. | 제목을 내용 중심으로 바꾸고 중복 설명을 줄였다. ‘8개월’로 표기를 통일했다. |

직접 인용한 백엔드 개발자의 발언은 경험담 원문에 있다. 첫날 대화와 부실공사 비유는 보관 자료에서 확인했고, 4월의 수면과 작업·5월의 거부감·동시번역 대화·대표가 일정을 태만으로 받아들였을 가능성은 현재 확인 가능한 저자의 발언에도 있다. 이전 팀장의 자신감과 해고 뒤 타인의 평가에 관한 문장은 당시 추측으로 구분했으며, 대화 출처까지 확인한 것은 아니다. 9월 10일 구성 정리에서는 검토 결과와 직접 연결되지 않는 이전 팀장의 자신감 추측을 삭제했다. 해고 뒤 타인의 평가에 관한 문장은 저자의 추측으로 유지했다.

당시에는 복원한 세 항목의 출처 외에도 미술관의 4주 기한을 넘긴 뒤 납품·계약 경과, 별도 NestJS·Flutter 프로젝트의 이후 상태, Android 개발자의 퇴사 시점과 이유, 저자의 해고 시점과 이유를 확인 대상으로 남겼다. 이 가운데 NestJS·Flutter 프로젝트는 대표의 새 프로젝트 때문에 모두 폐기했다고 저자가 9월 10일 확인했다. 나머지 확인 대상은 [사실과 시간 흐름](#facts)에 남아 있다. 이 목록이 대화 전체에 대한 확인을 마쳤다는 뜻은 아니다.

## 3. 문장 차이를 넘어 입장이 달라진 부분

단순한 중복으로 지우면 저자가 고민하던 논점까지 사라질 수 있어 별도로 남긴다. 특히 최근 2편 메모의 주장을 기존 통합본의 표현으로 덮어쓰지 않았다.

| 논점 | 초안별 차이 | 집필에서 정할 부분 |
| --- | --- | --- |
| AI보다 뛰어나야 하는가 | 통합본은 모든 기술을 AI보다 잘 알 필요가 없다고 설명. 최근 2편 메모는 “AI 이상의 능력”, AI가 생각하지 못한 논리와 통찰을 강조 | 기술 리더에게 필요한 우위가 개별 구현, 기술 판단, 문제 발견, 통합 중 무엇인지 구체화 |
| 남는 일과 역할 | 기존 원칙·통합본은 작업 종류로 역할을 고정하지 않으며 결과 책임을 강조. 최근 메모는 AI가 못 하거나 놓친 일을 찾아 직접 처리하는 팀장의 역할을 강조 | 추상적인 책임과 실제로 채워야 하는 역량·일을 어떻게 연결할지 |
| 주니어 비유 | 기존 초안은 유능한 주니어에 비유하며 능력·맥락·책임의 차이를 설명. 최근 메모는 팀원으로 표현 | “주니어”가 전달하려는 특성, 사람이 성장하며 책임을 축적하는 차이를 어디까지 설명할지 |
| 모두 풀스택이 되어야 하는가 | 경험담 원문에는 풀스택을 지향해야 한다는 표현. 통합본은 밀접한 기능과 작은 팀에서 책임 범위를 넓히는 것으로 한정 | 보편적인 진로 주장인지, 해당 프로젝트에서 분업 비용이 바뀐 경험인지 |
| 기술 자체는 중요하지 않은가 | 경험담 원문에는 한 줄도 코딩할 필요가 없다면 기술은 중요하지 않았다고 기록. 통합본은 당시 생각이 절반만 맞았다고 회고 | 당시 느낀 해방감과 이후 기술 판단의 필요성을 깨달은 경험을 연결할 근거 |
| 책임감과 성장 | 원문은 검증하지 않은 팀원의 태도를 강하게 평가. 통합본은 경험 부족과 책임 회피를 구분하고 회사의 육성 책임까지 확장 | 실제 행동·검증 기준·피드백을 바탕으로 인물 평가와 성장 문제의 범위를 정하기 |
| 개발자의 일자리 | 경험담 말미·통합본은 구현 외에 맡을 일이 없는 개발자의 자리가 줄 수 있다고 주장. 기존 README는 자기 범위에서 기술 리더 역할을 연습하는 데 집중 | 개인의 준비에 관한 주장과 채용·고용 전망을 구분해 어느 편에서 다룰지 |

2편 메모의 “AGENTS.md를 잘 쓰는 것과 개발자의 통찰은 다르다”는 문제의식도 유지한다. 이를 단순한 프롬프트·지침 작성 요령으로 바꾸지 않고, 어떤 공학적 판단이 필요했는지 사례와 연결할 수 있다.

## 4. 후속 글로 넓힐 수 있는 논점

### 기업과 주니어의 성장 경로

출처: 통합 초안 「주니어의 성장 경로를 다시 설계해야 한다」, 기존 원칙 초안 4.4와 후속 논점.

- 잘 정의된 구현 업무가 회사에 대한 기여이자 학습 경로였다. AI가 이를 수행하면 입문자의 연습 기회와 채용 이유가 함께 줄어들 수 있다는 문제의식이다.
- 시니어가 직접 AI로 처리하는 비용보다 주니어에게 설명하고 결과를 다시 검토하는 비용이 클 때, 작은 스타트업의 채용이 어려워질 수 있다는 주장이 있다.
- 회사가 미래의 숙련자를 필요로 한다면 작은 기능의 요구사항부터 배포·운영·장애 회고까지 책임질 기회와 피드백을 제공해야 한다는 제안도 있다.
- 실제 채용 시장의 변화는 한 팀의 경험만으로 확정하지 않는다. 개인의 연습 방법은 [성장 원칙](./02_principles.md#principle-12)에 두고 제도·비용 문제를 여기서 확장할 수 있다.

### 대학 교육의 수직·수평 확장

출처: 경험담 원문 말미의 대학 교육 메모, 통합 초안 「대학은 무엇을 가르쳐야 하는가」와 「기술적 깊이를 바탕으로 영역을 넓힌다」.

- 수직 확장은 구현에서 요구사항·아키텍처·검증·운영·기술 리더십까지 판단과 책임의 범위를 넓히는 것이다.
- 수평 확장은 경제·디자인·건축 등 다른 도메인으로 문제 이해의 범위를 넓히는 것이다.
- 프로젝트의 전체 생애주기를 가르치려면 실제 개발·실패·운영 경험을 가진 교수자와 오래 유지되는 프로젝트가 필요하다는 주장이 있다.
- 대학이 이런 조건을 충분히 마련하기 어려워 기존 전공을 연결하는 수평 확장이 먼저 일어날 수 있다는 전망은 원문의 가설이다.
- 컴퓨터공학의 깊이를 갖추지 못한 채 도메인과 AI 활용만 가르친다면 각 도메인 전공에서 AI를 배우는 것과 차이가 무엇인지 묻게 된다는 문제의식이 있다. “정체성의 해체”라는 강한 표현도 이 논점에 포함된다.
- 원문은 알고리즘·자료구조·언어·운영체제·네트워크·DB라는 기반 위에 설계·성능·보안·신뢰성·운영 판단을 연결할 것을 제안한다. 대학의 현재 역량과 교육 성과는 별도의 근거가 필요한 부분이다.

### 학생의 AI 학습 비용과 실습 기회

저자가 추가한 논점은 [2편 메모 「학생의 AI 학습에는 금전적 지원도 필요하다」](../ai_coding_part2_notes.md#student-ai-access)에 정리했다. 컴퓨터 구입 이후 반복 연습에 추가 사용료가 거의 들지 않던 조건과, AI를 충분히 사용하며 시행착오를 겪는 데 지속적인 비용이 드는 조건의 차이를 다룬다. 개인의 성장 방법에 더해 학교·기업 등의 학습 비용 지원을 논의할 수 있다.

저자는 2026년 9월 기준으로 월 15만 원을 이런 실습의 최소 비용으로 본다. 월 200달러 요금제 수준의 사용량은 필요하겠다는 판단은 여러 프로젝트의 개발과 분석·검토를 한 달 정도 함께 맡겨 본 경험에서 나온 추정이라고 추가로 설명했다. 필요한 사용량을 측정해 산출한 금액이나 검증된 학습 기준으로 서술하지 않고, 당시 작업 규모를 전제로 한 경험적 추정으로 유지한다.

상품 가격은 [OpenAI 공식 요금 안내](https://learn.chatgpt.com/docs/pricing)에서 2026년 9월 7일 확인했다. Pro 20x의 월 200달러라는 가격에 대한 출처로 인용하며, 그 정도 요금제의 사용량이 실습에 필요하다는 저자의 추정을 입증하는 자료로 사용하지 않는다. 과거의 공평성은 도구 비용과 반복 연습의 조건에 한정하며, 사용량이 많다는 사실만으로 학습 성과가 높아진다고 단정하지 않는다.

### 기획자·디자이너·비개발자의 역할

출처: 경험담 원문의 커뮤니케이션 비용·대표 사례, 통합 초안의 역할 경계, 기존 원칙 초안의 후속 질문. 최근 생각은 [2편 메모](../ai_coding_part2_notes.md)의 「비개발자는 처음의 선택을 검증하기 어렵다」를 참고한다.

- 기획 의도에서 동작하는 결과물을 빠르게 만들 수 있을 때 기획자·디자이너는 어떤 판단과 완료 기준을 맡는가?
- 백엔드·프론트엔드·UX가 책임 범위를 넓히는 일과 전문성의 필요성을 어떻게 함께 설명할 것인가?
- 비개발자도 첫 서비스를 만들 수 있지만, 어떤 조건을 고려해야 하는지 모르면 AI가 제안한 기술 스택과 도구를 평가하기 어렵다는 주장이 있다.
- 프로젝트가 커진 뒤 드러나는 운영·성능·연동·변경 비용과 초기 선택을 연결해 설명할 수 있다.
- [프로젝트 전체 검토 자료](../PROJECT_REVIEW_2026-09-04.md)가 추가됐고, [사례 15](./01_experiences.md#case-15)에 관찰과 증거 범위를 정리했다. 저자가 5월 초에 처음 본 뒤 약 네 달이 지난 9월 초에 검토한 자료라고 확인했다. 격리 환경 재현과 코드 검토를 실제 운영 사고나 수정 완료로 확대해 쓰지 않는다.

### 소프트웨어 산업과 아키텍처 선택

별도 초안 [AI_AFTER_SOFTWARE.md](../AI_AFTER_SOFTWARE.md)에 이미 모여 있다. 생산 비용 하락과 프로젝트 수요, MSA와 모듈러 모놀리스의 선택 기준을 다룬다. 이곳에 본문을 다시 복사하지 않고 후속 글 자료로 연결한다.
