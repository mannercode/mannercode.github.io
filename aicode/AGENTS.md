# AI 코딩 문서 작업 지침

## 프로젝트 목적과 현재 상태

- 이 프로젝트의 주 산출물은 AI 개발을 고민하는 프로그래머를 위한 한국어 A to Z 에세이인 `README.md`다.
- 독자에게 AI 도구 사용법만 소개하는 문서가 아니라, AI 시대의 개발 방식과 개발자의 역할 변화, 발생하는 문제와 통제 방법을 다루는 문서를 지향한다.
- 현재는 완성된 원고를 다듬는 단계가 아니라 생각나는 논지를 계속 수집하고 적절한 위치에 통합하는 단계다. 세부 목차와 순서는 논지가 늘어남에 따라 조정할 수 있다.
- `README.md`가 원고의 정본이다. `DB_SCHEMA_COMPLEXITY.md`는 README의 DB 복잡도 사례에서 사용하는 실제 사례이자 근거 문서다.

## 확정된 편집 방향

- 전체 구조는 세 개의 **챕터**로 유지한다. `1. AI로 어떻게 개발하며 기존 방식과 무엇이 다른가`, `2. 어떤 문제가 발생하는가`, `3. 그 문제를 어떻게 통제하고 해결할 것인가`의 흐름이다. 이를 부(部)라고 부르지 않는다.
- 용어는 `AI 코딩`으로 통일한다. `바이브 코딩`이나 별도의 개발 방식 이름은 사용하지 않는다.
- 핵심 주장은 AI가 구현 비용과 시간을 크게 줄이지만 개발자의 판단력과 설계 능력, 최종 책임까지 자동으로 대신하지는 않는다는 것이다.
- AI는 분석, 설계, 구현, 검증, 배포와 운영 전반의 작업을 도울 수 있다. 다만 목표와 우선순위, 채택할 설계, 증거의 충분성, 통합과 출시 여부는 사람이 판단하고 책임진다.
- 기존 개발 프로세스와 소프트웨어 공학을 폐기한다는 주장이 아니다. 높아진 생성 속도를 감당하려면 경계와 계약, 테스트 자동화, 회귀 검증, CI와 운영 통제가 더 이른 시점부터 필요하다는 주장이다.
- 검토의 중심은 요구사항과 완료 조건, 인터페이스와 시스템 경계, 실제 테스트 코드와 반복 가능한 증거다. 테스트 대상 구현을 일일이 정독하는 일을 기본 승인 절차로 삼지 않되, 복잡하거나 위험한 변경은 필요에 따라 직접 확인할 수 있다. 직접 검토만으로 승인하지 않고 반복 가능한 검증 조건을 우선한다.
- AI는 실패를 숨기는 편법뿐 아니라 요청하지 않은 보안, 추상화와 의존성을 추가해 과잉 구현할 수도 있다. AI가 테스트 초안을 만들더라도 사람이 실제 테스트 코드의 시나리오와 기대 결과를 검토한다. 승인된 스펙 테스트는 구현 단계에서 임의로 바꾸지 못하게 하고, 내부 구현 테스트는 필요한 곳에 보조적으로 사용한다. 커버리지 100%는 명세를 대신하지 않지만 측정 범위에 실행되지 않은 코드가 남지 않게 하는 품질 게이트로 사용할 수 있다.
- 직접 코딩의 가치를 부정하지 않는다. 프로덕션의 기본 생산 방식과 기초 원리·판단력을 익히기 위한 학습 훈련을 구분한다.
- AI의 설계는 정답이 아니라 검토할 후보안이다. AI의 폭넓은 지식과 유창한 설명을 프로젝트 맥락에 맞는 판단력으로 간주하지 않는다.

## 문체와 저자의 목소리

- 한국어로 명료하게 쓰되 중립적인 교과서나 기업 보고서 문체로 평탄화하지 않는다.
- 1995년 무렵의 C 학습, 97학번으로 받은 전산 교육, 실제 프로젝트의 설계·출시·운영 경험처럼 저자의 1인칭 경험과 문제의식을 살린다.
- 먼저 주장을 분명히 제시하고 그 주장이 나온 인과관계와 실제 개발 상황을 설명한다. 필요한 반례와 적용 한계는 덧붙이되 핵심 주장이 흐려질 만큼 방어적인 문장으로 만들지 않는다.
- AI를 무조건 유능하거나 무능하다고 단정하지 않는다. AI가 잘하는 일과 사람이 맡아야 하는 판단을 구체적으로 구분한다.
- 인용문, 목록과 소제목은 논지를 선명하게 할 때만 사용하고 같은 결론을 여러 형식으로 반복하지 않는다.

## 편집 작업 방식

- 사용자가 정리되지 않은 생각을 제시하면 먼저 의도를 파악한 뒤 기존 흐름에서 가장 적절한 위치에 통합한다. 표현이 모순되거나 의미가 갈릴 때는 해석한 의도를 짧게 밝힌다.
- 편집하기 전에 대상 절과 앞뒤 절을 함께 읽는다. 이미 있는 주장과 겹치면 새 절이나 새 문서를 만들기보다 기존 문장을 합치거나 재배치한다.
- 사용자가 직접 고친 문장과 경험은 저자의 원문으로 취급한다. 명백한 오류나 전체 논지와의 충돌이 없다면 목소리를 임의로 바꾸지 않는다.
- 코드, 스키마나 기존 원고에서 확인할 수 있는 내용을 별도 문서에 장문으로 복제하지 않는다. 새 문서는 독립적인 목적과 갱신 책임이 있을 때만 만든다.
- 사실과 저자의 경험·해석을 구분한다. 시점에 따라 바뀔 수 있는 외부 사실이나 제품 정보는 가능한 한 공식·1차 자료로 확인한다.
- 편집 후에는 제목 번호와 링크, 중복된 주장, Markdown 문법, 후행 공백과 충돌 표식을 확인한다.

## DB 복잡도 사례의 취급

- `DB_SCHEMA_COMPLEXITY.md`의 내용을 README에 장문으로 복제하지 말고 필요한 사실만 요약한 뒤 원문에 링크한다.
- 이 사례를 단순히 “테이블이 많아서 나쁘다”거나 “AI가 제시한 추가형 원칙 하나가 틀렸다”는 이야기로 축소하지 않는다. 합리적인 임시 결정이 적용 범위와 종료 조건 없이 반복됐고, 백엔드 방향 전환, 병렬 도메인 모델, 분산된 변경 소유권과 최종 정리 미실행이 함께 복잡성을 만들었다.
- DB 수치와 상태는 2026-07-12 스냅샷이다. 이를 현재 상태로 다시 사용할 때는 읽기 전용으로 재검증하고 사실과 해석을 구분한다.
- 고객 데이터, 파트너명, 이벤트명, UUID, 프로젝트 식별자와 인증정보는 기록하거나 공개하지 않는다. 서비스 규모나 프로젝트명을 외부에 공개할 때도 사용자의 승인을 먼저 받는다.
